# PLAN-038 — сквозная проверка файловых задач

Проверка 2026-10-07 на изолированном временном Git-проекте и отдельном локальном bare-remote `origin` с `main`. Использовались Python 3, PyYAML и [`sov-task`](../cli/sov-task/README.md) из этого checkout; общая `.sov/` находилась в основной папке проекта и была исключена из Git. Действующие проекты и их состояния не изменялись. Временные данные удалены после успешного прогона.

## Сценарий и результаты

1. Через `create --file` созданы пять YAML-карточек: `0001` — основа, `0002` и `0004` зависят от `0001`, `0003` — независима, `0005` — отдельная проба переноса. Сначала `list-ready` вернул `0001, 0003`; явный `claim 0002` вернул `not_ready`. Новая задача после архивации `0001` получила следующий ID `0005`.
2. Два параллельных **отдельных процесса** вызвали `claim-next` с разными диагностическими owner. Результат: `0001` и `0003` захвачены разными процессами, повторный `claim 0001` вернул `not_ready`, следующий `claim-next` — `no_ready_tasks`. `release 0003` вернул задачу в `READY`; повторный `claim` с owner `stale-probe` создал каталог claim. После завершения этого процесса сверены диагностический `owner`, отсутствие артефакта работы и чистый Git; неверный owner не смог сделать `release`. Для моделирования ручного восстановления удалён **только этот пробный** stale claim; новый `claim` с owner `recovered` прошёл. Сам по себе `owner` не подтверждает, что исполнитель остановился: в настоящем проекте потребовалась бы ещё проверка сеанса и worktree.
3. В `0001` записаны `task.md` и `checks.md`. До публикации ни marker, ни доступность зависимых задач не появились. Результат проекта закоммичен и опубликован через `git push origin main`; итоговый SHA `895093e1bec6f2ce4d894c14f98ab1103c925ce0` проверен чтением `main` в отдельном bare-remote. Только после этого вручную введено прерывание: создан `completed/0001`, но каталог ещё находился в `tasks/`. `show` показал `INCOMPLETE_COMPLETION`, `validate` вернул `valid:false`, `release` отказал; **`list-ready` уже показал `0002, 0004`**. Повторный `complete 0001` переместил весь каталог с артефактами в архив, удалил claim. Проверены marker, архив и отсутствие исходного каталога и claim.
4. Для `0005` искусственно выполнены marker и перенос `tasks/ → archive/`, но сохранён claim (прерывание перед последним шагом). `validate` обнаружил неполное завершение; повторный `complete 0005` удалил claim и сохранил `research.md` в архиве. Отдельный `complete 0004` без claim вернул ошибку и не создал marker. Итоговый `validate` вернул `valid:true`, `list-ready` — `0002, 0004`.

Прогон выполнен командой `python3 tests/filesystem_task_trial.py` из корня SOV; итог: `PASS`, занятые ID `0001, 0003`, готовые после marker `0002, 0004`, архивные ID `0001, 0005`. [Сценарий](../tests/filesystem_task_trial.py) создаёт временный стенд и проверяет ответы CLI, каталоги и Git assert-проверками; данные стенда удаляются по завершении.

## Границы подтверждения

- `complete` не проверяет Git и публикацию: правило «marker только после подтверждения удалённого `main`» проверено как порядок действий испытания и как требование [протокола](specs/filesystem-tasks.md), а не как запрет CLI. Вторая искусственная инъекция marker/rename для `0005` проверяла только восстановление файлового состояния, **не** успешную публикацию отдельной задачи.
- Промежуточный marker разблокирует зависимость, несмотря на `validate:false`; отсутствие многофайловой транзакции — реальная граница. Агент обязан диагностировать и завершить перенос, а не считать marker доказательством полного архива. Прогон не моделировал параллельный запуск зависимого агента в этом промежутке.
- Временный bare-remote подтверждает локальный Git push, но не работу GitHub, CI или OpenCode TUI; полная интерактивная оркестрация скилов и проектная установка из worktree здесь не испытывались. Атомарность на сетевых/разных файловых системах, выключение питания, автоматическое определение stale claim и проверка циклов зависимостей также не проверялись и не заявлены как гарантии CLI.

Применимые правила и порядок ручного восстановления: [спецификация](specs/filesystem-tasks.md), [скил задач](../skills/sov-tasks/SKILL.md), [инструкция установки](install-filesystem-tasks.md).
