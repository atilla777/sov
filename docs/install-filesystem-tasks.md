# Подключение SOV с файловыми задачами

Инструкция для агента, подключающего закреплённый выпуск SOV к целевому проекту с Git и OpenCode. [Протокол](specs/filesystem-tasks.md) использует Go CLI внутри [скила `sov-tasks`](../skills/sov-tasks/SKILL.md). При явном поручении обновить установленный выпуск используй также [скил `sov-update`](../skills/sov-update/SKILL.md); подробный порядок обновления приведён ниже. Подключение или обновление каждого проекта — отдельное поручение: публикация исходников SOV не меняет уже работающие сеансы и данные.

## Подготовка выпуска

1. Прочитай правила и требования целевого проекта, проверь Git и наличие других писателей. Выбери отдельный неизменяемый checkout SOV (`<sov>`) и абсолютный путь к основной копии проекта (`<project>`). Проверь Go 1.25.4 (или совместимую более новую версию), Git, OpenCode, локальную ФС с `flock` и атомарными `mkdir`/`rename`; исходники `skills/sov-tasks/`, остальные `skills/*/SKILL.md`, семь команд `templates/opencode/commands/sov*.md`, шаблоны артефактов у скилов и в `templates/`, файлы агентов, `templates/AGENTS.md` и `templates/installation.md` должны принадлежать одному выпуску.
2. Из `<sov>/skills/sov-tasks/` выполни `go test -race ./...`. Собери `go build -o <bin-dir>/.sov-task-next .` в **существующем каталоге назначения** (он может находиться вне неизменяемого checkout). Проверь кандидата на отдельном пробном хранилище; с остановленными писателями атомарно замени в этом же каталоге `<bin-dir>/sov-task`. Не заменяй бинарник, который ещё используют сеансы другого выпуска. Запиши абсолютный путь к проверенному бинарнику в правилах проекта; Go требуется для сборки, но не для его работы.

## Первое подключение

1. Добавь абсолютный `<sov>/skills` к `skills.paths` проектного `opencode.json` или `.opencode/opencode.json`, сохрани существующие настройки. Установи семь команд `/sov`, `/sov-feature`, `/sov-bug`, `/sov-fast`, `/sov-decompose`, `/sov-retro`, `/sov-update` из `<sov>/templates/opencode/commands/` в `<project>/.opencode/commands/`. Сверь одноимённые файлы и пользовательские правки; при конфликте с глобальными `/sov*` согласуй, какую версию видит проект, до работы. Установи агентов из `<sov>/templates/opencode/agents/` в `<project>/.opencode/agents/`, настрой доступные `model` для `sov-standard` и `sov-advanced`, не меняй `build`/`plan`. Проверяй объединённые настройки через `opencode debug config`, `opencode debug agent sov-standard` и `opencode debug agent sov-advanced`, модели — через `opencode models <provider>`; фактический запуск проверяй через `task` основного агента.
2. Только при новой установке без прежнего состояния добавь `.sov/` в корневой `.gitignore` и создай **в основной копии** `<project>/.sov/` с пустыми `tasks/`, `claims/`, `completed/`, `archive/`. Проверь `git check-ignore .sov/tasks/0001-probe/task.yaml` и `git check-ignore .sov/installation.md`. Если `.sov/` уже существует, не создавай пустую замену: выясни источник и состояние данных до переключения. Не создавай вторую `.sov/` внутри worktree.
3. По [образцу локальной записи](../templates/installation.md) создай `<project>/.sov/installation.md` с проверенным закреплённым commit SOV, абсолютными `<sov>`, `<project>`, `<project>/.sov`, `<bin-dir>/sov-task`, файловым источником через `sov-tasks` и размещением команд, агентов и настроенных моделей. Этот локальный файл нужен для установки и обновления, а не для каждого запуска оркестратора. В опубликованных `rules/`, доступных через `rules/index.md`, зафиксируй абсолютные пути к основной папке, общему `.sov/` и бинарнику `sov-task`, источник задач, remote, проверки и порядок публикации; эти операционные пути `sov-tasks` использует из основной копии и worktree. В проектном `AGENTS.md` по [образцу](../templates/AGENTS.md) оставь общие правила проекта без упоминания SOV и без ссылки на локальную запись. Из любой worktree используй один и тот же `state-dir`, например `"<bin-dir>/sov-task" --state-dir "<project>/.sov" validate`. При необходимости разреши OpenCode чтение `<sov>/**`, запуск бинарника и доступ к `<project>/.sov/**` через узкие `permission.external_directory`; успех терминальной команды не доказывает права агента.
4. Перезапусти OpenCode. Из основной копии и пробной worktree с **той же устанавливаемой конфигурацией** проверь соответствие локальной записи установки фактической конфигурации и опубликованным операционным путям, `validate` и `list`, права на бинарник, шаблон и артефакты, обнаружение команд и скилов, обе модели и реальный вызов субагентов. Проверь, что обычный запрос на правку файла не загружает SOV, а `/sov` загружает оркестратор без чтения локальной записи. На изолированном состоянии проверь `create`, `show`, `claim`, `release`; `complete` вызывай только после подтверждения внешних условий. Проверяй `/sov-decompose` на опубликованной Spec: отсутствие однозначной опубликованной Spec не должно создавать карточки. Если проектная конфигурация ещё не опубликована, используй worktree от локального коммита с ней и повтори проверку из чистой worktree после публикации.

Для ретро проверь обнаружение [`sov-retro`](../skills/sov-retro/SKILL.md) и `/sov-retro`, чтение завершённой задачи и уточнение запроса без известного ID. Ретро не запускается после `done` само по себе. Для необязательного чтения явно связанных трасс отдельно установи официальный [скил Langfuse](https://langfuse.com/docs/api-and-data-platform/features/agent-skill) и его [CLI](https://langfuse.com/docs/api-and-data-platform/features/cli); ключи настраиваются в окружении. Без них проверь отчёт по архивным артефактам с указанием ограничения. После изменения файлов команд или скилов перезапусти OpenCode.

## Проектный `AGENTS.md`

При первой установке прочитай существующий `AGENTS.md`, индексы `rules/index.md` и `docs/index.md`, применимые правила и требования проекта. Если `AGENTS.md` отсутствует, создай его как точку входа для общих проектных правил с проверенными ссылками на существующие индексы; если индексов ещё нет, создай или согласуй их в рамках установки. Не копируй [шаблон](../templates/AGENTS.md) поверх существующего файла и не добавляй в `AGENTS.md` упоминание SOV либо ссылку на `.sov/installation.md`: запись нужна только установке и ручному обновлению. Сохрани пользовательские разделы, порядок и действующие правила. При переносе старой подробной секции подключения удали лишь сверенные установочные сведения после записи в локальный файл; проектные правила проверок, операционные пути и публикацию оставь в `rules/`. При конфликте обязательного PR/защиты ветки с прямой публикацией SOV в `main` останови подключение и согласуй решение с владельцем проекта.

Шаблон лежит вне `.opencode/`: OpenCode читает заполненный `AGENTS.md` из корня целевого проекта, а не исходный образец выпуска SOV. Команды `/sov*` загружают оркестратор самостоятельно; обычная просьба, даже «используй SOV», не активирует маршрут SOV.

При обновлении подключения сверь локальную запись основной копии с новой закреплённой версией, опубликованными операционными путями, командами, агентами и фактическими проверками; не заменяй весь `AGENTS.md` шаблоном и не меняй пользовательские модели без решения проекта. Если запись утрачена, не выводи прежний выпуск только из наличия каталога `.sov/` или видимости `/sov`: сверяй реальные конфигурацию и ресурсы, при неопределённости остановись. Инструкция перехода и остановки писателей приведена ниже.

## Обновление действующего подключения

Перед изменениями сверь явное поручение, текущий закреплённый commit, фактические абсолютные пути к checkout, бинарнику, `skills.paths`, командам, агентам, основной копии и `.sov/` с локальной `.sov/installation.md`, опубликованными `rules/` и настройками OpenCode. Для установки прежнего выпуска с подробной секцией в `AGENTS.md` сверь её по тем же критериям перед переносом; отсутствие нового файла в таком проекте ожидаемо. Установи перечень задач и claims, worktree, незавершённых публикаций, артефакты, `git status` и пользовательские правки. При отсутствии локальной записи **и** проверяемых сведений прежней установки, несовпадении, чужой работе или конфликте правил уточни решение владельца до переключения: не создавай запись по догадке. Докажи остановку всех писателей (включая CLI и старые OpenCode-сеансы) и сохрани проверяемую копию `.sov/`; новый бинарник и инструкции не должны работать одновременно со старыми сеансами над одним состоянием. Подготовь **отдельный** закреплённый checkout и кандидат бинарника по разделу [«Подготовка выпуска»](#подготовка-выпуска); не обновляй исходники или бинарник, которыми ещё пользуются другие проекты.

При обновлении файлового протокола сверь карточки, маркеры, архив и зависимости с новым выпуском. Если проект использует иной источник задач, сначала согласуй судьбу **каждой** задачи и артефактов: автоматической конвертации Markdown-таблиц, статусов и назначений нет. Старые открытые задачи, worktree и незавершённые публикации требуют решения до допуска писателей. Не теряй историю и не подставляй пустое состояние вместо старого.

При переходе на выпуск с `type`/`executor` проверь `validate` и просмотр активных и архивных карточек: исторические без **обоих** полей остаются читаемыми без классификации по умолчанию, один пропущенный или неправильное сочетание блокируют работу до сверки карточки. Новые карточки создаются только с обоими полями; существующим классификацию добавляй после явного решения по содержанию. Проверь из основной копии и worktree выбор с пропуском готовой внешней задачи без claim, ручное подтверждение получения по критериям и разблокировку зависимой задачи лишь после marker на отдельном пробном состоянии. `/sov` предлагает fast для тривиальной разработки и ждёт согласия, `/sov-fast` оценивает результат и риск; действующие сессии переключаются только после перезапуска.

До замены сверь одноимённые файлы команд и агентов и локальные настройки: пользовательские правки не перезаписывай без решения. Для прежнего выпуска источник команд мог находиться в `<старый sov>/.opencode/commands/` или глобально; используй фактическую закреплённую версию для сверки старых копий, а новую — из `<новый sov>/templates/opencode/commands/`. При глобальном размещении согласуй переход на проектные команды и разреши одноимённые конфликты, чтобы из основной копии и worktree загружался один выпуск. Переключи вместе проектные пути и закреплённый commit, бинарник, скилы, команды и агентов; не перезаписывай пользовательские модели и настройки `build`/`plan`. Одновременно обнови локальную запись `.sov/installation.md` по [образцу](../templates/installation.md) и опубликованные операционные пути в `rules/`. Если прежний `AGENTS.md` содержал установочные параметры или ссылку на запись, перенеси их лишь после сверки, сохрани проектные правила в `rules/` и убери SOV-вход из `AGENTS.md` по [разделу о проектных инструкциях](#проектный-agentsmd); не публикуй локальную запись вместе с конфигурацией. Конфликт маршрута публикации согласуй до изменения.

Перезапусти OpenCode, повтори из основной копии и worktree с одной `.sov/` проверку локальной записи на соответствие реальным ресурсам и опубликованным операционным путям, обнаружения команд и скилов, прав доступа, шаблонов и фактического вызова обеих моделей через субагентов. Проверь обычный запрос без SOV и явный `/sov` без чтения записи установки. Выполни `validate`, `list`, `show`, `list-completed` и сверку ожидаемых задач и claims; пробы записи проводи только на отдельном состоянии. Проверь diff и обязательные проверки установки, затем опубликуй проектные изменения по согласованным правилам и подтверди публикацию. До подтверждения результата писателей не запускай. При отрицательной проверке оставь их остановленными, запиши точное препятствие и фактическое состояние, сообщи владельцу; не выполняй автоматический откат после новых claims или завершений.

Описание команд и пределов валидации: [Go CLI](../skills/sov-tasks/README.md).
