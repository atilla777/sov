# Подключение SOV с файловыми задачами

Инструкция для агента, подключающего закреплённый выпуск SOV к целевому проекту с Git и OpenCode. [Протокол](specs/filesystem-tasks.md) использует Go CLI внутри [скила `sov-tasks`](../skills/sov-tasks/SKILL.md). Подключение или обновление каждого проекта — отдельное поручение: публикация исходников SOV не меняет уже работающие сеансы и данные.

## Подготовка выпуска

1. Прочитай правила и требования целевого проекта, проверь Git и наличие других писателей. Выбери отдельный неизменяемый checkout SOV (`<sov>`) и абсолютный путь к основной копии проекта (`<project>`). Проверь Go 1.25.4 (или совместимую более новую версию), Git, OpenCode, локальную ФС с `flock` и атомарными `mkdir`/`rename`; исходники `skills/sov-tasks/`, остальные `skills/*/SKILL.md`, пять команд `.opencode/commands/sov*.md`, шаблоны и файлы агентов должны принадлежать одному выпуску.
2. Из `<sov>/skills/sov-tasks/` выполни `go test -race ./...`. Собери `go build -o <bin-dir>/.sov-task-next .` в **существующем каталоге назначения** (он может находиться вне неизменяемого checkout). Проверь кандидата на отдельном пробном хранилище; с остановленными писателями атомарно замени в этом же каталоге `<bin-dir>/sov-task`. Не заменяй бинарник, который ещё используют сеансы другого выпуска. Запиши абсолютный путь к проверенному бинарнику в правилах проекта; Go требуется для сборки, но не для его работы.

## Первое подключение

1. Добавь абсолютный `<sov>/skills` к `skills.paths` проектного `opencode.json` или `.opencode/opencode.json`, сохрани существующие настройки. Установи пять команд `/sov`, `/sov-feature`, `/sov-bug`, `/sov-fast`, `/sov-decompose` из `<sov>/.opencode/commands/` глобально либо в проекте. Сверь одноимённые файлы и пользовательские правки. Установи агентов из `<sov>/templates/opencode/agents/` в `<project>/.opencode/agents/`, настрой доступные `model` для `sov-standard` и `sov-advanced`, не меняй `build`/`plan`. Проверяй объединённые настройки через `opencode debug agent sov-standard` и `opencode debug agent sov-advanced`, модели — через `opencode models <provider>`; фактический запуск проверяй через `task` основного агента.
2. Только при новой установке без прежнего состояния добавь `.sov/` в корневой `.gitignore` и создай **в основной копии** `<project>/.sov/` с пустыми `tasks/`, `claims/`, `completed/`, `archive/`. Проверь `git check-ignore .sov/tasks/0001-probe/task.yaml`. Если `.sov/` уже существует, не создавай пустую замену: выясни источник и состояние данных до переключения. Не создавай вторую `.sov/` внутри worktree.
3. Запиши в проектном `AGENTS.md`/`rules/` закреплённый commit SOV, абсолютные `<sov>`, `<project>`, `<project>/.sov`, `<bin-dir>/sov-task`, файловый источник через `sov-tasks`, расположение агентов/моделей, remote, порядок проверок и публикации. Определи проектные правила и профиль документов. Из любой worktree используй один и тот же `state-dir`, например `"<bin-dir>/sov-task" --state-dir "<project>/.sov" validate`. При необходимости разреши OpenCode чтение `<sov>/**`, запуск бинарника и доступ к `<project>/.sov/**` через узкие `permission.external_directory`; успех терминальной команды не доказывает права агента.
4. Перезапусти OpenCode. Из основной копии и пробной worktree с **той же устанавливаемой конфигурацией** проверь `validate` и `list`, права на бинарник, шаблон и артефакты, обнаружение команд и скилов, обе модели и реальный вызов субагентов. На изолированном состоянии проверь `create`, `show`, `claim`, `release`; `complete` вызывай только после подтверждения внешних условий. Проверяй `/sov-decompose` на опубликованной Spec: отсутствие однозначной опубликованной Spec не должно создавать карточки. Если проектная конфигурация ещё не опубликована, используй worktree от локального коммита с ней и повтори проверку из чистой worktree после публикации.

## Обновление действующего подключения

Установи текущую закреплённую версию, перечень задач и claims, worktree, артефакты и пользовательские правки. Останови всех писателей и сохрани проверяемую копию `.sov/`; новый бинарник и инструкции не должны работать одновременно со старыми сеансами над одним состоянием. Подготовь **отдельный** закреплённый checkout и кандидат бинарника; не обновляй исходники, которыми ещё пользуются другие проекты.

При обновлении файлового протокола сверь карточки, маркеры, архив и зависимости с новым выпуском. Если проект использует иной источник задач, сначала согласуй судьбу **каждой** задачи и артефактов: автоматической конвертации Markdown-таблиц, статусов и назначений нет. Старые открытые задачи, worktree и незавершённые публикации требуют решения до допуска писателей. Не теряй историю и не подставляй пустое состояние вместо старого.

Переключи вместе проектные пути и версию, бинарник, скилы, команды и агентов; не перезаписывай пользовательские модели. Перезапусти OpenCode, повтори проверки основной копии и worktree, выполни `validate`, `list`, `show`, `list-completed` и сверку ожидаемых задач. До подтверждения результата писателей не запускай. Если проверка не прошла, оставь их остановленными и разбери фактическое состояние; не выполняй автоматический откат после новых claims или завершений.

Описание команд и пределов валидации: [Go CLI](../skills/sov-tasks/README.md).
