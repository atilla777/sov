# Проект: локальная CLI для условного сохранения общего списка задач

Статус: **проект перехода**, не описание установленного механизма. По PLAN-017 согласовано изменение §§1 и 6 спецификации и добавлены [исходники CLI](../cli/sov-state/README.md); установка и переключение действующих инструкций остаются отдельными задачами из Obsidian `SOV - backlog.md`. Исходные правила: [спецификация SOV](sov-spec.md), [файловый учёт задач](../skills/sov-tasks/SKILL.md), [образец списка](../templates/ROADMAP.md).

## 1. Установленное состояние и границы изменения

- Реально существует скил `skills/sov-tasks/SKILL.md`, а не консольная программа `sov-tasks`. Его файловый источник — `<основная папка проекта>/.sov/ROADMAP.md`, явно выбранный в правилах целевого проекта. Абсолютный путь к основной папке передаётся из этих правил; относительный `.sov/` в worktree не является общим состоянием. `.sov/` игнорируется Git; `.sov/tasks/<ID>/` и `.sov/worktree/<ID>/` общие для проекта, но имеют иное назначение. Установка и доступ из worktree описаны в [README](../README.md#установка-и-обновление-в-существующем-проекте-для-агента), ветки и worktree — в [`sov-git`](../skills/sov-git/SKILL.md).
- В `ROADMAP.md` находятся следующий ID, физический порядок строк (очередь), название, статус, устойчивый исполнитель, зависимости, признак публикации. Поля приоритета нет: изменение приоритета сейчас означает согласованную перестановку строк. Нет отдельного общего файла статусов/назначений. `task.md` в папке задачи содержит основания, ход работы, причины блокировки и доказательство публикации, но не второй общий статус. Создание папки и её артефактов выполняет оркестратор, не `sov-tasks`.
- Записи сейчас выполняет `sov-tasks` как инструкция агенту: инициализация отсутствующего списка из шаблона; создание задачи и увеличение следующего ID; назначение вместе с `in_progress`; изменение статуса, исполнителя, зависимостей, названия, публикации и порядка; завершение после подтверждения PR. При каждой записи он перечитывает файл и проверяет его, но атомарной проверки версии и публикации нет. `sov-spec` предлагает декомпозицию и передаёт создание/обновление `sov-tasks`; `sov-orchestrator` вызывает его для выбора, назначения и завершения; команды `/sov*` вызывают оркестратор. `README.md` разрешает при первом подключении прямое создание списка из шаблона. Остальные скилы не должны редактировать `ROADMAP.md` напрямую. `sov-git` меняет Git/worktree, `sov-okf` — документацию рабочей копии; эти действия не являются записью в список.
- [`docs/sov-spec.md`](sov-spec.md) §§1 и 6 уточнены по PLAN-017: вспомогательная CLI предусмотрена, но независимые координаторы допускаются лишь после подключения и проверки общего протокола записи. §§7 и 12 допускают иной CLI-источник задач после подключения, но **это не готовая поддержка локальной CLI**. Пока рабочая интеграция не опубликована, действуют старые ограничения. `AGENTS.md` содержит устаревшую фразу «Скилы SOV пока не реализованы»; фактические исходники находятся в `skills/`, а `README.md` отражает их наличие.

После перехода не должно остаться инструкции прямой **записи** в существующий `ROADMAP.md`, включая обновление установки и ручную «починку» списка без контролируемой процедуры обслуживания.

## 2. Предлагаемый контракт CLI

Имя бинарника `sov-state` (не совпадает со скилом `sov-tasks` и командами `/sov*`). Основные подкоманды `read` и `commit`; флаги одинаковы независимо от cwd. Служебный `--version` сообщает версию исходников SOV и версию протокола JSON (`v: 1`) для проверки установки. Первая версия — Go, Linux, локальная ФС с работающими `flock`, `rename` и `fsync`; не сервер, не хранилище задач и не инструмент merge.

```text
sov-state read   --state-dir /abs/project/.sov
sov-state commit --state-dir /abs/project/.sov --expected sha256:<64 lowercase hex> --input /abs/local/new-roadmap.md --lock-timeout 5s
```

`--state-dir` обязателен, абсолютный путь; указывает **один явно настроенный** в правилах проекта каталог основной копии, а не текущую worktree. При запуске CLI приводит каталог к физическому абсолютному пути (разрешает symlink каталога) и открывает только `ROADMAP.md` внутри него; флага выбора произвольного целевого файла нет. Выбранная область MVP — **только существующий** `.sov/ROADMAP.md`. `read` возвращает bytes файла, закодированные в base64 внутри JSON, и `revision = sha256:` + SHA-256 ровно этих bytes (включая завершающую новую строку). Ограничение размера входного списка и нового файла — 16 MiB для предсказуемой памяти; превышение — некорректный ввод для `--input`, ошибка ФС/ресурса при чтении списка. Контент Markdown CLI не парсит.

`commit` считывает `--input` в память **до** получения lock (не изменяет входной файл), затем в короткой критической секции берёт эксклюзивный `flock`, читает цель, проверяет revision и при совпадении публикует bytes; новый revision вычисляется из новых bytes. `--input` — отдельный локальный регулярный файл, он не может быть целевым файлом, mutex-файлом или их hardlink; symlink входа разрешён только к регулярному локальному файлу, проверяемому при чтении. Результат операции выводится одной JSON-строкой в stdout, диагностические подробности можно писать в stderr. Нельзя интерпретировать отсутствие ответа как отказ от записи. Договоримся о схеме ответа `v: 1`, `status`, `resource`, `revision` для успеха и `code`, `message`, `may_have_committed` для ошибок; при конфликте дополнительно `current_revision`. `resource` всегда `ROADMAP.md`, полное содержимое возвращается **только** `read`. По умолчанию ожидание lock 5s; `--lock-timeout` принимает неотрицательную длительность Go (`0s` — немедленно), ограничение 60s; для `read` lock не нужен.

| Exit | `status` / `code` | Значение |
| --- | --- | --- |
| 0 | `ok` | Успех (для `commit` также `changed: false` при одинаковых bytes). |
| 10 | `error` / `revision_conflict` | Expected уже не совпадает; файл не менялся этим вызовом. |
| 11 | `error` / `lock_timeout` | Не удалось получить mutex вовремя; файл не менялся этим вызовом. |
| 12 | `error` / `invalid_input` | Неизвестная команда, неверный флаг/revision/путь/вход или недопустимый тип файла. |
| 13 | `error` / `io_error` | Доступ, отсутствие состояния/файла, чтение, запись, `rename` или `fsync`; `may_have_committed` показывает, возможна ли публикация до ошибки. |

Примеры: `read` пустого существующего файла, затем `commit` файла с единственным байтом `a` при указанном expected, затем конфликт второй попытки с прежним expected:

```json
{"v":1,"status":"ok","resource":"ROADMAP.md","content_base64":"","revision":"sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"}
{"v":1,"status":"ok","resource":"ROADMAP.md","revision":"sha256:ca978112ca1bbdcafac231b39a23dc4da786eff8147c4e72b9807785afee48bb","changed":true}
{"v":1,"status":"error","resource":"ROADMAP.md","code":"revision_conflict","current_revision":"sha256:ca978112ca1bbdcafac231b39a23dc4da786eff8147c4e72b9807785afee48bb","message":"revision changed","may_have_committed":false}
```

Отсутствующий `.sov` или `ROADMAP.md` — `io_error` с `message` о пути, никакого автоматического создания пустого списка или revision «отсутствует». Одинаковое содержимое при совпавшем expected — успех `changed:false`, без `rename`; при несовпавшем expected даже идентичный ввод — конфликт. После потери ответа повторное чтение и проверка **нужного смыслового результата**, а не только совпадения hash, определяют дальнейшее действие.

### Адресация и lock

Рекомендуемое правило целевого проекта: у всех worktree одинаковый настроенный абсолютный путь к основной папке и `state-dir=<main>/.sov`; запуск из worktree не меняет этот путь. CLI канонизирует существующий каталог `.sov` до открытия файла. Алиасы каталога через symlink сходятся к одному физическому каталогу и lock. `ROADMAP.md` должен быть обычным файлом без symlink и hardlink (`nlink == 1`); alias целевого файла не разрешён, проверка типа и inode выполняется при каждом вызове. Mutex — постоянный `<state-dir>/.roadmap.lock`, один на проект: сериализует все записи в один ROADMAP, включая изменение разных строк; отдельные mutex на задачи не защищали бы общий файл. Открывать mutex без перехода по symlink, требовать обычный файл с одним link, проверять inode открытого дескриптора с записью по имени после получения lock; неожиданный тип/подмена → ошибка, не публикация. Создавать mutex один раз при установке (0600); CLI не создаёт отсутствующий mutex при `commit` (ошибка `io_error`), не удаляет и не заменяет его при штатной работе, включая обновление и уборку временных файлов. Все участники используют один протокол. Одновременная внешняя подмена каталога/lock непривилегированным конфликтующим процессом вне протокола не входит в гарантию MVP; при обнаружении расхождения — остановка.

### Публикация и сбои

При совпадении revision под lock: создать уникальный временный файл `.<ROADMAP>.tmp-*` посредством безопасного эксклюзивного создания в **том же каталоге**, записать все bytes и обработать короткие записи/ошибки, унаследовать mode существующего списка (для нового списка через отдельную инициализацию — 0600; сохранять mode без расширения прав; если не удаётся — отказ), `fsync` temp и закрыть его с проверкой ошибок, `rename` temp поверх `ROADMAP.md`, затем `fsync` каталога до ответа об успехе. При ошибке до rename удалить только свой temp, оставить старую версию; после rename не откатывать чужой/свой файл, ошибка `fsync` каталога даёт `io_error` с `may_have_committed:true` и требует read. При SIGKILL lock снимается ядром после закрытия дескриптора, прежний либо новый файл виден целиком; оставшийся уникальный temp не является опубликованным и удаляется при плановом обслуживании только после проверки, что он не используется. Ошибка после фактического `rename` или потеря stdout также разрешается проверкой состояния, не слепым повтором.

На поддерживаемой локальной ФС `rename` обеспечивает атомарность имени для читателей: `read` открывает файл один раз и считывает из одного дескриптора до конца, поэтому получает целую старую либо новую версию. Завершение процесса до публикации не повреждает старую. `fsync` temp **до** rename и каталога **после** него — политика MVP для устойчивости при штатных гарантиях ФС; это не обещание пережить любой аппаратный сбой/особенности ФС. До успешного `fsync` каталога при потере питания новая версия может не сохраниться; после ошибки `fsync` или потери ответа исход считать неопределённым и перечитать. `flock` advisory и работает только для сотрудничающих процессов на одном компьютере/локальной ФС.

### Границы гарантий

Прямые записи в обход CLI не защищаются; пока хотя бы старый писатель жив, безопасная конкуренция не подтверждена. Успешный commit подтверждает актуальность **байтовой исходной версии**, не правильность смысла правки. Один файл — одна условная публикация, не транзакция над `.sov/tasks/<ID>/task.md`, Git или несколькими файлами. SHA-256 содержимого — не монотонный номер истории: переход A→B→A возвращает прежний revision (ABA); для MVP важна актуальность содержимого, не идентичность истории. Утилита не проверяет статус, исполнителя, зависимости, права на изменение задачи, опубликованность PR и не делает merge Markdown. Инициализация отсутствующего списка, восстановление утраченного `.sov/` и перенос между машинами вне MVP.

## 3. Предлагаемое поведение `sov-tasks`

Для **каждой** операции записи (создание, ID, перестановка строк, изменение полей, назначение, завершение):

1. `sov-state read --state-dir ...` → декодировать `content_base64`, проверить формат всего списка и сохранить revision; смысловые проверки выполнять над этим содержимым и актуальными внешними условиями (например, слияние PR).
2. Построить целиком новую версию в отдельном локальном файле **в папке данной задачи или отдельном временном каталоге сессии**, не редактируя `ROADMAP.md` напрямую. Проверить результирующий список, сохранение остальных строк и очереди.
3. `sov-state commit --expected <прочитанный revision> --input <подготовленный файл> ...`. Только `ok` подтверждает назначение/создание/переход; `changed:false` не создаёт новый ID и не подтверждает несуществующее назначение.
4. На `revision_conflict` перечитать файл, заново проверить предусловия операции и **заново собрать изменение**, включая выбор ID/строки/зависимостей. Нельзя просто заменить expected у прежнего файла. Максимум 3 попытки commit на одну операцию (включая первую), с небольшим ограниченным случайным ожиданием; после исчерпания сообщить конфликт/препятствие и сохранить контекст для ручного продолжения. `lock_timeout` — остановка или не более одного повтора после read и проверки предпосылок; `invalid_input`/`io_error` — устранить причину, при неопределённой публикации сначала сверить фактическое состояние. Никаких бесконечных повторов.

Для одновременной попытки взять одну `planned` задачу только один commit исходной версии выигрывает; проигравший перечитывает, видит чужое назначение и выбирает другую доступную задачу либо останавливается. Выполнение, создание worktree и изменение артефактов **после** подтверждённого назначения. Используется нынешнее поле `Исполнитель` — устойчивый ID **отдельного независимого исполнителя** из правил проекта; для двух одновременных сессий нужны два различающихся устойчивых ID (например, именованные рабочие слоты), сохраняющихся для возобновления. Если несколько независимых сессий используют один ID, запись не позволяет отличить продолжение своей работы от чужой: такие сессии не должны параллельно выбирать/продолжать одну задачу; переход к поддержке этого случая потребовал бы отдельного маркера claim и правил передачи, он не включён в MVP. Формат всех строк менять не требуется.

После прерывания, потери stdout либо `may_have_committed:true` прочитать свежий список, проверить ID, исполнителя, статус и конкретный желаемый эффект; если он уже достигнут — сверить артефакты и продолжить, без повторного изменения; если другой участник занял задачу/изменил основание — не повторять прежнюю правку; если результата нет — провести новый полный цикл. Для создания задачи узнавать выданный ID по содержимому и контексту операции; **если нельзя однозначно отличить собственную созданную строку от чужой совпадающей**, остановиться и запросить решение, не создавать дубликат. Для предсказуемого восстановления можно заранее записывать намерение и уникальный контекст операции в локальный материал поручения, но не считать его вторым статусом или гарантией атомарного создания.

Необходимой многофайловой транзакции в MVP не обнаружено: `task.md` и запись списка могут расходиться после прерывания. Минимальный порядок: для создания — сначала подтверждённая строка списка, затем папка/`task.md`; отсутствие папки обнаруживается при возобновлении и доводится до согласованного состояния. Для `done` — сначала доказательство публикации в `task.md` и GitHub, затем CAS статуса; повторно проверять реальный PR при возобновлении. Если создание/изменение задания требует дополнительного артефакта, сообщить промежуточное состояние и завершить его прежде чем считать операцию целиком выполненной. Не пытаться скрыть окно между двумя файлами.

## 4. План проверок и перехода

### Поставка в составе установки SOV

Исходники Go поставляются **в той же закреплённой версии SOV**, что `skills/`, `templates/` и команды OpenCode; в первой версии бинарник собирается локально из этих исходников при подключении или обновлении SOV. Предлагаемое расположение одного общего исполняемого файла — `<sov>/bin/sov-state`, где `<sov>` — уже настроенная общая папка установленной версии SOV, доступная из основной копии и всех worktree. Если установка SOV размещена без возможности записи, установщик заранее выбирает иной **единый абсолютный** каталог для бинарника и фиксирует его в правилах проекта; не создаёт отдельные копии в worktree и не полагается на случайный `PATH`. Агент вызывает зафиксированный абсолютный путь. Требуется установленный Go для сборки; если сборка невозможна, установка версии с новым файловым протоколом не объявляется завершённой.

При первом включении протокола (в новом или ранее подключённом проекте) агент: проверяет версию SOV и поддерживаемую платформу, собирает из её исходников во временный файл в каталоге назначения, проверяет запуск `--version` и совместимость `v:1`, публикует бинарник заменой файла без частично записанного исполняемого файла; проверяет наличие исходного `ROADMAP.md`, создаёт один постоянный mutex при отсутствии **только при первом включении**, проверяет права и `read` из основной копии и пробной worktree с одним `--state-dir`. Адрес каталога состояния и путь к CLI записываются в правилах целевого проекта, как и путь/версия SOV. Скил сам себя не компилирует при каждом вызове: развертывание — явный шаг инструкции установки из [`README.md`](../README.md), которую предстоит обновить в PLAN-018, а не неявное действие `sov-tasks`.

При обновлении агент сравнивает текущие закреплённую версию SOV, бинарник, команды и инструкции с новыми. На согласованном окне без старых писателей собирает и проверяет новую CLI, затем согласованно обновляет установленный путь к CLI и файлы инструкций/команд; до включения нового `sov-tasks` проверяет версию/контракт, исполнение, права и доступ к **тому же** ROADMAP и mutex из основной копии и worktree. После обновления OpenCode перезапускается, а оставшиеся старые сессии не пишут в общее состояние до явного возобновления на новой версии. Список и mutex нельзя пересоздавать при обновлении. При провале сборки или проверок сохраняют прежнюю работоспособную установку и правило одного координатора, не переходят к прямой записи при уже включённом новом протоколе. Для первых установок без бинарника новый протокол включается лишь после этих проверок; одно присутствие скила или бинарника недостаточно. Совместимость версий проверяется до активации, а переключение **нескольких файлов установки** не считается атомарной транзакцией — поэтому нужно окно без старых писателей.

**CLI, автоматизированные тесты Go + отдельные процессы:** два commit с одним revision и разными bytes (ровно один `ok`, второй `revision_conflict`); read/rebuild/retry сохраняет обе правки; конкурентные commits разных строк одного файла; `read` во время цикла больших замен не видит частичного файла; дочерний процесс удерживает lock и убивается — следующий процесс получает lock; остановка до rename оставляет старый файл (инъекция сбоя в точках записи/синхронизации); результат после потерянного stdout распознаётся повторным read; два запуска из разных worktree с одним настроенным `--state-dir` используют одну физическую цель и lock; алиасы/symlink/hardlink, неверные flags/revision, отсутствующий список, права доступа, ошибка записи/`fsync`, timeout и no-op проверяются по отдельным кодам и отсутствию повреждений. Инъекции сбоев в тестах не должны становиться публичной командой CLI.

**`sov-tasks`, проверки сценариев инструкций на пробном проекте:** две сессии с различающимися устойчивыми ID пытаются назначить одну задачу — работает только победитель; изменение двух разных задач в одном ROADMAP через конфликт и пересборку не теряет ни одной; создание двух задач выдаёт разные ID и двигает счётчик; изменение порядка и зависимостей после конфликта пересчитывается, цикл и отменённая зависимость отклоняются; `done` только после подтверждения PR; прерывание между записью списка и `task.md` восстанавливается; три конфликта дают явную остановку; потерянный ответ разрешается read, а не вторым безусловным commit. Тесты CLI доказывают байтовую атомарность, не семантическую корректность: маршруты и предусловия проверяются отдельно инструкцией.

**Порядок включения:** сначала согласовать изменение §§1, 6, 7, 12 [спецификации](sov-spec.md) и разработать CLI/тесты отдельно от действующих скилов; затем выполнить описанную выше установку бинарника из закреплённой версии SOV и проверить разрешения OpenCode на запуск/доступ к общему каталогу из основной копии и worktree. На согласованном окне без старых писателей проверить инициализированный ROADMAP, сохранить резервную копию по правилам проекта, проинвентаризировать активные сессии и назначения. Остановить/закончить старые сессии или перевести их на обновлённые инструкции **до** параллельных записей; перезапустить OpenCode после обновления установки. Только затем одновременно включить CAS-маршрут в `sov-tasks`, установку и ссылки других инструкций, убрать прямую запись, провести сквозные параллельные сценарии и зафиксировать результат. Если инструмент недоступен, не переходить молча на прямую запись и не объявлять параллельный режим активным; в ожидании миграции применять прежнее правило одного координатора. Установленный бинарник сам по себе не переключает источник задач и не заменяет другой возможный CLI-источник (например, REST API).

## 5. Допущения и вопросы перед реализацией

1. У всех сессий одна локальная Linux-ФС с корректным `flock` и `rename`; сетевые/синхронизируемые каталоги и конкурирующие несотрудничающие писатели исключены.
2. В MVP один ROADMAP и один mutex на проект; дополнительные общие файлы добавляются только при отдельной проверке владельца и необходимости. `task.md` предполагает одного ответственного писателя в рамках задачи; одновременное редактирование его несколькими сессиями вне гарантии.
3. В целевом проекте различаются устойчивые ID независимых исполнителей. Решение о работе нескольких одновременных сессий **под одним** ID потребует отдельного согласования модели claim/передачи, а не скрытого изменения шаблона.
4. При обновлении уже работающих проектов требуется определить конкретное окно переключения, местоположение основного каталога и способ остановки старых сессий. Пока установка и принятый источник явно не проверены, новая защита отсутствует.
