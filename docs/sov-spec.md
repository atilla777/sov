# SOV — спецификация принципов работы

> **Действующий протокол задач (2026-10-07).** Учёт задач целевых проектов определяется [SOV Tasks](specs/filesystem-tasks.md): `.sov/tasks/`, `.sov/claims/`, `.sov/completed/`, `.sov/archive/` и Go CLI `sov-task` внутри `skills/sov-tasks/`. Подключённые проекты переключаются отдельно по [инструкции](install-filesystem-tasks.md): публикация исходников не мигрирует данные.

## 1. Назначение

SOV — набор взаимосвязанных скилов (Agent Skills) и шаблонов артефактов для организации разработки с помощью агентов в средах типа OpenCode.

SOV задаёт порядок подготовки продуктовой спецификации, планирования технической реализации, разработки, независимой проверки и публикации изменений. Скилы универсальны: особенности конкретного проекта определяются его документацией и правилами.

SOV не содержит собственного программного движка выполнения задач или сервера. Скилы являются инструкциями, которые читает и выполняет агент. Для работы используются инструменты среды и доступные внешние утилиты, например Git и GitHub CLI. Текущие инструкции для файловых задач используют Go CLI `sov-task`, поставляемую со скилом `sov-tasks`, по [SOV Tasks](specs/filesystem-tasks.md); наличие исходников не означает подключения в целевом проекте.


Оркестратором является основной агент, работающий по инструкциям скила `sov-orchestrator`. Он определяет необходимые шаги, управляет их выполнением, передаёт контекст исполнителям и проверяет результаты.

SOV устанавливает обязательные правила работы агентов, но сам по себе не обеспечивает программную невозможность их нарушения. Ограничения доступа и опасных действий задаются средствами среды запуска и правилами проекта.

## 2. Постановка задачи и границы поручения

### Единая точка входа

Пользователь описывает желаемый результат обычным языком либо указывает существующую задачу. Выбирать тип задачи и последовательность шагов не требуется. Обязательного поля «тип задачи» в SOV нет.

Для OpenCode при установке SOV предусматриваются пользовательские команды `/sov`, `/sov-feature`, `/sov-bug`, `/sov-fast`, `/sov-decompose` и `/sov-retro`, передающие запрос одному и тому же оркестратору. `/sov` — универсальный вход; `feature` и `bug` подсказывают предмет обращения, `/sov-fast` явно выбирает политику быстрого маршрута для данного поручения, `/sov-decompose` выражает явную просьбу о декомпозиции опубликованной Spec, а `/sov-retro` — просьбу о ретроспективе. Команда не расширяет границы поручения. Это команды среды, а не отдельные консольные программы SOV и не скилы шагов.

Примеры обращений:

```text
/sov-feature Обсудим систему сохранения игры и подготовим продуктовую спецификацию.
/sov-feature Подготовь спецификацию системы сохранения и задачи для реализации.
/sov-bug Найди причину пропажи предметов после загрузки.
/sov-bug Исправь пропажу предметов после загрузки.
/sov Выполни задачу №42.
/sov Продолжай текущую задачу.
/sov
/sov-fast Исправь небольшую ошибку установщика hook.
/sov-decompose Разбей опубликованную спецификацию docs/specs/saves.md на задачи.
/sov-retro Проанализируй сессии задачи №42 и предложи улучшения.
```

Если задача явно указана для исполнения или продолжения, оркестратор работает с ней после проверки её состояния и условий начала работы. Наличие задачи само по себе не означает поручения писать код: маршрут определяется ожидаемым результатом. Указание номера не отменяет зависимости задачи и не позволяет забирать её у другого исполнителя. Указание ID для ретро означает read-only анализ существующих свидетельств, а не захват или возобновление задачи.

При запросе продолжить без ID действующий `sov-tasks` сверяет файловые задачи, claim, артефакты и Git по [SOV Tasks](specs/filesystem-tasks.md#состояния-зависимости-и-выбор) и [инструкции скила](../skills/sov-tasks/SKILL.md): занятый claim не даёт другому сеансу права продолжать даже при совпадении `owner`; после освобождения готовую задачу захватывают заново, а оставшийся после аварии claim разбирают вручную. При недоступном источнике задач оркестратор не угадывает прежнюю задачу и не создаёт вместо неё новую очередь. Новый запрос без ID рассматривается как отдельное поручение, а не как команда продолжить прежнюю задачу.


Команда `/sov-feature` помогает начать обсуждение фичи, а `/sov-bug` — исследование либо исправление ошибки. Если запрос к этим командам ограничен обсуждением или поиском причины, оркестратор не переходит к реализации без соответствующего поручения.

### Определение результата

До начала существенной работы оркестратор определяет ожидаемый результат и границы поручения, учитывая запрос, предыдущие договорённости, состояние задачи и правила проекта. Он кратко сообщает человеку своё понимание предстоящей работы. Вход `/sov` или `/sov-fast` не определяет заранее, требуется ли разработка.

Оркестратор самостоятельно выбирает способ достижения результата, но не расширяет само поручение. Обсуждение фичи не означает разрешения реализовать её. Просьба выяснить причину ошибки не означает поручения исправить её. Подготовка спецификации не означает, что описанная возможность должна быть реализована в той же задаче.

Подтверждать каждое действие не требуется. Вопрос задаётся, если существенная неоднозначность меняет ожидаемый результат, объём работы или допустимые действия и не разрешается имеющимися сведениями.

Обсуждение, консультация или разовое разъяснение могут завершиться ответом без создания задачи, worktree и артефактов, если результат не нужно сохранять в проекте. Если поручение предполагает сохраняемую работу над проектом (в том числе исследование, подготовку требований или изменение файлов), оркестратор создаёт либо использует существующую задачу и записывает необходимые результаты в её артефакты. При исследовании без исправления не создаются технический план и рабочая копия для реализации только ради прохождения маршрута разработки; для сохраняемого изменения файлов действуют правила рабочей копии и публикации. Если результат должен поступить извне, оркестратор фиксирует, что именно ожидается и от кого, и не объявляет результат полученным или зависимую работу готовой по одному лишь ожиданию. Учёт внешних зависимостей и способ их закрытия уточняются в [SOV Tasks](specs/filesystem-tasks.md) отдельно; ожидание не является разрешением обойти зависимости.

По умолчанию один запуск выполняет одно поручение или одну выбранную задачу. Подготовка спецификации фичи не создаёт задачи реализации: после её подтверждённой публикации явная просьба о задачах запускает `sov-decompose`, но не их реализацию. Просьба о Spec и задачах в одном поручении считается явной просьбой о декомпозиции после публикации. После завершения оркестратор сообщает следующую доступную задачу, но не начинает её без указания пользователя; следующую задачу рекомендуется вести в новой сессии.

## 3. Выбор последовательности шагов

### Принцип выбора

Оркестратор выбирает последовательность шагов на основании цели и границ поручения, состояния задачи, доступных артефактов и применимых правил проекта.

Он использует типовой маршрут как основу и при необходимости адаптирует его по установленным правилам. Команда помогает понять намерение пользователя, но не заменяет определения результата и границ поручения.

Типовые маршруты:

| Поручение | Последовательность скилов-шагов |
|---|---|
| Ответ или обсуждение без сохраняемого результата | Ответ без задачи, worktree и формальных шагов. |
| Подготовка продуктовой спецификации | `sov-spec → sov-review-spec → публикация требований`; обсуждение без подготовки требований может завершиться ответом. |
| Явно запрошенная декомпозиция опубликованной спецификации | После подтверждения публикации требований в удалённом `main`: `sov-decompose` → создание карточек через `sov-tasks`; реализация не начинается. Запрос на Spec и задачи вместе сохраняет просьбу о декомпозиции до публикации. |
| Разработка подготовленной задачи | `sov-plan → sov-implement → sov-review-implementation`. |
| Исследование ошибки без исправления | `sov-research` (диагностика причины и предложение решения); после исследования человек получает отчёт и может запросить независимую перепроверку вывода по инструкции `sov-research`. |
| Исправление ошибки | `sov-research → sov-plan → sov-implement → sov-review-implementation`. |
| Явная ретроспектива задач или сессий | Аналитический `sov-retro` → отчёт в диалоге по умолчанию; без автоматического продолжения разработки. |
| Ожидание внешнего результата | Зафиксировать ожидаемый результат и условия продолжения; не начинать зависимую разработку до подтверждения получения и проверки пригодности результата. |

После необходимых шагов оркестратор публикует результат прямым push в удалённый `main`, если поручение предполагает публикацию. Подготовленная для разработки продуктовая спецификация публикуется до декомпозиции и начала зависимых задач. Публикация и обновление состояния задачи — действия оркестратора, а не дополнительные скилы-шаги. Исследование без исправления не переходит к реализации, а обсуждение вариантов не требует публикации.

### Явный быстрый маршрут

Типовые маршруты выше действуют для `/sov`, `/sov-feature` и `/sov-bug`. Если `/sov` получает тривиальное поручение разработки, для которого уместен пропуск обычных шагов, оркестратор предлагает быстрый маршрут **для этого поручения** и ждёт согласия человека; при отказе применяет обычный маршрут, а отсутствие ответа не считается согласием и не разрешает пропуск шагов. При других входах без `/sov-fast` пропуск обязательного шага также требует отдельного согласования. После согласия требования к свидетельствам, входам и проверкам при пропуске те же, что в быстром маршруте, но согласие относится только к указанным шагам, а не ко всем последующим решениям агента. Проектные правила могут устанавливать более строгие условия. Выбранный режим и основание выбора фиксируются в `task.md` для сохраняемой задачи и сверяются при её продолжении; быстрый режим не переносится молча на другое поручение. Если прежний выбор режима не подтверждён, применяется обычный маршрут либо запрашивается решение человека.

Явный `/sov-fast` выбирает быструю политику без отдельного согласия на сам режим, но не обещает сокращённый маршрут: для поручения без разработки выбираются только шаги, необходимые его результату, а при разработке оркестратор оценивает ясность и риск. Для небольшого, ясного и обратимого изменения он сам определяет необходимость отдельных `sov-research`, `sov-plan` и итогового `sov-review-implementation`. Он кратко записывает в `task.md` факты, подтверждающие ожидаемое поведение и решение, границы, риск, выбранные/пропущенные шаги и применимые проверки; отдельные `research.md` и `plan.md` не требуются, если соответствующие шаги обоснованно пропущены. Для сохраняемого изменения файлов проекта задача, захват и рабочая копия ведутся по обычным правилам; быстрая реализация может выполняться основным агентом без формального вызова `sov-implement` либо через него при наличии пригодных входов. При пропуске независимого ревью основной агент самостоятельно сверяет итоговый diff, требования и свидетельства проверок; эта самопроверка не называется независимым ревью.

Итоговое независимое ревью **нельзя пропустить** при разработке основного кода игры или движка. В остальных задачах его назначают, если риск ошибки оправдывает ревью: например, изменение может отключить чужие hooks или проверки, повлиять на данные, публичный интерфейс, труднообратимое действие либо имеет неясные последствия. Быстрый маршрут не отменяет согласование нового/изменённого продуктового поведения и необходимое ревью его спецификации, обязательные проверки, учёт сохраняемой работы и публикацию по правилам проекта. При неопределённой причине, конкурирующих решениях, существенных зависимостях, высоком риске или новых рисках оркестратор назначает необходимые формальные шаги до продолжения, используя пригодные уже полученные результаты; даже явный `/sov-fast` не оправдывает их пропуск. Открытые замечания устраняются и перепроверяются независимо от режима.

Шаг можно не выполнять повторно, если необходимый результат уже существует и проверен на пригодность. Для разработки новой функциональности нужны опубликованные согласованные требования в `docs/specs/` целевой ветки либо в применимых опубликованных источниках проекта; отдельный локальный `spec.md` не обязателен. Однозначный баг можно исправлять без предварительной публикации отдельной продуктовой спецификации, если ожидаемое поведение зафиксировано в задаче, подтверждается свидетельствами и не противоречит опубликованным требованиям. До выполняемого `sov-plan` нужны определённое ожидаемое поведение и, в обычном маршруте исправления, пригодный результат `sov-research`; пригодный `plan.md` требуется перед `sov-implement` обычного маршрута. В быстром маршруте при обоснованном пропуске отдельных шагов достаточные факты и решение записываются в `task.md`. Технический план не подменяет продуктовые требования.

### Уточнение маршрута

Типовые маршруты задаются этой спецификацией. Применимость шагов, выбранная последовательность, состояние работы и результаты проверки существующих артефактов сохраняются в локальных материалах задачи. Инструкции выполнения находятся в скилах и применимых правилах проекта.

При появлении новых требований, результатов исследования или замечаний оркестратор пересматривает маршрут и фиксирует причину изменения. Изменение маршрута не может использоваться для обхода обязательных проверок или неустранённых замечаний.

Если ожидаемое поведение при исправлении неясно, противоречит опубликованным требованиям или требуется его изменить, оркестратор возвращается к `sov-spec` и обеспечивает согласование требований и `sov-review-spec` до реализации. Существенное изменение цели или объёма оформляется отдельной связанной задачей; небольшое уточнение может оставаться в текущей задаче, если входит в поручение. Сам по себе большой объём технических изменений не требует повторного обсуждения продуктовых требований, когда ожидаемое поведение уже определено.

## 4. Состав SOV

### Оркестратор

**`sov-orchestrator`** — управление выполнением поручения. Определяет задачу и результат, выбирает маршрут, проверяет условия шагов, привлекает субагентов, принимает результаты, управляет возвратами, публикацией и состоянием задачи, формирует итоговый отчёт.

### Скилы шагов

| Скил            | Ответственность                                                                                                                                                                                                                                                       |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sov-spec`      | Обсуждение фичи, уточнение потребности и сценариев; подготовка продуктовой спецификации без деталей реализации, при необходимости ADR с выбранными и отклонёнными техническими решениями. Включение согласованных требований в `docs/specs/`. |
| `sov-decompose` | По явной просьбе после подтверждённой публикации Spec: проверяемые задачи реализации, их объём, зависимости и покрытие требований; создание карточек только через `sov-tasks`. |
| `sov-research`  | Для бага — воспроизведение, исследование причины, свидетельства и предложение решения; если причину установить не удалось, фиксируется препятствие либо обоснованная гипотеза без объявления её установленной причиной. |
| `sov-plan`      | Техническая спецификация и план реализации задачи разработки или исправления ошибки, включая проверки и риски; при исправлении использует результат `sov-research`, не проводя диагностику вместо него. |
| `sov-implement` | Изменение кода и тестов по требованиям и техническому плану, запуск и исправление тестов до успешного прохождения обязательных проверок, сохранение их результатов, актуализация затронутых спецификаций и правил в пределах согласованного поведения.                |
| `sov-review-spec` | Независимая проверка продуктовой спецификации перед публикацией: ясность и согласованность поведения, сценарии, ограничения, критерии приёмки; замечания и проверка их устранения. Задачи реализации для этого ревью не требуются. |
| `sov-review-implementation` | Независимая проверка результата реализации перед публикацией: код, тесты, результаты проверок и затронутая документация в сопоставлении с требованиями, границами задачи и техническим планом; замечания и проверка их устранения. Качество самого плана не оценивается повторно на этом шаге: при обнаружении ошибки плана оркестратор возвращает задачу к `sov-plan`. |

`sov-spec` определяет ожидаемое поведение в диалоге с человеком: уточняет потребность и варианты поведения, задаёт вопросы, фиксирует ответы и закрывает существенные открытые вопросы. Когда все вопросы, влияющие на требования, закрыты, итоговая спецификация считается согласованной в рамках поручения; отдельное формальное подтверждение не требуется, если его не требуют правила проекта. Перед публикацией оркестратор показывает человеку отчёт с результирующей спецификацией или точной ссылкой на её полный текст и даёт возможность указать на расхождения с договорённостями. Если обнаружено расхождение, требования уточняются и необходимые шаги проверки повторяются до публикации. ADR фиксирует существенный технический выбор и обоснование, но не превращает продуктовую спецификацию в технический план. После публикации оркестратор может предложить декомпозицию, но без явной просьбы не запускает её. `sov-research` исследует причину ошибки; `sov-plan` определяет способ выполнения конкретной задачи. `sov-implement` не меняет согласованные требования только для того, чтобы они соответствовали написанному коду: при расхождении исправляется реализация либо отдельно согласуется изменение требований через `sov-spec`.

Уточнение потребности, оформление документации и публикация не требуют отдельных скилов-шагов: они выполняются в рамках ответственного шага либо оркестратором. Диагностика ошибки — отдельный шаг `sov-research`. Наличие отдельного артефакта само по себе не подразумевает отдельный скил.

### Вспомогательные скилы

`sov-retro` — отдельный аналитический скил, вызываемый только по явному запросу через `/sov`, `/sov-retro` или напрямую. Он восстанавливает ход одной задачи, указанных сессий или набора задач по доступным артефактам, истории и Git; при наличии явной связи трасс с ID задачи либо указанных пользователем точных ID/ссылок сессий может читать Langfuse через отдельный низкоуровневый официальный скил `langfuse` и его CLI. Связь только по времени, проекту или тексту недопустима. При отсутствии доступа к трассам анализ продолжается с указанием ограничений; отсутствие записи не доказывает отсутствие действия. Вывод отделяет свидетельства от гипотез и предлагает проверяемые улучшения для проекта либо SOV. Отчёт остаётся в диалоге, если не запрошен постоянный документ; сохранение документа подчиняется правилам задач проекта, а применение рекомендаций требует отдельного согласования. Ретро не является шагом обязательного маршрута после `done` и не запускается автоматически по неудаче или замечаниям.

| Скил | Ответственность |
|---|---|
| `sov-tasks` | Создание и выбор задач, выдача идентификаторов, ведение порядка, статусов, зависимостей и назначений, проверка согласованности списка задач. Скрывает способ хранения учётных данных задач. |
| `sov-git` | Операции с репозиторием, ветками, worktree и GitHub через доступные инструменты согласно правилам проекта. |
| `sov-okf` | Оформление документации и правил по принятому в проекте профилю Open Knowledge Format (OKF): структура, метаданные, индексы и ссылки. |

`sov-tasks` управляет учётными данными задач, `sov-git` — веткой, рабочей копией и публикацией в GitHub. Декомпозицию опубликованных требований по явной просьбе выполняет `sov-decompose`, а создание и изменение карточек задач — только `sov-tasks`. Для действующего файлового источника `sov-tasks` использует собранную из собственных Go-исходников CLI `sov-task` закреплённой версии SOV; CLI не принимает смысловых решений. Артефакты в каталоге задачи ведут ответственные скилы шагов; оркестратор ведёт `task.md`. Остальные скилы не редактируют хранилище задач напрямую. Вспомогательные скилы не являются шагами каждого маршрута.

`sov-okf` определяет оформление документов, но не содержание требований и не продуктовые решения. Формат документов OKF не подменяет формат скилов.

## 5. Правила выполнения шагов

### Входы, действия и результаты

Скил шага определяет универсальные входы, границы действий, ожидаемый результат, условия завершения и основания для возврата либо остановки. Проектные особенности выполнения он берёт из `rules/`, а ожидаемое поведение — из `docs/` и поручения. Скил не закрепляет язык, инструменты сборки, конкретные тестовые команды или формат проектной спецификации.

Шаг может выполняться только при наличии пригодных обязательных входов. Артефакт пригоден, если относится к нужной задаче, содержит необходимые сведения, соответствует актуальным требованиям и состоянию изменений и не содержит открытых вопросов, препятствующих этому шагу.

Пустой шаблон, устаревший документ или неподтверждённое утверждение о проверке не считаются достаточным входом. Артефактами могут быть не только Markdown-файлы, но также изменения кода, тесты и результаты выполнения инструментов.

После изменения входов оркестратор пересматривает пригодность зависимых результатов. Повторяются только необходимые шаги: исправление опечатки не равнозначно изменению требований или технического решения.

### Работа с субагентами

Оркестратор работает в текущем основном агенте среды (например, `build` или `plan` в OpenCode) на выбранной пользователем модели. Команды `/sov*` не переключают модель или режим. Для шагов установлены уровни возможностей `standard` и `advanced`, сопоставляемые конкретным моделям **при подключении SOV в целевом проекте**, а не внутри скилов:

| Работа | Уровень по умолчанию |
|---|---|
| `sov-spec`, `sov-decompose`, `sov-research`, `sov-implement` | `advanced` |
| `sov-plan` | `standard` |
| `sov-review-spec`, `sov-review-implementation` | `advanced` |

Вспомогательные `sov-tasks`, `sov-git` и `sov-okf` вызываются ответственным агентом и не требуют собственной модели. Для плана с миграцией данных, изменением публичного интерфейса, труднообратимыми действиями или сложными межкомпонентными зависимостями оркестратор повышает `sov-plan` до `advanced` с записью причины. Адресная перепроверка исследования использует `advanced`; перепроверка плана — уровень проверяемого плана (при высоком риске `advanced`). Снижение установленного уровня шага не производится молча: изменение политики проекта требует явного согласования, а изменение модели, соответствующей уровню, — настройки проекта.

Формальные шаги выполняются отдельными субагентами выбранного уровня; простое обсуждение и непосредственную быструю реализацию без формального шага может вести основной агент. Выполняемые `sov-review-spec` и `sov-review-implementation` проводят независимые субагенты, не участвовавшие в подготовке проверяемого результата; одинаковый уровень или тип субагента не означает повторное использование автора. Оркестратор поручает субагенту выполнить формальный шаг с использованием соответствующего скила. При отсутствии настроенной или доступной модели либо необходимого субагента он сообщает о препятствии, не подменяет модель наследованием основного агента и не выдаёт обязательный шаг за выполненный. Ограничения основного режима среды сохраняются: из режима без разрешения на запись оркестратор не запускает пишущий шаг под видом субагента, а сообщает о необходимости перейти в режим разработки.

Поручение содержит идентификатор задачи и шаг, выбранный уровень, ожидаемый результат, нужный скил, путь к рабочей копии кода и к локальной папке артефактов задачи, применимые требования и правила либо точные ссылки на них, а также границы допустимых изменений. Оркестратор фиксирует в `task.md` реально выбранный уровень и модель исполнителя, основание повышения и сверяет их при продолжении работы. Субагент читает и сохраняет артефакты своего шага в переданной папке; нельзя предполагать, что он автоматически располагает всем контекстом основного агента.

Субагент возвращает сведения о выполненной работе, созданных и изменённых артефактах, фактических проверках, оставшихся проблемах и вопросах. Основной диалог с человеком ведёт оркестратор; вопросы субагентов передаются через него.

Оркестратор принимает результат после проверки артефактов и условий завершения, а не только на основании сообщения исполнителя «готово».

## 6. Задачи, план и параллельная работа

**Действующий учёт задач:** [SOV Tasks](specs/filesystem-tasks.md) определяет карточки `task.yaml`, порядок по ID, зависимости через `completed/<id>`, захват каталогом `claims/<task>/` и перенос каталога задачи с артефактами в `archive/`. `sov-tasks` использует `sov-task`; постоянный владелец, UUID координатора и прежние статусы для этого протокола не требуются. Оркестратор начинает работу только после подтверждённого claim, сверяет состояние при возобновлении и не снимает чужой claim без проверки. Общие правила требований, worktree и публикации ниже сохраняются.

`sov-tasks` предоставляет перечень задач с ID, вычисленным состоянием, зависимостями и порядком по ID. Оркестратор выбирает готовую задачу через него, не разбирая файлы самостоятельно.

**Правила начала и выполнения задач:**

Условия начала зависят от поручения: для новой функциональности нужны опубликованные согласованные требования; для исправления бага достаточно определённого ожидаемого поведения, а при его неоднозначности задача может начинаться с согласования требований без перехода к реализации. Результат исследования и технический план не требуются до начала задачи, которая должна их подготовить.

Если доступных задач нет, оркестратор сообщает причины и не снимает блокировки самостоятельно ради продолжения работы. Прерывание сессии само по себе не освобождает claim.

Карточки целевого проекта различают `type: development | non_development` и `executor: agent | external` по [SOV Tasks](specs/filesystem-tasks.md#формат-taskyaml). Это классификация ожидаемого результата и исполнителя, а не файловый статус и не автоматический маршрут. Агентская подготовка требований или исследование без исправления относится к `non_development + agent`; внешняя поставка — к `non_development + external`, а зависимая разработка — к отдельной `development + agent` задаче. Для исторической карточки без обоих полей маршрут определяется по её содержанию с уточнением неоднозначности; недопустимые сочетания не исполняются. При выборе без ID внешние задачи сообщаются человеку и пропускаются без claim; их наличие само по себе не блокирует выбор следующей подходящей агенту задачи. Файловое `READY` означает выполненные зависимости, но не получение внешнего результата.

Состояние задачи предоставляется `sov-tasks`; его независимая копия в локальных артефактах не ведётся. Подробное состояние шагов и причины препятствий оркестратор сохраняет в локальных материалах задачи.

После подтверждённой публикации Spec в удалённом `main` и только по явному запросу (в том числе через `/sov-decompose`, `/sov` или прямую просьбу оркестратору) `sov-decompose` проверяет покрытие требований задачами и отсутствие циклов зависимостей. Если применимая Spec не определяется однозначно, её уточняют до создания карточек. Задачи реализации создаются через `sov-tasks` после публикации; если задача подготовки существует, её завершённый ID можно указать как зависимость, но внешняя опубликованная Spec не требует выдумывать ID подготовки. Перед началом реализации дополнительно проверяется актуальность требований.

Для параллельного выполнения изменений каждой задаче выделяются отдельная ветка и Git worktree через `sov-git`. Ветка задачи реализации создаётся от актуального удалённого `main`, содержащего применимые опубликованные требования; при исправлении однозначного бага без отдельной спецификации проверяется отсутствие противоречий с опубликованными источниками. При последующем изменении требований оркестратор проверяет актуальность входов ещё не завершённых зависимых задач. Перед прямым push каждой параллельной задачи заново проверяются актуальный удалённый `main` и совместимость после публикации других задач.

При явном сообщении человека о готовности внешнего результата оркестратор сверяет ID, проверяемые критерии и подтверждение получения, записывает свидетельства в локальный `task.md` и через `sov-tasks` захватывает и завершает доступную карточку. Ожидание, обещание или неполная поставка не дают основания создать `completed/<id>`. Если файлы проекта не изменялись, публикация в `main` для этого завершения не нужна; при изменениях действуют обычные проверки и публикация. Зависимая работа разблокируется только созданным marker. Подробный порядок — в [SOV Tasks](specs/filesystem-tasks.md#завершение-и-архив).

## 7. Структура проекта и источники истины

**Структура целевого проекта** (формат каталога `.sov/` подробно определён в [SOV Tasks](specs/filesystem-tasks.md#хранилище-и-идентичность)):

```text
project/
├── AGENTS.md
├── rules/
│   ├── index.md
│   └── *.md
├── docs/
│   ├── index.md
│   ├── specs/
│   └── adrs/
└── .sov/
    ├── tasks/<id>-<slug>/
    │   ├── task.yaml
    │   └── *.md
    ├── claims/
    ├── completed/
    └── archive/
```

`AGENTS.md` — точка входа для агентов. Содержит обязательные общие инструкции и порядок обращения к скилам SOV, индексам, применимым правилам и спецификациям. Перед работой агент читает правила, относящиеся к выбранному шагу и затрагиваемым частям проекта; ссылка без прочтения необходимого документа недостаточна.

`rules/` — настраиваемые правила проекта: архитектура и ограничения, язык и стек, стиль, требования к продуктовой и технической спецификациям, ADR, тестам, ревью, документации и публикации. Здесь задаются применимые команды и критерии проверок, remote и порядок прямой публикации в `main`. Правила находятся через `rules/index.md` и применяются ко всем затронутым шагам, а не копируются в каждый скил; документы оформляются по принятому профилю OKF.

Скилы SOV задают неизменные для проектов границы ответственности, необходимые результаты и условия перехода между шагами. Правила проекта уточняют способы выполнения и могут добавлять требования, но не отменяют границы поручения, проверку результатов, независимость ревью и подтверждение прямой публикации в удалённом `main` перед закрытием публикуемой задачи. При противоречии правил (например, при обязательном PR или запрете прямого push) и этих условий оркестратор останавливается и сообщает о конфликте, а не выбирает удобную трактовку.

`docs/specs/` — постоянные продуктовые спецификации согласованного ожидаемого поведения независимо от степени реализации. Они описывают, что должна делать фича, её сценарии и ограничения, но не дублируют внутреннее устройство кода и технический план задачи. Внешние интерфейсы и форматы данных могут быть частью требований. `docs/adrs/` содержит долговременные ADR; значимые для будущих задач технические решения не остаются только в материалах задачи.

Каталог задачи содержит `task.yaml` и артефакты, а при завершении перемещается целиком в `.sov/archive/` согласно [SOV Tasks](specs/filesystem-tasks.md#завершение-и-архив).

Согласованные требования после публикации находятся в `docs/specs/`. Артефакт задачи `spec.md` служит проектом новых или изменяемых продуктовых требований, а не вторым независимым источником истины. Подзадачи реализации начинаются после подтверждённой публикации исходной верхнеуровневой спецификации в удалённом `main` и опираются на опубликованные требования. Небольшое уточнение ожидаемого поведения в пределах поручения проходит `sov-spec` и `sov-review-spec` до его реализации и может публиковаться вместе с реализацией в одной задаче; до подтверждения публикации другие задачи не опираются на уточнение как на опубликованное требование. Существенное изменение оформляется отдельной связанной задачей с публикацией требований до зависящей от него реализации. Затронутые задачи после публикации изменений требований сверяют свои входы и при необходимости пересматривают результаты шагов. В спецификациях не ведётся отдельный статус реализации фичи: публикация требований не означает, что они уже реализованы; состояние выполнения отражается в задачах.

Ожидаемое поведение однозначного бага, не меняющее опубликованных требований, фиксируется в `task.md` для данного исправления и не становится автоматически новой опубликованной продуктовой спецификацией. Если существующие опубликованные требования противоречат ожидаемому исправлению, их изменение сначала проходит согласование и независимое ревью.

### Локальное хранилище и рабочие копии

Пути `.sov/...` относятся к локальному хранилищу задач, артефактам и рабочим копиям; они отсчитываются от основной папки проекта. Каталог `.sov/` исключается из Git основной рабочей копии. Публикация проекта не означает сохранения локальных задач и артефактов в удалённом репозитории.

Worktree — отдельная рабочая копия репозитория для задачи. Изменения её кода, `docs/` и `rules/` учитываются веткой задачи обычным образом, несмотря на расположение рабочей копии внутри локального хранилища.
Если для задачи создавалась worktree, после её завершения она удаляется через `sov-git`, только после подтверждения сохранности результатов.

Хранилище задач и артефакты не копируются в каждую worktree как независимые данные. Оркестратор явно передаёт идентификатор задачи, пути к её рабочей копии и локальной папке артефактов. Путь к `.sov/` всегда относится к основной папке проекта.

Код, `docs/` и `rules/` для конкретного изменения читаются из worktree задачи; состояние задач получают через `sov-tasks`, а артефакты — из локальной папки задачи.

### Граница учёта задач и артефактов

В действующем протоколе `sov-tasks` создаёт и выбирает карточки и выполняет захват, освобождение и завершение через `sov-task` согласно [SOV Tasks](specs/filesystem-tasks.md#интерфейс-скила-и-возможной-cli). CLI не участвует в записи кода и документов проекта; локальные артефакты находятся в каталоге задачи, который при завершении переходит в архив.

Артефакты `task.md`, `spec.md`, `plan.md` и другие читают и изменяют ответственные за них агенты как локальные файлы. Рабочие копии Git остаются в ведении `sov-git`.

Отложенная задача: определить сохранение и перенос `.sov/` между машинами и восстановление состояния задач после потери локального каталога. Пока продолжение работы опирается на сохранность `.sov/` на той же локальной установке; способ резервного копирования и восстановления будет определён отдельно.

### Файлы самого SOV

Скилы и шаблоны относятся к установленному набору SOV, а не к спецификациям целевого проекта. В исходном проекте SOV инструкции и специализированные шаблоны артефактов находятся в `skills/<имя скила>/`, общие для нескольких скилов `checks.md` и `review.md` — в `templates/`. Шаблон проектного `AGENTS.md`, команды и агенты OpenCode для установки находятся в `templates/` и `templates/opencode/` соответственно; исходники команд не активируют их в репозитории SOV. Команды устанавливаются в целевом проекте из того же закреплённого выпуска, что скилы и агенты. Проектные правила и продуктовые спецификации живут в целевом проекте, а не в скилах SOV.

При инициализации фиксируется расположение ресурсов SOV. Они должны быть доступны агентам из основной рабочей копии и worktree задач. Подключение к конкретной среде не меняет универсальные правила SOV.

## 8. Артефакты задачи

Артефакты незавершённой задачи находятся в `.sov/tasks/<id>-<короткое-имя>/`, а после завершения — в `.sov/archive/<id>-<короткое-имя>/` по [SOV Tasks](specs/filesystem-tasks.md#хранилище-и-идентичность); их читают и изменяют ответственные агенты. Состав обязательных результатов определяется выбранными шагами; все перечисленные файлы не создаются автоматически для каждой задачи. Исторический путь прежних выпусков был `.sov/tasks/<task-id>/` с отдельной записью в общем списке.

| Артефакт      | Назначение                                                                                                                                                                                                                                                                    |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `task.md`     | Исходный запрос, ожидаемый результат, границы поручения, критерии приёмки, ссылки на требования и правила, уточнения и ответы человека; выбранный маршрут, состояние шагов, сведения для продолжения, remote, целевая ветка, итоговый коммит и подтверждение его публикации. Ведёт оркестратор. |
| `spec.md`     | Проект продуктовой спецификации: ожидаемое поведение, сценарии, ограничения и критерии приёмки, без технического плана реализации. Готовит `sov-spec`; согласованное содержание публикуется в `docs/specs/`.                                                                  |
| `adr.md`      | Существенный технический выбор при обсуждении фичи: альтернативы, причины выбора и отклонения. Готовит `sov-spec` при необходимости; долговременное решение публикуется в `docs/adrs/`.                                                                                       |
| `research.md` | Для бага: воспроизведение, ожидаемое и фактическое поведение, свидетельства, гипотезы, установленная причина либо препятствие и предложенное решение. Готовит `sov-research`; может быть конечным результатом исследования без исправления.                     |
| `plan.md`     | Техническая спецификация конкретной задачи: затрагиваемые части системы и их изменение, порядок реализации, тесты и проверки, риски. Готовит `sov-plan`; для разработки должен содержать достаточно сведений, чтобы приступить к реализации.                                  |
| `checks.md`   | Фактически выполненные проверки, их результаты и состояние изменений, к которому они относятся. Записывает выполнявший проверки агент.                                                                                                                                        |
| `review.md`   | Замечания, их важность, основания, состояние устранения и итоги независимых ревью и промежуточных проверок с указанием проверяемого шага. Записывают ответственные проверяющие. |

Результаты уточнения потребности и явно запрошенной декомпозиции могут сохраняться в `task.md`; отдельный файл для декомпозиции не обязателен. Для исследования без исправления не требуются `plan.md` и `checks.md`, если проверки кода не выполнялись; вывод об установленной причине предъявляется человеку вместе со свидетельствами и предложением независимой перепроверки. Для разработки в обычном маршруте необходим пригодный технический план; в быстром маршруте при его пропуске техническое решение и проверки кратко фиксируются в `task.md`. Для обоих маршрутов нужны подтверждённые успешные результаты обязательных проверок; если их нельзя добиться, задача останавливается с зафиксированным препятствием, а не признаётся выполненной. Новые документы не создаются ради заполнения списка.

Оркестратор ведёт состояние процесса и фиксирует принятие результатов. Изменения `docs/` и применимых `rules/` готовит `sov-spec` при подготовке требований либо `sov-implement` при актуализации после разработки; в быстром маршруте без формального шага их может готовить основной агент. При назначенном ревью проверяющий проверяет их вместе с остальным результатом.

Важные долговременные сведения не должны оставаться только в локальных артефактах. Требования включаются в `docs/specs/`, а архитектурные ограничения, обязательные для последующей работы, — в `rules/` вместе с обоснованием; ADR публикуется в `docs/adrs/`.

## 9. Проверки и ревью

Проверяется объём, относящийся к текущей задаче, а не готовность всей фичи или проекта. Условия приёмки определяются требованиями задачи и правилами проекта.

В результатах проверок различаются успешное выполнение, ошибка и отсутствие запуска. Невозможность выполнить обязательную проверку фиксируется как препятствие, а не как успешный результат. После существенных изменений повторяются затронутые проверки. Успешные hook при фактическом push и CI для того же проверенного состояния кода и условий учитываются как свидетельства соответствующих проверок без повторного ручного запуска: фиксируются диапазон/commit, результат и источник. Проверка не распространяется на незакоммиченные файлы, новую базу, изменённую конфигурацию или команды, которых она не запускала. Для документации нужны применимые проверки содержания, ссылок и оформления, а не игровые тесты; изменение hook проверяется действительным push, включая отказ при ошибке, если меняется блокировка push, в изолированный remote при необходимости. Обязательность проверок определяется правилами проекта; противоречие с требованием повторного ручного запуска требует согласования с владельцем проекта, а не молчаливого обхода.

Если ревью обязательно или назначено, `sov-review-spec` и `sov-review-implementation` выполняют отдельные субагенты, не участвовавшие в подготовке проверяемого результата. Проверяющий самостоятельно оценивает основания и относящиеся к предмету ревью фактические результаты проверок, формирует замечания и проверяет их устранение, но не исправляет проверяемые изменения. Если независимый субагент недоступен, оркестратор сообщает о препятствии и не считает обязательное ревью выполненным. Пропуск итогового ревью допускается только на условиях явного быстрого маршрута либо после отдельного согласования с человеком в обычном маршруте, если правила проекта не требуют его безусловно; для разработки основного кода игры или движка ревью обязательно. Известные блокирующие замечания остаются обязательными к устранению и подтверждению проверяющим.

При приёмке результата каждого шага оркестратор проверяет пригодность входов и результатов. До реализации исправления дополнительная независимая проверка исследования ошибки или технического плана назначается по запросу человека, требованию правил проекта либо если ошибка на этом этапе повлечёт существенную переделку: для исследования — при конкурирующих объяснениях причины или неполном воспроизведении, для плана — при миграции данных, изменении публичных интерфейсов, труднообратимых действиях или нетривиальных зависимостях между несколькими компонентами. Оркестратор фиксирует основание решения о проверке или её пропуске в `task.md`. Это короткая адресная проверка по инструкции ответственного скила (`sov-research` для исследования, `sov-plan` для плана), а не отдельный обязательный скил-шаг; проверяющий получает свидетельства и конкретные вопросы, работает независимо и записывает вывод и замечания в `review.md` до перехода к следующему шагу. Нехватка свидетельств не превращается в подтверждённую причину по итогам ревью: исследование продолжается либо фиксируется препятствие.

После исследования ошибки без исправления оркестратор показывает человеку отчёт с выводом, свидетельствами и ограничениями исследования и предлагает независимую перепроверку как опцию. Если человек выбирает перепроверку, её результат рассматривается до завершения задачи; без запроса она не обязательна, если иного не требуют правила проекта. При недостатке свидетельств вывод обозначается как гипотеза, а не как установленная причина. Блокирующие замечания к результатам проведённой промежуточной или итоговой проверки устраняются до перехода дальше; независимая проверка не заменяет обязательное ревью спецификации или реализации.

Используются три уровня важности:

| Уровень | Значение |
|---|---|
| Критичный | Серьёзная ошибка, неприемлемый риск или нарушение ключевых требований. Блокирует принятие результата и публикацию. |
| Средний | Конкретный дефект или невыполненное обязательное требование. Также блокирует принятие результата и публикацию. |
| Низкий | Рекомендация или необязательное улучшение, которое не препятствует приёмке задачи. |

Каждое замечание содержит место проблемы, основание и ожидаемый результат исправления. Личное предпочтение проверяющего не становится блокирующим требованием, если не опирается на согласованные требования или правила.

Оркестратор возвращает задачу на шаг, ответственный за проблему: ошибки кода, тестов и актуализации документации — в `sov-implement`, ошибки диагностики — в `sov-research`, технического решения — в `sov-plan`, продуктовых требований и решений при обсуждении фичи — в `sov-spec`.

После исправления выполняются необходимые зависимые шаги и повторное ревью. Критичные и средние замечания должны быть устранены либо обоснованно сняты проверяющим. Низкие замечания исправляются в текущей задаче или сохраняются как явно отложенные рекомендации.

Исправления, найденные до первой публикации задачи в удалённом `main` и остающиеся в исходных границах результата, выполняются в той же задаче с повтором затронутых проверок и, если ревью проводилось, адресной проверкой устранения. Новая задача нужна для существенно иного результата либо изменения, обнаруженного после публикации; локальный коммит сам по себе не завершает цикл задачи.

## 10. Публикация и завершение

Задача считается завершённой, когда достигнут результат поручения, выполнены обязательные проверки и отсутствуют нерешённые блокирующие замечания. Для задачи с публикацией требуется подтверждённое включение итогового коммита в удалённый `main` после прямого push и лишь затем завершение через `sov-tasks`: `sov-task complete` создаёт marker и переносит каталог задачи в архив по [SOV Tasks](specs/filesystem-tasks.md#завершение-и-архив).

Для задач, ограниченных обсуждением, исследованием или подготовкой локальных материалов, публикация не является обязательной сама по себе. Завершение подготовки требований не означает завершения их реализации.

Непубликуемый разговор и временный эксперимент вне файлов целевого репозитория могут завершиться без задачи и публикации. Если изменяются файлы проекта, это сохраняемая работа: учитывать её в задаче и соблюдать правила рабочей копии и публикации проекта; временные изменения, которые решено не сохранять, не включать в итоговый push и проверять их удаление без потери чужой работы. Быстрый режим не отменяет требования к проверкам и прямой публикации.

Порядок публикации учитывает правила проекта: remote, обязательные проверки до и после push и необходимые решения человека. Целевая ветка маршрута SOV — `main`; если проект не разрешает прямой push в неё или требует PR, сначала согласуй изменение проектных правил и защиты ветки, не обходи их.

Публикация изменений проходит прямым нефорсированным push проверенного коммита из ветки задачи в удалённый `main`, без PR и без переключения основной рабочей копии. Локальный коммит или push только ветки задачи не завершают публикуемую задачу. После push заново прочитай удалённый `main` и подтверди, что итоговый коммит включён в его историю и ожидаемый результат присутствует; если удалённый репозиторий недоступен или push отклонён, задачу не завершай.

Перед push проверяются состав всех коммитов относительно актуального удалённого `main`, отсутствие случайно включённых служебных данных и совместимость с ним. Ветка задачи должна включать актуальный `main` без посторонних коммитов; при его продвижении сначала обнови ветку задачи без потери чужих изменений и повтори затронутые проверки и обязательное либо назначенное независимое ревью; при пропущенном ревью пересмотри оценку риска. Обычный push без `--force` отклонит гонку с новым коммитом в `main`: повтори сверку и проверки, не переписывай чужую историю. Отсутствие текстовых конфликтов не заменяет проверку согласованности изменений. Если обязательные проверки выполняются только после push в `main`, дождись их результата перед `done`; при провале сохрани задачу открытой и исправь результат, повторив затронутые проверки.

Перед публикацией новых или изменённых продуктовых требований, после необходимых проверок, оркестратор показывает человеку отчёт с результирующей спецификацией или ссылкой на её полный текст. Отчёт отражает договорённости диалога и закрытые вопросы; при указании человеком расхождений оркестратор уточняет требования и повторяет затронутые шаги. Сам отчёт не требует отдельного формального подтверждения, если правила проекта его не устанавливают.

Оркестратор через `sov-git` проверяет предусмотренные правилами условия и доводит публикацию до подтверждённого включения итогового коммита в удалённый `main`. Он сохраняет remote, целевую ветку, SHA итогового коммита и свидетельство публикации в локальном `task.md`, затем через `sov-tasks` завершает задачу. Если публикация либо обязательные проверки после push ещё не подтверждены, задача остаётся незавершённой с зафиксированной в артефактах причиной ожидания или препятствием; отдельного статуса препятствия в действующем протоколе нет.

При прерывании публикации сначала проверяется фактическое состояние репозитория, после чего выполняются только незавершённые действия. Уже опубликованные изменения не публикуются повторно из-за отсутствующей записи в системе задач.

Worktree удаляется только после подтверждения сохранности результатов и согласно правилам проекта. Ошибка публикации не является основанием для удаления рабочей копии или отметки задачи как выполненной.

## 11. Продолжение работы и взаимодействие с человеком

### Автономность и остановки

Оркестратор самостоятельно выполняет доступные шаги до достижения результата либо появления препятствия, которое невозможно безопасно устранить в пределах его полномочий.

Основания для остановки включают необходимость решения человека, отсутствие доступа или обязательного инструмента, внешнюю блокировку, противоречие требований, ограничение текущей сессии либо повторяющиеся неудачные попытки без существенного продвижения.

При остановке сохраняются выполненные шаги, актуальные артефакты, оставшиеся действия, причина препятствия и сведения для продолжения. Нельзя представлять частичный результат как завершённую задачу.

При продолжении, в том числе из новой сессии, оркестратор получает задачу через `sov-tasks`, читает сохранённое состояние, сверяет его с файлами, репозиторием и удалённым `main`, проверяет актуальность входов и продолжает с первого необходимого незавершённого либо потерявшего актуальность шага. Если запись, общие артефакты или рабочая копия отсутствуют либо противоречат друг другу, он сначала выясняет фактическое состояние, не начинает новую задачу вместо прежней молча и не считает восстановление завершённым. Контекст переписки помогает работе, но не заменяет сохранённые материалы задачи.

### Вопросы и отчёты

Общение с человеком ведётся простым и понятным языком, с необходимым контекстом, без лишнего жаргона и сокращений. Технические идентификаторы, названия файлов, API и команды сохраняют точное написание.

Вопросы задаются по одному. По возможности предлагаются варианты ответа с номерами и сохраняется возможность собственного ответа. В OpenCode для этого предпочтительно использовать доступный встроенный инструмент вопросов. Уже зафиксированные ответы повторно не запрашиваются, если не появились новые противоречащие сведения.

Итоговый отчёт сообщает, какое поручение выполнялось, какой результат получен, что изменилось для пользователя программы, какие проверки выполнены, завершена ли публикация и какие ограничения остались.

Для подготовки требований прямо указывается, что созданы спецификация и задачи, но поведение программы пока не изменилось. При остановке вместо завершения указываются препятствие и точка продолжения.

Если дальнейшая работа нужна, отчёт содержит один конкретный следующий шаг: действие человека либо способ продолжить текущую или следующую доступную задачу. Пример команды приводится только в соответствии с фактически настроенным интерфейсом SOV.

## 12. Инициализация и обновление

Установку SOV в проект выполняет агент по [инструкции файловых задач](install-filesystem-tasks.md). Рекомендуется закреплённый внешний выпуск скилов, шаблонов, команд среды и собранной Go CLI одной совместимой версии; проект хранит свои `AGENTS.md`, `rules/`, `docs/` и исключённую из Git `.sov/`. Агент явно записывает версию ресурсов, абсолютные пути и источник задач, подключает необходимые ресурсы и проверяет отсутствие конфликтов имён с установленными командами и скилами. Для OpenCode установка создаёт в проекте два настраиваемых субагента уровней `standard` и `advanced`, по умолчанию сопоставленных `openai/gpt-6-luna` и `openai/gpt-6-sol`. Проект может менять конкретные модели в их конфигурации без изменения скилов; установка проверяет фактическую доступность обеих моделей и разрешения из основной копии и worktree после перезапуска. Существующие `build`, `plan`, их модели и `default_agent` не заменяются. Глобальные команды являются тонким входом только для подключённых проектов: их видимость не подтверждает подключение. Если глобальный способ недоступен, допускается установка проектных команд с доступом из worktree. Для других сред применяется принцип закрепления версии и доступности ресурсов, без предположения о конкретном механизме обнаружения. Настройка источника учётных данных задач относится к `sov-tasks`: для действующих файловых задач используется бинарник `sov-task` из закреплённого выпуска. Наличие CLI само по себе не переключает ранее подключённый проект; при отсутствии подключения агент сообщает о препятствии и не меняет источник либо способ записи молча.

Инициализация проверяет доступность необходимых инструментов и разрешений, включая доступ из worktree к общему хранилищу и ресурсам SOV. Первое подключение действующего протокола создаёт каталоги `tasks/`, `claims/`, `completed/`, `archive/` в основной `.sov/` только при отсутствии прежнего состояния; переход существующего проекта требует отдельного решения, сверки задач и остановки старых писателей по [инструкции](install-filesystem-tasks.md). Проверка из worktree проводится на копии, содержащей устанавливаемые команды и конфигурацию, либо как явно обозначенная предварительная проверка тех же файлов; ветка без новых проектных файлов не подтверждает их работу. Принятый проектом профиль OKF фиксируется явно в правилах проекта.

**Историческая инициализация прежнего файлового списка:** при первом подключении создавались оба файла состояния и постоянный mutex при остановленных писателях; обновление проекта без архива требовало отдельного проверенного переключения без замены ROADMAP и без автоматического переноса задач. Устойчивый идентификатор исполнителя, не привязанный к сессии OpenCode, фиксировался в правилах проекта; прежние назначения по ID сессий не заменялись автоматически и требовали явного решения при переносе.

Повторная инициализация и обновление сохраняют пользовательские изменения. Существующие правила и документы не перезаписываются молча; при конфликте требуется согласованное решение.

Обновление SOV не должно незаметно менять маршрут или смысл шагов уже выполняемой задачи. При изменении инструкций оркестратор проверяет влияние на незавершённые задачи, их артефакты и условия выполнения и фиксирует необходимые изменения до продолжения работы. Выпуск не заменяется на месте в активных сессиях; переключение инструкций и общего бинарника выполняется в согласованном окне остановки писателей всех затронутых проектов.
