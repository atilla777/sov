# SOV — спецификация принципов работы

## 1. Назначение

SOV — набор взаимосвязанных скилов (Agent Skills) и шаблонов артефактов для организации разработки с помощью агентов в средах типа OpenCode.

SOV задаёт порядок подготовки продуктовой спецификации, планирования технической реализации, разработки, независимой проверки и публикации изменений. Скилы универсальны: особенности конкретного проекта определяются его документацией и правилами.

SOV не содержит собственного программного движка выполнения задач или сервера. Скилы являются инструкциями, которые читает и выполняет агент. Для работы используются инструменты среды и доступные внешние утилиты, например Git и GitHub CLI. В составе SOV может поставляться вспомогательная локальная CLI `sov-state` для байтового чтения и условной атомарной записи существующего файлового списка задач. Она не выбирает задачи, не проверяет их смысл и не заменяет `sov-tasks`; наличие исходников или бинарника не означает, что CLI установлена и подключена в целевом проекте.

Оркестратором является основной агент, работающий по инструкциям скила `sov-orchestrator`. Он определяет необходимые шаги, управляет их выполнением, передаёт контекст исполнителям и проверяет результаты.

SOV устанавливает обязательные правила работы агентов, но сам по себе не обеспечивает программную невозможность их нарушения. Ограничения доступа и опасных действий задаются средствами среды запуска и правилами проекта.

## 2. Постановка задачи и границы поручения

### Единая точка входа

Пользователь описывает желаемый результат обычным языком либо указывает существующую задачу. Выбирать тип задачи и последовательность шагов не требуется. Обязательного поля «тип задачи» в SOV нет.

Для OpenCode при установке SOV предусматриваются пользовательские команды `/sov`, `/sov-feature` и `/sov-bug`, передающие запрос одному и тому же оркестратору. `/sov` — универсальный вход; две другие команды подсказывают предмет обращения, но не предписывают выполнить работу за пределами запроса. Это команды среды, а не отдельные консольные программы SOV и не скилы шагов.

Примеры обращений:

```text
/sov-feature Обсудим систему сохранения игры и подготовим продуктовую спецификацию.
/sov-feature Подготовь спецификацию системы сохранения и задачи для реализации.
/sov-bug Найди причину пропажи предметов после загрузки.
/sov-bug Исправь пропажу предметов после загрузки.
/sov Выполни задачу №42.
/sov Продолжай текущую задачу.
/sov
```

Если задача явно указана, оркестратор работает с ней после проверки её состояния и условий начала работы. Указание номера не отменяет зависимости задачи и не позволяет забирать её у другого исполнителя.

Если аргументов нет или запрошено продолжение без ID, оркестратор через `sov-tasks` сначала ищет незавершённые задачи, назначенные устойчивому исполнителю, указанному в правилах проекта. Это работает и в новой сессии после перезагрузки, без памяти предыдущего диалога. При единственной задаче `in_progress` он сверяет сохранённое и фактическое состояние и продолжает её; при единственной `blocked` сообщает препятствие и условие возобновления, не переключаясь на другую. Если таких задач несколько, запрашивает ID и ничего не выбирает автоматически. Только если незавершённых задач данного исполнителя нет, он выбирает первую доступную `planned` задачу. Новый запрос без ID рассматривается как отдельное поручение, а не как команда продолжить прежнюю задачу. При неизвестном исполнителе или недоступном источнике задач не угадывает прежнюю задачу и не создаёт вместо неё новую очередь.

Команда `/sov-feature` помогает начать обсуждение фичи, а `/sov-bug` — исследование либо исправление ошибки. Если запрос к этим командам ограничен обсуждением или поиском причины, оркестратор не переходит к реализации без соответствующего поручения.

### Определение результата

До начала существенной работы оркестратор определяет ожидаемый результат и границы поручения, учитывая запрос, предыдущие договорённости, состояние задачи и правила проекта. Он кратко сообщает человеку своё понимание предстоящей работы.

Оркестратор самостоятельно выбирает способ достижения результата, но не расширяет само поручение. Обсуждение фичи не означает разрешения реализовать её. Просьба выяснить причину ошибки не означает поручения исправить её. Подготовка спецификации не означает, что описанная возможность должна быть реализована в той же задаче.

Подтверждать каждое действие не требуется. Вопрос задаётся, если существенная неоднозначность меняет ожидаемый результат, объём работы или допустимые действия и не разрешается имеющимися сведениями.

Обсуждение может завершаться ответом без создания задачи, worktree или изменения файлов. Если поручение предполагает сохраняемую работу над проектом, оркестратор создаёт либо использует существующую задачу.

По умолчанию один запуск выполняет одно поручение или одну выбранную задачу. Подготовка спецификации фичи может создавать задачи разработки, но не запускает их автоматически. После завершения оркестратор сообщает следующую доступную задачу, но не начинает её без указания пользователя; следующую задачу рекомендуется вести в новой сессии.

## 3. Выбор последовательности шагов

### Принцип выбора

Оркестратор выбирает последовательность шагов на основании цели и границ поручения, состояния задачи, доступных артефактов и применимых правил проекта.

Он использует типовой маршрут как основу и при необходимости адаптирует его по установленным правилам. Команда помогает понять намерение пользователя, но не заменяет определения результата и границ поручения.

Типовые маршруты:

| Поручение | Последовательность скилов-шагов |
|---|---|
| Обсуждение фичи, подготовка продуктовой спецификации и задач разработки | `sov-spec → sov-review-spec → публикация требований`; задачи разработки становятся доступными после слияния PR с требованиями. Простое обсуждение может завершиться ответом без формальных шагов. |
| Разработка подготовленной задачи | `sov-plan → sov-implement → sov-review-implementation`. |
| Исследование ошибки без исправления | `sov-research` (диагностика причины и предложение решения); после исследования человек получает отчёт и может запросить независимую перепроверку вывода по инструкции `sov-research`. |
| Исправление ошибки | `sov-research → sov-plan → sov-implement → sov-review-implementation`. |

После необходимых шагов оркестратор публикует результат через GitHub, если поручение предполагает публикацию. Подготовленная для разработки продуктовая спецификация публикуется до начала зависимых задач. Публикация и обновление статуса задачи — завершающие действия оркестратора, а не дополнительные скилы-шаги. Исследование без исправления не переходит к реализации, а обсуждение вариантов не требует публикации.

Шаг можно не выполнять повторно, если необходимый результат уже существует и проверен на пригодность. Для разработки новой функциональности нужны опубликованные согласованные требования в `docs/specs/` целевой ветки либо в применимых опубликованных источниках проекта; отдельный локальный `spec.md` не обязателен. Однозначный баг можно исправлять без предварительной публикации отдельной продуктовой спецификации, если ожидаемое поведение зафиксировано в задаче, подтверждается исследованием и не противоречит опубликованным требованиям. До `sov-plan` нужны определённое ожидаемое поведение и, для исправления, пригодный результат `sov-research`; пригодный `plan.md` требуется только перед `sov-implement`. Технический план не подменяет продуктовые требования.

### Уточнение маршрута

Типовые маршруты задаются этой спецификацией. Применимость шагов, выбранная последовательность, состояние работы и результаты проверки существующих артефактов сохраняются в локальных материалах задачи. Инструкции выполнения находятся в скилах и применимых правилах проекта.

При появлении новых требований, результатов исследования или замечаний оркестратор пересматривает маршрут и фиксирует причину изменения. Изменение маршрута не может использоваться для обхода обязательных проверок или неустранённых замечаний.

Если ожидаемое поведение при исправлении неясно, противоречит опубликованным требованиям или требуется его изменить, оркестратор возвращается к `sov-spec` и обеспечивает согласование требований и `sov-review-spec` до реализации. Существенное изменение цели или объёма оформляется отдельной связанной задачей; небольшое уточнение может оставаться в текущей задаче, если входит в поручение. Сам по себе большой объём технических изменений не требует повторного обсуждения продуктовых требований, когда ожидаемое поведение уже определено.

## 4. Состав SOV

### Оркестратор

**`sov-orchestrator`** — управление выполнением поручения. Определяет задачу и результат, выбирает маршрут, проверяет условия шагов, привлекает субагентов, принимает результаты, управляет возвратами, публикацией и состоянием задачи, формирует итоговый отчёт.

### Скилы шагов

| Скил            | Ответственность                                                                                                                                                                                                                                                       |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sov-spec`      | Обсуждение фичи, уточнение потребности и сценариев; подготовка продуктовой спецификации без деталей реализации, при необходимости ADR с выбранными и отклонёнными техническими решениями и предложений по декомпозиции. Включение согласованных требований в `docs/specs/`. |
| `sov-research`  | Для бага — воспроизведение, исследование причины, свидетельства и предложение решения; если причину установить не удалось, фиксируется препятствие либо обоснованная гипотеза без объявления её установленной причиной. |
| `sov-plan`      | Техническая спецификация и план реализации задачи разработки или исправления ошибки, включая проверки и риски; при исправлении использует результат `sov-research`, не проводя диагностику вместо него. |
| `sov-implement` | Изменение кода и тестов по требованиям и техническому плану, запуск и исправление тестов до успешного прохождения обязательных проверок, сохранение их результатов, актуализация затронутых спецификаций и правил в пределах согласованного поведения.                |
| `sov-review-spec` | Независимая проверка продуктовой спецификации перед публикацией: ясность и согласованность поведения, сценарии, ограничения, критерии приёмки, покрытие требований задачами разработки; замечания и проверка их устранения. |
| `sov-review-implementation` | Независимая проверка результата реализации перед публикацией: код, тесты, результаты проверок и затронутая документация в сопоставлении с требованиями, границами задачи и техническим планом; замечания и проверка их устранения. Качество самого плана не оценивается повторно на этом шаге: при обнаружении ошибки плана оркестратор возвращает задачу к `sov-plan`. |

`sov-spec` определяет ожидаемое поведение в диалоге с человеком: уточняет потребность и варианты поведения, задаёт вопросы, фиксирует ответы и закрывает существенные открытые вопросы. Когда все вопросы, влияющие на требования, закрыты, итоговая спецификация считается согласованной в рамках поручения; отдельное формальное подтверждение не требуется, если его не требуют правила проекта. Перед публикацией оркестратор показывает человеку отчёт с результирующей спецификацией или точной ссылкой на её полный текст и даёт возможность указать на расхождения с договорённостями. Если обнаружено расхождение, требования уточняются и необходимые шаги проверки повторяются до публикации. ADR фиксирует существенный технический выбор и обоснование, но не превращает продуктовую спецификацию в технический план. `sov-research` исследует причину ошибки; `sov-plan` определяет способ выполнения конкретной задачи. `sov-implement` не меняет согласованные требования только для того, чтобы они соответствовали написанному коду: при расхождении исправляется реализация либо отдельно согласуется изменение требований через `sov-spec`.

Уточнение потребности, оформление документации и публикация не требуют отдельных скилов-шагов: они выполняются в рамках ответственного шага либо оркестратором. Диагностика ошибки — отдельный шаг `sov-research`. Наличие отдельного артефакта само по себе не подразумевает отдельный скил.

### Вспомогательные скилы

| Скил | Ответственность |
|---|---|
| `sov-tasks` | Создание и выбор задач, выдача идентификаторов, ведение порядка, статусов, зависимостей и назначений, проверка согласованности списка задач. Скрывает способ хранения учётных данных задач. |
| `sov-git` | Операции с репозиторием, ветками, worktree и GitHub через доступные инструменты согласно правилам проекта. |
| `sov-okf` | Оформление документации и правил по принятому в проекте профилю Open Knowledge Format (OKF): структура, метаданные, индексы и ссылки. |

`sov-tasks` управляет учётными данными задач, `sov-git` — веткой, рабочей копией и публикацией в GitHub. Предложения по декомпозиции формируются в ходе `sov-spec`, а создание и изменение записей задач выполняется через `sov-tasks`. Для выбранного файлового источника он использует проверенную CLI `sov-state` из той же установленной версии SOV: читает bytes и revision, проверяет смысл операции и условно публикует целый новый файл; CLI не принимает смысловых решений. Артефакты в локальной папке задачи ведут ответственные скилы шагов; оркестратор ведёт `task.md`. Остальные скилы не читают и не изменяют хранилище списка задач напрямую. Вспомогательные скилы не являются шагами каждого маршрута.

`sov-okf` определяет оформление документов, но не содержание требований и не продуктовые решения. Формат документов OKF не подменяет формат скилов.

## 5. Правила выполнения шагов

### Входы, действия и результаты

Скил шага определяет универсальные входы, границы действий, ожидаемый результат, условия завершения и основания для возврата либо остановки. Проектные особенности выполнения он берёт из `rules/`, а ожидаемое поведение — из `docs/` и поручения. Скил не закрепляет язык, инструменты сборки, конкретные тестовые команды или формат проектной спецификации.

Шаг может выполняться только при наличии пригодных обязательных входов. Артефакт пригоден, если относится к нужной задаче, содержит необходимые сведения, соответствует актуальным требованиям и состоянию изменений и не содержит открытых вопросов, препятствующих этому шагу.

Пустой шаблон, устаревший документ или неподтверждённое утверждение о проверке не считаются достаточным входом. Артефактами могут быть не только Markdown-файлы, но также изменения кода, тесты и результаты выполнения инструментов.

После изменения входов оркестратор пересматривает пригодность зависимых результатов. Повторяются только необходимые шаги: исправление опечатки не равнозначно изменению требований или технического решения.

### Работа с субагентами

Оркестратор работает в текущем основном агенте среды (например, `build` или `plan` в OpenCode) на выбранной пользователем модели. Команды `/sov*` не переключают модель или режим. Для шагов установлены уровни возможностей `standard` и `advanced`, сопоставляемые конкретным моделям **при подключении SOV в целевом проекте**, а не внутри скилов:

| Работа | Уровень по умолчанию |
|---|---|
| `sov-spec`, `sov-research`, `sov-implement` | `advanced` |
| `sov-plan` | `standard` |
| `sov-review-spec`, `sov-review-implementation` | `advanced` |

Вспомогательные `sov-tasks`, `sov-git` и `sov-okf` вызываются ответственным агентом и не требуют собственной модели. Для плана с миграцией данных, изменением публичного интерфейса, труднообратимыми действиями или сложными межкомпонентными зависимостями оркестратор повышает `sov-plan` до `advanced` с записью причины. Адресная перепроверка исследования использует `advanced`; перепроверка плана — уровень проверяемого плана (при высоком риске `advanced`). Снижение установленного уровня шага не производится молча: изменение политики проекта требует явного согласования, а изменение модели, соответствующей уровню, — настройки проекта.

Шаги выполняются отдельными субагентами выбранного уровня; простое обсуждение, не требующее формального шага, может вести основной агент. `sov-review-spec` и `sov-review-implementation` выполняются независимыми субагентами, не участвовавшими в подготовке проверяемого результата; одинаковый уровень или тип субагента не означает повторное использование автора. Оркестратор поручает субагенту выполнить шаг с использованием соответствующего скила. При отсутствии настроенной или доступной модели либо необходимого субагента он сообщает о препятствии, не подменяет модель наследованием основного агента и не выдаёт шаг за выполненный. Ограничения основного режима среды сохраняются: из режима без разрешения на запись оркестратор не запускает пишущий шаг под видом субагента, а сообщает о необходимости перейти в режим разработки.

Поручение содержит идентификатор задачи и шаг, выбранный уровень, ожидаемый результат, нужный скил, путь к рабочей копии кода и к локальной папке артефактов задачи, применимые требования и правила либо точные ссылки на них, а также границы допустимых изменений. Оркестратор фиксирует в `task.md` реально выбранный уровень и модель исполнителя, основание повышения и сверяет их при продолжении работы. Субагент читает и сохраняет артефакты своего шага в переданной папке; нельзя предполагать, что он автоматически располагает всем контекстом основного агента.

Субагент возвращает сведения о выполненной работе, созданных и изменённых артефактах, фактических проверках, оставшихся проблемах и вопросах. Основной диалог с человеком ведёт оркестратор; вопросы субагентов передаются через него.

Оркестратор принимает результат после проверки артефактов и условий завершения, а не только на основании сообщения исполнителя «готово».

## 6. Задачи, план и параллельная работа

`sov-tasks` предоставляет перечень задач с идентификаторами, краткими названиями, общими статусами, зависимостями, назначениями и порядком выполнения. Оркестратор выбирает доступную задачу через него, не разбирая файлы или ответы сервера самостоятельно.

Статусы задач:

| Статус | Значение |
|---|---|
| `planned` | Задача запланирована, но ещё не выполняется. |
| `in_progress` | Задача назначена исполнителю и выполняется. |
| `blocked` | Продолжение невозможно до устранения указанного препятствия. |
| `done` | Ожидаемый результат достигнут, обязательные условия завершения выполнены; для публикуемой задачи PR слит. |
| `cancelled` | Задача отменена. |

Доступной для нового назначения считается первая запланированная задача, которая не назначена другому исполнителю, не имеет незавершённых блокирующих зависимостей и удовлетворяет условиям начала работы. Отменённая зависимость не считается автоматически выполненной. Исполнитель задаётся устойчивым, не зависящим от сессии идентификатором в правилах проекта; новая сессия использует его для поиска собственных `in_progress` и `blocked` задач до выбора новых. Идентификатор сессии не является единственным ключом для продолжения. При нескольких собственных незавершённых задачах нужен явный ID; чужое назначение не перехватывается.

Условия начала зависят от поручения: для новой функциональности нужны опубликованные согласованные требования; для исправления бага достаточно определённого ожидаемого поведения, а при его неоднозначности задача может начинаться с согласования требований без перехода к реализации. Результат исследования и технический план не требуются до начала задачи, которая должна их подготовить.

Если доступных задач нет, оркестратор сообщает причины и не снимает блокировки самостоятельно ради продолжения работы. Назначение задачи другому исполнителю изменяется явно; прерывание сессии само по себе не означает освобождения задачи.

Общий статус задачи предоставляется `sov-tasks`; его независимая копия в локальных артефактах не ведётся. Подробное состояние шагов и причины препятствий оркестратор сохраняет в локальных материалах задачи.

При декомпозиции в `sov-spec` перед завершением подготовки проверяется, что итоговые требования покрыты задачами, а зависимости не образуют циклов. Задачи реализации зависят от завершения задачи подготовки и публикации требований; подготовка не должна зависеть от выполнения созданных ею задач реализации. Их можно создать до публикации спецификации, но назначать и начинать только после слияния её PR и проверки актуальности требований.

Для параллельного выполнения изменений каждой задаче выделяются отдельная ветка и Git worktree через `sov-git`. Ветка задачи реализации создаётся от актуальной целевой ветки, содержащей применимые опубликованные требования; при исправлении однозначного бага без отдельной спецификации проверяется отсутствие противоречий с опубликованными источниками. При последующем изменении требований оркестратор проверяет актуальность входов ещё не завершённых зависимых задач. Файловый маршрут `sov-tasks` предписывает условную запись существующего общего списка через `sov-state`: после чтения проверяются формат и смысл операции, собирается отдельный файл, публикуемый только при совпадении revision. При конфликте проверка и сборка повторяются на новом снимке с ограничением числа попыток; при потере ответа фактический результат выясняется новым чтением. Работа начинается только после подтверждённого назначения. Однако независимое конкурентное назначение несколькими координаторами допустимо **только после** установки совместимой CLI, перевода всех писателей на единый протокол и сквозной проверки параллельного маршрута в проекте; до этого действует один координатор. Для независимых одновременных координаторов требуются разные устойчивые идентификаторы исполнителя: сессии с одним идентификатором не могут безопасно различать чужую и свою незавершённую задачу.

## 7. Структура проекта и источники истины

Структура при файловом учёте задач:

```text
project/
├── AGENTS.md
├── rules/
│   ├── index.md
│   └── *.md
├── docs/
│   ├── index.md
│   ├── specs/
│   └── adrs/
└── .sov/
    ├── ROADMAP.md
    ├── tasks/
    │   └── <task-id>/
    │       └── *.md
    └── worktree/
        └── <task-id>/
            └── ...
```

`AGENTS.md` — точка входа для агентов. Содержит обязательные общие инструкции и порядок обращения к скилам SOV, индексам, применимым правилам и спецификациям. Перед работой агент читает правила, относящиеся к выбранному шагу и затрагиваемым частям проекта; ссылка без прочтения необходимого документа недостаточна.

`rules/` — настраиваемые правила проекта: архитектура и ограничения, язык и стек, стиль, требования к продуктовой и технической спецификациям, ADR, тестам, ревью, документации и публикации. Здесь задаются применимые команды и критерии проверок, целевая ветка и порядок работы с PR. Правила находятся через `rules/index.md` и применяются ко всем затронутым шагам, а не копируются в каждый скил; документы оформляются по принятому профилю OKF.

Скилы SOV задают неизменные для проектов границы ответственности, необходимые результаты и условия перехода между шагами. Правила проекта уточняют способы выполнения и могут добавлять требования, но не отменяют границы поручения, проверку результатов, независимость ревью и подтверждение слияния PR перед закрытием публикуемой задачи. При противоречии правил и этих условий оркестратор останавливается и сообщает о конфликте, а не выбирает удобную трактовку.

`docs/specs/` — постоянные продуктовые спецификации согласованного ожидаемого поведения независимо от степени реализации. Они описывают, что должна делать фича, её сценарии и ограничения, но не дублируют внутреннее устройство кода и технический план задачи. Внешние интерфейсы и форматы данных могут быть частью требований. `docs/adrs/` содержит долговременные ADR; значимые для будущих задач технические решения не остаются только в материалах задачи.

`.sov/ROADMAP.md` — файловое хранилище списка задач, используемое `sov-tasks` через локальную CLI `sov-state`; при выборе другого подключённого CLI-источника этот файл не требуется. `.sov/tasks/<task-id>/` — отдельное локальное хранилище артефактов, доступное оркестратору и скилам шагов; оно не принадлежит `sov-tasks`.

Согласованные требования после публикации находятся в `docs/specs/`. Артефакт задачи `spec.md` служит проектом новых или изменяемых продуктовых требований, а не вторым независимым источником истины. Подзадачи реализации начинаются после слияния PR с исходной верхнеуровневой спецификацией и опираются на опубликованные требования. Небольшое уточнение ожидаемого поведения в пределах поручения проходит `sov-spec` и `sov-review-spec` до его реализации и может публиковаться в том же PR, что и реализация; до слияния этого PR другие задачи не опираются на уточнение как на опубликованное требование. Существенное изменение оформляется отдельной связанной задачей с публикацией требований до зависящей от него реализации. Затронутые задачи после слияния изменений требований сверяют свои входы и при необходимости пересматривают результаты шагов. В спецификациях не ведётся отдельный статус реализации фичи: публикация требований не означает, что они уже реализованы; состояние выполнения отражается в задачах.

Ожидаемое поведение однозначного бага, не меняющее опубликованных требований, фиксируется в `task.md` для данного исправления и не становится автоматически новой опубликованной продуктовой спецификацией. Если существующие опубликованные требования противоречат ожидаемому исправлению, их изменение сначала проходит согласование и независимое ревью.

### Локальное хранилище и рабочие копии

Пути `.sov/...` относятся к локальным артефактам, рабочим копиям и, при файловом учёте, списку задач; они отсчитываются от основной папки проекта. Каталог `.sov/` исключается из Git основной рабочей копии. Публикация проекта не означает сохранения локального списка и артефактов в удалённом репозитории.

Worktree — отдельная рабочая копия репозитория для задачи. Изменения её кода, `docs/` и `rules/` учитываются веткой задачи обычным образом, несмотря на расположение рабочей копии внутри локального хранилища.
Если для задачи создавалась worktree, после её завершения она удаляется через `sov-git`, только после подтверждения сохранности результатов.

Список задач и артефакты не копируются в каждую worktree как независимые данные. Оркестратор явно передаёт идентификатор задачи, пути к её рабочей копии и локальной папке артефактов. При файловом учёте относительный путь `.sov/ROADMAP.md` внутри worktree нельзя считать путём к общему списку задач.

Код, `docs/` и `rules/` для конкретного изменения читаются из worktree задачи; состояние списка задач получают через `sov-tasks`, а артефакты — из локальной папки задачи.

### Граница учёта задач и артефактов

`sov-tasks` предоставляет создание, получение и выбор доступных задач, назначение, изменение статуса и зависимостей. В файловом варианте он работает с существующим `.sov/ROADMAP.md` только через настроенную `sov-state read/commit`; оркестратор и скилы шагов к этому файлу напрямую не обращаются. CLI не участвует в записи кода, документов и локальных артефактов. У задачи есть стабильный идентификатор, по которому оркестратор связывает подтверждённую запись в системе задач с папкой `.sov/tasks/<task-id>/`. Эту папку создаёт оркестратор после подтверждения создания и назначения при начале сохраняемой работы, если её ещё нет; при прерывании сверяет оба состояния, не создавая дубль строки.

Артефакты `task.md`, `spec.md`, `plan.md` и другие читают и изменяют ответственные за них агенты как локальные файлы. При переходе `sov-tasks` на CLI, обращающийся к REST API приложения на Rails, учёт задач меняет источник данных, а работа с артефактами остаётся прежней. Прозрачность такого перехода требует сохранить стабильность идентификаторов задач и их соответствие локальным папкам; если изменится и место хранения артефактов, одной замены `sov-tasks` будет недостаточно. Рабочие копии Git остаются в ведении `sov-git`.

Отложенная задача: определить сохранение и перенос `.sov/` между машинами и восстановление состояния задач после потери локального каталога. Пока продолжение работы опирается на сохранность `.sov/` на той же локальной установке; способ резервного копирования и восстановления будет определён отдельно.

### Файлы самого SOV

Скилы и шаблоны относятся к установленному набору SOV, а не к спецификациям целевого проекта. В исходном проекте SOV они размещаются в `skills/` и `templates/` соответственно. Проектные правила и продуктовые спецификации живут в целевом проекте, а не в скилах SOV.

При инициализации фиксируется расположение ресурсов SOV. Они должны быть доступны агентам из основной рабочей копии и worktree задач. Подключение к конкретной среде не меняет универсальные правила SOV.

## 8. Артефакты задачи

Артефакты находятся в `.sov/tasks/<task-id>/` и читаются и изменяются непосредственно ответственными за них агентами. Состав обязательных результатов определяется выбранными шагами; все перечисленные файлы не создаются автоматически для каждой задачи. Идентификатор папки соответствует идентификатору задачи, выдаваемому `sov-tasks`.

| Артефакт      | Назначение                                                                                                                                                                                                                                                                    |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `task.md`     | Исходный запрос, ожидаемый результат, границы поручения, критерии приёмки, ссылки на требования и правила, уточнения и ответы человека; выбранный маршрут, состояние шагов, сведения для продолжения, ссылка на PR и подтверждение слияния при публикации. Ведёт оркестратор. |
| `spec.md`     | Проект продуктовой спецификации: ожидаемое поведение, сценарии, ограничения и критерии приёмки, без технического плана реализации. Готовит `sov-spec`; согласованное содержание публикуется в `docs/specs/`.                                                                  |
| `adr.md`      | Существенный технический выбор при обсуждении фичи: альтернативы, причины выбора и отклонения. Готовит `sov-spec` при необходимости; долговременное решение публикуется в `docs/adrs/`.                                                                                       |
| `research.md` | Для бага: воспроизведение, ожидаемое и фактическое поведение, свидетельства, гипотезы, установленная причина либо препятствие и предложенное решение. Готовит `sov-research`; может быть конечным результатом исследования без исправления.                     |
| `plan.md`     | Техническая спецификация конкретной задачи: затрагиваемые части системы и их изменение, порядок реализации, тесты и проверки, риски. Готовит `sov-plan`; для разработки должен содержать достаточно сведений, чтобы приступить к реализации.                                  |
| `checks.md`   | Фактически выполненные проверки, их результаты и состояние изменений, к которому они относятся. Записывает выполнявший проверки агент.                                                                                                                                        |
| `review.md`   | Замечания, их важность, основания, состояние устранения и итоги независимых ревью и промежуточных проверок с указанием проверяемого шага. Записывают ответственные проверяющие. |

Результаты уточнения потребности и предварительной декомпозиции могут сохраняться в `task.md`; отдельный файл для них не обязателен. Для исследования без исправления не требуются `plan.md` и `checks.md`, если проверки кода не выполнялись; вывод об установленной причине предъявляется человеку вместе со свидетельствами и предложением независимой перепроверки. Для разработки необходимы пригодный технический план и подтверждённые успешные результаты обязательных проверок; если их нельзя добиться, задача останавливается с зафиксированным препятствием, а не признаётся выполненной. Новые документы не создаются ради заполнения списка.

Оркестратор ведёт состояние процесса и фиксирует принятие результатов. Изменения `docs/` и применимых `rules/` готовит `sov-spec` при подготовке требований либо `sov-implement` при актуализации после разработки; соответствующий скил ревью проверяет их вместе с остальным результатом.

Важные долговременные сведения не должны оставаться только в локальных артефактах. Требования включаются в `docs/specs/`, а архитектурные ограничения, обязательные для последующей работы, — в `rules/` вместе с обоснованием; ADR публикуется в `docs/adrs/`.

## 9. Проверки и ревью

Проверяется объём, относящийся к текущей задаче, а не готовность всей фичи или проекта. Условия приёмки определяются требованиями задачи и правилами проекта.

В результатах проверок различаются успешное выполнение, ошибка и отсутствие запуска. Невозможность выполнить обязательную проверку фиксируется как препятствие, а не как успешный результат. После существенных изменений повторяются затронутые проверки.

`sov-review-spec` и `sov-review-implementation` выполняют отдельные субагенты, не участвовавшие в подготовке проверяемого результата. Проверяющий самостоятельно оценивает основания и относящиеся к предмету ревью фактические результаты проверок, формирует замечания и проверяет их устранение, но не исправляет проверяемые изменения. Если независимый субагент недоступен, оркестратор сообщает о препятствии и не считает обязательное ревью выполненным.

При приёмке результата каждого шага оркестратор проверяет пригодность входов и результатов. До реализации исправления дополнительная независимая проверка исследования ошибки или технического плана назначается по запросу человека, требованию правил проекта либо если ошибка на этом этапе повлечёт существенную переделку: для исследования — при конкурирующих объяснениях причины или неполном воспроизведении, для плана — при миграции данных, изменении публичных интерфейсов, труднообратимых действиях или нетривиальных зависимостях между несколькими компонентами. Оркестратор фиксирует основание решения о проверке или её пропуске в `task.md`. Это короткая адресная проверка по инструкции ответственного скила (`sov-research` для исследования, `sov-plan` для плана), а не отдельный обязательный скил-шаг; проверяющий получает свидетельства и конкретные вопросы, работает независимо и записывает вывод и замечания в `review.md` до перехода к следующему шагу. Нехватка свидетельств не превращается в подтверждённую причину по итогам ревью: исследование продолжается либо фиксируется препятствие.

После исследования ошибки без исправления оркестратор показывает человеку отчёт с выводом, свидетельствами и ограничениями исследования и предлагает независимую перепроверку как опцию. Если человек выбирает перепроверку, её результат рассматривается до завершения задачи; без запроса она не обязательна, если иного не требуют правила проекта. При недостатке свидетельств вывод обозначается как гипотеза, а не как установленная причина. Блокирующие замечания к результатам проведённой промежуточной или итоговой проверки устраняются до перехода дальше; независимая проверка не заменяет обязательное ревью спецификации или реализации.

Используются три уровня важности:

| Уровень | Значение |
|---|---|
| Критичный | Серьёзная ошибка, неприемлемый риск или нарушение ключевых требований. Блокирует принятие результата и публикацию. |
| Средний | Конкретный дефект или невыполненное обязательное требование. Также блокирует принятие результата и публикацию. |
| Низкий | Рекомендация или необязательное улучшение, которое не препятствует приёмке задачи. |

Каждое замечание содержит место проблемы, основание и ожидаемый результат исправления. Личное предпочтение проверяющего не становится блокирующим требованием, если не опирается на согласованные требования или правила.

Оркестратор возвращает задачу на шаг, ответственный за проблему: ошибки кода, тестов и актуализации документации — в `sov-implement`, ошибки диагностики — в `sov-research`, технического решения — в `sov-plan`, продуктовых требований и решений при обсуждении фичи — в `sov-spec`.

После исправления выполняются необходимые зависимые шаги и повторное ревью. Критичные и средние замечания должны быть устранены либо обоснованно сняты проверяющим. Низкие замечания исправляются в текущей задаче или сохраняются как явно отложенные рекомендации.

## 10. Публикация и завершение

Задача считается завершённой, когда достигнут результат поручения, выполнены обязательные проверки и отсутствуют нерешённые блокирующие замечания. Для задачи с публикацией требуется подтверждённое слияние PR и лишь затем перевод задачи в `done` через `sov-tasks`.

Для задач, ограниченных обсуждением, исследованием или подготовкой локальных материалов, публикация не является обязательной сама по себе. Завершение подготовки требований не означает завершения их реализации.

Порядок публикации определяется правилами проекта: целевая ветка, обязательные проверки GitHub, способ слияния PR и необходимые решения человека.

Публикация изменений проходит через PR в GitHub и завершается после подтверждения его слияния в целевую ветку. Отправка ветки, создание PR или готовность к слиянию не завершают публикуемую задачу.

Перед созданием PR проверяются состав изменений, отсутствие случайно включённых служебных данных и совместимость с актуальной целевой веткой. После обновления ветки, изменений в PR или разрешения конфликтов повторяются затронутые проверки и независимое ревью. Отсутствие текстовых конфликтов не заменяет проверку согласованности изменений.

Перед публикацией новых или изменённых продуктовых требований, после необходимых проверок, оркестратор показывает человеку отчёт с результирующей спецификацией или ссылкой на её полный текст. Отчёт отражает договорённости диалога и закрытые вопросы; при указании человеком расхождений оркестратор уточняет требования и повторяет затронутые шаги. Сам отчёт не требует отдельного формального подтверждения, если правила проекта его не устанавливают.

Оркестратор через `sov-git` создаёт PR, проверяет предусмотренные правилами условия и доводит публикацию до подтверждённого слияния. Он сохраняет ссылку на PR и результат слияния в локальном `task.md`, затем через `sov-tasks` отмечает задачу выполненной. Если слияние ещё не состоялось, задача остаётся незавершённой с зафиксированной причиной ожидания или препятствием.

При прерывании публикации сначала проверяется фактическое состояние репозитория, после чего выполняются только незавершённые действия. Уже опубликованные изменения не публикуются повторно из-за отсутствующей записи в системе задач.

Worktree удаляется только после подтверждения сохранности результатов и согласно правилам проекта. Ошибка публикации не является основанием для удаления рабочей копии или отметки задачи как выполненной.

## 11. Продолжение работы и взаимодействие с человеком

### Автономность и остановки

Оркестратор самостоятельно выполняет доступные шаги до достижения результата либо появления препятствия, которое невозможно безопасно устранить в пределах его полномочий.

Основания для остановки включают необходимость решения человека, отсутствие доступа или обязательного инструмента, внешнюю блокировку, противоречие требований, ограничение текущей сессии либо повторяющиеся неудачные попытки без существенного продвижения.

При остановке сохраняются выполненные шаги, актуальные артефакты, оставшиеся действия, причина препятствия и сведения для продолжения. Нельзя представлять частичный результат как завершённую задачу.

При продолжении, в том числе из новой сессии, оркестратор получает задачу через `sov-tasks`, читает сохранённое состояние, сверяет его с файлами, репозиторием и состоянием PR, проверяет актуальность входов и продолжает с первого необходимого незавершённого либо потерявшего актуальность шага. Если запись, общие артефакты или рабочая копия отсутствуют либо противоречат друг другу, он сначала выясняет фактическое состояние, не начинает новую задачу вместо прежней молча и не считает восстановление завершённым. Контекст переписки помогает работе, но не заменяет сохранённые материалы задачи.

### Вопросы и отчёты

Общение с человеком ведётся простым и понятным языком, с необходимым контекстом, без лишнего жаргона и сокращений. Технические идентификаторы, названия файлов, API и команды сохраняют точное написание.

Вопросы задаются по одному. По возможности предлагаются варианты ответа с номерами и сохраняется возможность собственного ответа. В OpenCode для этого предпочтительно использовать доступный встроенный инструмент вопросов. Уже зафиксированные ответы повторно не запрашиваются, если не появились новые противоречащие сведения.

Итоговый отчёт сообщает, какое поручение выполнялось, какой результат получен, что изменилось для пользователя программы, какие проверки выполнены, завершена ли публикация и какие ограничения остались.

Для подготовки требований прямо указывается, что созданы спецификация и задачи, но поведение программы пока не изменилось. При остановке вместо завершения указываются препятствие и точка продолжения.

Если дальнейшая работа нужна, отчёт содержит один конкретный следующий шаг: действие человека либо способ продолжить текущую или следующую доступную задачу. Пример команды приводится только в соответствии с фактически настроенным интерфейсом SOV.

## 12. Инициализация и обновление

Установку SOV в проект выполняет агент по инструкции в отдельном разделе `README.md` проекта SOV. Рекомендуется закреплённый внешний выпуск скилов, шаблонов, команд среды и CLI одной совместимой версии; проект хранит свои `AGENTS.md`, `rules/`, `docs/` и исключённую из Git `.sov/`. Агент явно записывает версию ресурсов, абсолютные пути и источник задач, подключает необходимые ресурсы и проверяет отсутствие конфликтов имён с установленными командами и скилами. Для OpenCode установка создаёт в проекте два настраиваемых субагента уровней `standard` и `advanced`, по умолчанию сопоставленных `openai/gpt-6-luna` и `openai/gpt-6-sol`. Проект может менять конкретные модели в их конфигурации без изменения скилов; установка проверяет фактическую доступность обеих моделей и разрешения из основной копии и worktree после перезапуска. Существующие `build`, `plan`, их модели и `default_agent` не заменяются. Глобальные команды являются тонким входом только для подключённых проектов: их видимость не подтверждает подключение. Если глобальный способ недоступен, допускается установка проектных команд с доступом из worktree. Для других сред применяется принцип закрепления версии и доступности ресурсов, без предположения о конкретном механизме обнаружения. Настройка источника учётных данных задач относится к `sov-tasks`: файловый список использует совместимый установленный `sov-state`, а иной CLI-источник требует отдельного подключения и подтверждения доступности. Один бинарник может обслуживать несколько проектов одной совместимой версии, но состояние и mutex у каждого проекта свои; при разных версиях закрепляются соответствующие бинарники. Наличие бинарника само по себе не включает протокол в ранее подключённом проекте; при отсутствии подключения агент сообщает о препятствии и не переключает источник либо способ записи молча.

Инициализация проверяет доступность необходимых инструментов и разрешений, включая доступ из worktree к общему хранилищу и ресурсам SOV. Проверка из worktree проводится на копии, содержащей устанавливаемые команды и конфигурацию, либо как явно обозначенная предварительная проверка тех же файлов; ветка без новых проектных файлов не подтверждает их работу. Принятый проектом профиль OKF и устойчивый идентификатор исполнителя, не привязанный к сессии OpenCode, фиксируются явно в правилах проекта. При обновлении ранее созданные назначения по ID сессий не заменяются автоматически: перенос назначения другому идентификатору требует явного решения и записи причины.

Повторная инициализация и обновление сохраняют пользовательские изменения. Существующие правила и документы не перезаписываются молча; при конфликте требуется согласованное решение.

Обновление SOV не должно незаметно менять маршрут или смысл шагов уже выполняемой задачи. При изменении инструкций оркестратор проверяет влияние на незавершённые задачи, их артефакты и условия выполнения и фиксирует необходимые изменения до продолжения работы. Выпуск не заменяется на месте в активных сессиях; переключение инструкций и общего бинарника выполняется в согласованном окне остановки писателей всех затронутых проектов.
