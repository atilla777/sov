# PLAN-044 — проверка передачи SDLC-контекста

2026-10-07 выполнен воспроизводимый сценарий [`tests/plan044_trial.py`](../tests/plan044_trial.py) на временном Git-проекте с общей `.sov/` и отдельным локальным bare-remote. Вызов: `python3 tests/plan044_trial.py`. Действующие проекты не затрагивались; временный стенд удаляется после прогона.

## Фактический маршрут

1. Для неопределённого требования «показать метку» в фикстуре заданы решения: отсутствие входа — ошибка, пустая строка — допустима, текст сохраняется. Создана поведенческая `docs/specs/labels.md`. До и сразу после её push в `main` `sov-task list` возвращал пустой список: публикация требований не создала задачи сама по себе. Отдельным условием фикстуры задан запрос `/sov-decompose docs/specs/labels.md`; только после подтверждения SHA удалённого `main` через CLI созданы две карточки с критериями и зависимостью `0002 → 0001`. `list-ready` показывал только `0001`, `show 0002` — `BLOCKED`.
2. `0001` получила claim; в общей папке задачи записаны `task.md` с решением, SHA Spec, границами и следующим действием и `plan.md` с подходом и проверками. После `release` новый процесс Python, получив **только пути** к файлам (без истории диалога), прочёл `task.md`, `plan.md`, опубликованную Spec и восстановил следующий шаг; последующий `claim` заново захватил тот же ID.
3. Для первой версии `labels.py` обычный тест прошёл, а полный `unittest discover` выявил несоответствие пустой строки критерию. В `checks.md` записаны разные состояния проверок, в `review.md` — запись R1 с замечанием F1 средней важности по оси требований и свидетельством неполной первоначальной проверки по инженерной оси. До устранения F1 completion marker отсутствовал. Второй новый процесс прочёл `task.md`, `checks.md`, `review.md` и восстановил открытое замечание и нужное исправление.
4. Та же задача исправлена; полный набор из двух тестов прошёл для новой версии. Запись R2 в том же `review.md` ссылается на R1/F1 и фиксирует закрытие замечания. Исправление опубликовано прямым push в локальный `origin/main`, SHA проверен чтением bare-remote. Лишь затем `complete 0001` перенёс все артефакты в архив, создал marker и открыл `0002`. Итоговый `validate` вернул `valid:true`.

## Границы и вывод

- Диалог об уточнении требования, показ текста человеку до публикации, независимое ревью Spec, фактический вызов `/sov-decompose` в OpenCode и независимые агентные вызовы `sov-plan`, `sov-implement`, `sov-review-implementation` **не проводились**. Решения и просьба о декомпозиции заданы фикстурой; проверки R1/R2 написаны сценарием, а не независимым проверяющим. Это проверка стыковки файлов и переходов, а не доказательство работы интерактивного маршрута или независимости ревью.
- Восстановление из файлов подтверждено двумя отдельными интерпретаторами и точечными проверками содержания, но не полноценной новой OpenCode-сессией с самостоятельным принятием решения. Пробел для такой сессии: она должна сама прочитать правила целевого проекта, проверить актуальность удалённой Spec и удостовериться, что прежний claim действительно освобождён; наличие того же `owner` само по себе не даёт права продолжить. После R1 для передачи важны **оба** файла `review.md` и `checks.md`, иначе нельзя отличить открытый дефект от проверки старого состояния.
- Карточка `0002` оставлена готовой и не выполнялась: критерии PLAN-044 требуют прохождения одной подготовленной задачи. В стенде её задача про отсутствующий вход остаётся за границами реализации `0001`; полный продукт не объявлялся готовым.
- Расхождений между инструкциями `sov-spec`, `sov-decompose`, `sov-plan`, `sov-implement`, `sov-review-implementation`, `sov-orchestrator`, `sov-tasks` и наблюдаемыми файловыми переходами для этого сценария не выявлено. Изменений маршрута, контракта артефактов или протокола не потребовалось.
