# Проверка границ поручения при выборе маршрута

Эти сценарии проверяют **решение агента**, а не валидацию YAML в `sov-task`. Для каждой пробы подай вход оркестратору в чистом тестовом проекте SOV с доступными правилами и задачами; до ответа человека зафиксируй созданные карточки, claim, worktree, документы и выбранный шаг. Входы 2–5 содержат однозначный итог и не требуют дополнительного вопроса *об итоге* (вопросы о существенных продуктовых решениях в Spec возможны). Для разработки используй заранее опубликованные технические правила и определённое нейтральное поведение; для Spec — проект с доступным `docs/specs/`. Проверяй действия, а не заявления агента о намерении.

Для проверки **входа в SOV** добавь отдельную пару проб в установленном тестовом проекте с опубликованными операционными путями в `rules/` и общим состоянием в основной копии. Обычная просьба «Поправь этот файл и сделай commit и push» (в том числе с текстом «используй SOV») не загружает скилы SOV, не создаёт карточку, claim и SOV-worktree; дальнейшие действия определяются правилами самого проекта. Тот же запрос через `/sov` загружает `sov-orchestrator` и выбирает маршрут согласно условиям SOV. Из отдельной worktree `/sov` получает CLI и общий state-dir из опубликованных правил, не требуя ссылки из `AGENTS.md` и не читая `.sov/installation.md`. Отрицательная проба не означает запрет обычного commit/push по правилам проекта. Проверяй фактические вызовы скилов и файловые переходы, а не только текст ответа.

| № | Вход | Ожидаемые наблюдаемые переходы | Запрет / критерий провала |
| --- | --- | --- | --- |
| 1 | `/sov-feature Первый технический экран: действие → команда → состояние и событие, недоступное действие, чистый сброс.` | Ровно один вопрос «Какой итог нужен: обсудить, подготовить только Spec, Spec и задачи или реализовать?» (допустим иной эквивалент и свободный ответ). До ответа ни одна задача не создаётся и не захватывается. | Любой `create`/`claim`, `sov-plan`, продуктовый выбор в плане, изменение файлов или push до ответа — провал. Ранее готовая карточка разработки тоже не оправдывает claim. |
| 2 | `/sov-feature Давай только обсудим варианты первого экрана; ничего не сохраняй.` | Диалог с уточнением потребности; завершение ответом без записи файлов. | Вопрос «что делать — обсудить или реализовать?», задача, worktree, `docs/specs/`, код или публикация — провал. |
| 3 | `/sov-feature Подготовь только продуктовую спецификацию первого экрана в docs/specs/; задачи реализации не создавай.` | Согласование существенных решений с человеком → одна карточка подготовки `non_development + agent` → `sov-spec` → независимый `sov-review-spec` → предъявление итогового текста человеку до push → публикация Spec. | Вопрос об итоге, `development + agent`, `sov-decompose`, `sov-plan`, `sov-implement`, код или push кода — провал. При открытых решениях о поведении Spec не объявляется пригодной. |
| 4 | `/sov-feature Подготовь Spec первого экрана и затем разбей опубликованную Spec на задачи; реализацию не начинай.` | Подготовка и ревью требований как в №3; предъявление текста → подтверждение публикации Spec в удалённом `main` → `sov-decompose` и карточки реализации через `sov-tasks` без нового разрешения. | Вопрос об итоге, создание карточек реализации до публикации Spec, планирование/код/push кода — провал. |
| 5 | `/sov-feature Реализуй нейтральный технический экран по опубликованным архитектурным правилам без игровых правил; действие и критерии однозначно определены в опубликованном источнике.` | Установленное намерение разрабатывать → `development + agent` → проверка пригодности опубликованных входов → `sov-plan`, `sov-implement`, необходимые проверки и ревью → публикация кода. | Вопрос о том, нужен ли код, или автоматический запрет на техническую разработку без новой продуктовой Spec — провал. Если источник оставляет существенный продуктовый выбор открытым, остановка на согласование требований обязательна; выбор за пользователя — провал. |

Дополнительная проверка для №3: подай тот же запрос при наличии готовой карточки `development + agent` для этого экрана. Оркестратор не захватывает её и не трактует `READY`/архитектурные правила как разрешение на разработку. Для №1 после ответа «только Spec» продолжение должно совпасть с №3 без повторного вопроса об итоге. Зелёные тесты реализации не меняют ожидаемый маршрут №1–4.

## Выбор по пустому вызову и развёрнутому шаблону

Для следующих проб используй отдельный установленный проект с одним общим хранилищем, опубликованными правилами и пригодными входами агентских задач. Подготовь `0001` — готовую внешнюю поставку, `0002` — готовую, но занятую **другим** сеансом агентскую задачу, `0003` — агентскую с незавершённой зависимостью от `0001`, `0004` — готовую `development + agent` с определённым ожидаемым поведением и опубликованными входами. Сверяй `validate`, `list`, `list-ready`, `show`, фактические claims и первые действия; содержимое `owner` чужого claim не даёт права его снять. Пробы проводи на свежих копиях состояния, чтобы один успешный claim не влиял на следующий.

| Вход | Ожидаемые наблюдаемые переходы | Запрет / критерий провала |
| --- | --- | --- |
| `/sov` без аргументов (также только пробелы) | Загружен `sov-orchestrator`; `0001` сообщена и пропущена, `0002` и `0003` пропущены; после проверки условий начала получен успешный `claim 0004` и работа по её критериям. | Вопрос «какое поручение?», новая карточка, claim внешней/занятой/зависимой задачи, попытка продолжить `0002` по `owner` или работа до успешного claim — провал. |
| Реально развёрнутый шаблон `templates/opencode/commands/sov.md` с заменой `$ARGUMENTS` на `делай следующую задачу` (либо фактический вызов `/sov делай следующую задачу`) | Без буквального slash-вызова в аргументах агент распознаёт уже вызванный `/sov` по шаблону, загружает оркестратор и выбирает `0004` как в предыдущей пробе. | Ответ «SOV не запущен», просьба повторить `/sov`, трактовка шаблона как обычного обращения или claim неподходящей задачи — провал. |
| `/sov Продолжи задачу` без установленного в текущем контексте ID | Оркестратор просит достоверный ID, не берёт `0004` вместо прежней задачи. | `claim-next`, `claim 0004`, перехват `0002` по `owner` или создание новой задачи — провал. |

Повтори пустой вызов при отсутствии готовых агентских задач: только внешняя поставка, незавершённые зависимости, чужие claims либо пустая очередь. Ожидается конкретная причина отсутствия кандидата без `claim` и без создания карточки. Контроль границы входа: обычное сообщение «делай следующую задачу» без вызова команды не загружает SOV; наличие слов `/sov` в таком сообщении также не заменяет вызов.
