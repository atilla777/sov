# Включение параллельных координаторов файлового SOV

Протокол условной записи проверен в [PLAN-020](parallel-state-results.md). Это разрешает **контролируемое включение в отдельном целевом проекте**, а не переключает уже работающие проекты или сессии автоматически. Применяйте только к одному локальному Linux-каталогу `.sov` с работающими `flock`, `rename`, `fsync` и сотрудничающими писателями. Для независимых сессий нужны разные устойчивые ID исполнителей; две сессии с одним ID не должны одновременно выбирать или продолжать задачи. Иной источник задач требует отдельного подключения.

## Окно переключения

1. Согласуйте окно без писателей. Инвентаризируйте все сессии, назначенные `in_progress`/`blocked` задачи, источник задач и закреплённую версию SOV в правилах проекта. Завершите старые сессии или остановите их запись и возобновляйте **только** после перезапуска с обновлёнными инструкциями. Не проверяйте переход запуском старого писателя одновременно с новым. Не переназначайте задачи, помеченные прежними ID сессий, без выяснения владельца и явного решения. Сохраните резервную копию существующих ROADMAP и, если уже подключён, ARCHIVE согласно правилам проекта; убедитесь, что она не заменяет общие файлы. Для перехода с версии без ARCHIVE сначала выполните [отдельную процедуру обновления](../README.md#повторная-установка-и-обновление).
2. Подготовьте внешний закреплённый checkout **одной версии SOV**: `skills/`, `templates/`, `.opencode/commands/`, исходники `cli/sov-state/` и бинарник должны соответствовать ей. Один бинарник может обслуживать несколько проектов совместимой версии, но каждому нужен свой абсолютный `state-dir` и свой mutex; замена общего пути требует остановки писателей всех использующих его проектов. Для разных версий используйте разные закреплённые бинарники. Сравните конфигурацию и пользовательские правки до обновления. В окне без писателей выполните [подготовку бинарника и mutex](../README.md#подготовка-общего-бинарника-sov-state-linux): кандидат, `--version` с `v:1`, `read` из основной копии и двух worktree, проверка прав и no-op `commit` с тем же абсолютным `state-dir` **для каждого проекта**; только затем атомарно замените бинарник. Существующие ROADMAP и `.roadmap.lock` не пересоздавайте и не заменяйте. Сверьте один inode mutex и одно содержимое списка между копиями **одного проекта**.
3. При остановленных писателях переключите настройки источника, путь к бинарнику, версию скилов и три команды `/sov*` согласованно; запишите **один абсолютный путь** к основной `.sov` и бинарнику в правилах проекта. Глобальные команды требуют проверки подключения каждого проекта; проектные команды и конфигурация должны находиться в проверяемой worktree: ветка без них не подтверждает установку. Следуйте [порядку первой проверки](../README.md#первое-подключение). Удалите инструкции прямой записи и возможный fallback в установленной конфигурации, не затирая пользовательские изменения. Перезапустите OpenCode. Проверьте из основной копии и двух worktree обнаружение скилов и команд без конфликтов имён, запуск бинарника, доступ OpenCode на чтение ресурсов SOV и чтение/запись общего состояния, артефакты задач, no-op `commit` и `git check-ignore .sov/ROADMAP.md`. Терминальная проба сама по себе не доказывает разрешения OpenCode.
4. Сверьте источник, текущие назначения, зависимости и локальные артефакты с состоянием PR/Git перед возобновлением старых задач. Новые независимые координаторы допускаются **только после** успешных проверок и фиксации в правилах целевого проекта, что все писатели используют условную запись `sov-tasks` одной совместимой версии и разные устойчивые ID. Первая реальная конкуренция должна быть наблюдаемой: проигравший перечитывает список и не начинает занятую задачу. После переключения на версию с архивом список и архив изменяются только через `sov-tasks` → `sov-state read/commit/archive`; `task.md` и Git не входят в эту транзакцию.

Если сборка, контракт, права, единый mutex, переход инструкций или сверка назначений не прошли, **не объявляйте параллельный режим действующим**. До переключения оставьте прежнюю работоспособную установку с одним координатором; после переключения остановите писателей и устраните причину. Прежние бинарник и инструкции можно вернуть только пока не выполнен первый перенос в ARCHIVE: после переноса прежний маршрут без архива не видит все задачи, для отката нужна отдельная проверка и восстановление списка при остановленных писателях. Не возвращайтесь к прямой записи как запасному пути для включённого CLI-протокола. Потеря ответа на `commit` или `archive` разрешается свежим чтением и смысловой сверкой эффекта, а не безусловным повтором. Обновление нескольких файлов установки не атомарно, поэтому окно без старых писателей обязательно при каждом таком обновлении.

Границы защиты: CLI сериализует **байты одного** ROADMAP; корректность назначений, зависимости, PR и восстановление артефактов остаются обязанностью `sov-tasks`/оркестратора. Запись в обход CLI и параллельные сессии под одним ID не защищены. Подробности [контракта CLI](shared-state-cli-proposal.md#2-предлагаемый-контракт-cli) и [маршрута задач](../skills/sov-tasks/SKILL.md).
