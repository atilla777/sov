# SOV Tasks — файловая система управления задачами

## Назначение и область действия

Это целевые требования к учёту задач **целевых проектов SOV** вместо файлового списка `.sov/ROADMAP.md` / `.sov/ARCHIVE.md` и протокола `sov-state`. Источник требований — `sov_tasks_filesystem_concept.md` в Obsidian-хранилище проекта SOV (редакция, предоставленная 2026-10-07) и уточнения пользователя при подготовке этой спецификации. CLI и исходные инструкции скилов реализуют новый маршрут; подключённые проекты пока не переключены: включение требует отдельной установки и остановки старых писателей. Обратная совместимость со старым протоколом не требуется.

Цель — понятное агенту и человеку файловое хранение без базы данных и сервера, с предпочтительным порядком выполнения, зависимостями, конкурентным захватом и архивированием. Файловая система — единственный источник истины для состояния задач. Скилы принимают смысловые решения и ведут workflow; возможная CLI служит тонким слоем файловых операций, проверки инвариантов и валидации, а не планировщиком или хранилищем состояния.

## Хранилище и идентичность

```text
.sov/
├── tasks/
│   └── 0012-mailbox-sync/
│       ├── task.yaml
│       ├── task.md
│       └── ...
├── claims/
│   └── 0012-mailbox-sync/
│       ├── owner
│       └── claimed_at
├── completed/
│   └── 0007
└── archive/
    └── 0007-bootstrap/
        └── task.yaml
```

`tasks/` содержит незавершённые задачи; `claims/` — каталоги текущих захватов; `completed/` — лёгкие маркеры успешного завершения по ID; `archive/` — полное описание завершённых задач. Отдельных каталогов `planned/`, `active/`, `done/` нет. `ROADMAP.md` может быть представлением или отчётом, но не источником runtime-состояния и не общей изменяемой очередью.

ID — стабильная строка из четырёх цифр (`0001`…`9999`), не кодирующая иной семантики. Каталог называется `<id>-<короткое-имя>`, например `0012-mailbox-sync`. ID обеспечивает естественную сортировку и предпочтительный порядок рассмотрения; реальные ограничения задают зависимости. Уже созданная задача идентифицируется своим ID и каталогом; повторное использование ID после завершения противоречит стабильности идентификатора.

Каталог незавершённой задачи также хранит локальные артефакты шагов SOV (`task.md`, `spec.md`, `plan.md`, `research.md`, `checks.md`, `review.md` при применимости). При завершении каталог со всем содержимым перемещается в `archive/`. Результаты, которые по общим правилам должны быть опубликованы в `docs/` и `rules/`, остаются документами проекта, а не заменяются архивом задачи. Worktree задачи — отдельная рабочая копия; поиск файлового хранилища идёт от основной папки проекта, а не от её копии в worktree.

### Формат `task.yaml`

```yaml
id: "0012"
title: Implement mailbox sync
description: |
  Реализовать синхронизацию mailbox.
  Учесть существующую архитектуру и текущие API.
depends_on:
  - "0007"
  - "0009"
acceptance_criteria:
  - Синхронизация запускается для активного mailbox.
  - Ошибки корректно обрабатываются.
  - Существующие тесты проходят.
  - Добавлены тесты новой логики.
```

Обязательны `id`, `title`, `description`, `depends_on`, `acceptance_criteria`. ID и ID зависимостей записываются **строками** с ведущими нулями. Необязательные поля в будущем: `type`, `workflow`, `tags`, `references`. Runtime-поля `status`, `claimed_by`, `claimed_at`, `completed_at` в `task.yaml` не записываются: состояние вычисляется из файловой системы. Семантическое описание и критерии остаются в карточке задачи; подробности исполнения — в артефактах шагов.

## Состояния, зависимости и выбор

- Незавершённая задача в `tasks/` без claim и completion marker — `READY`, если все ID из `depends_on` имеют соответствующие `completed/<id>`; иначе `BLOCKED`. Это блокировка **зависимостями**, а не прежний вручную назначаемый статус препятствия.
- Задача с каталогом `claims/<task>/` — `IN PROGRESS`.
- Успешное завершение отмечается `completed/<id>`, а описание перемещается в `archive/<task>/`.

Зависимость считается выполненной **только** при наличии `completed/<id>`; читать архив для этого не нужно. Отменённая или удалённая незавершённая задача не создаёт такой маркер и не разблокирует зависимые задачи. Выполнять можно лишь задачи с завершёнными зависимостями. Из `tasks/` задачи просматриваются по возрастанию ID; заблокированная или уже занятая задача пропускается, следующая готовая может быть взята вне строгого порядка ID. Если готовых задач нет, агент сообщает об этом и не снимает захваты или зависимости ради продолжения.

Отдельных статусов `blocked` (препятствие при исполнении) и `cancelled` в новой файловой модели нет: препятствие фиксируется в артефактах задачи; при прекращении работы без успешного завершения claim освобождается, а ненужная незавершённая задача может быть удалена. Удаление не является обычным способом завершения и не создаёт completion marker. Архив завершённых задач предпочтительно сохраняется.

## Захват и параллельная работа

Для готовой задачи агент атомарно создаёт `claims/<task>/` через `mkdir`. Один из конкурирующих вызовов получает успех, остальные при `File exists` пропускают задачу; проверка готовности без успешного `mkdir` не является захватом. Агент вправе записать в захваченный каталог файлы `owner` и `claimed_at` для диагностики. Само **существование каталога** — lock; записи в нём не заменяют его и не являются вторым протоколом владения. Постоянный владелец, UUID-захват и автоматический lease для нового протокола не требуются.

Один агент рассматривает задачи по ID, проверяет `task.yaml` и зависимости, пропускает уже захваченные и пытается `mkdir` для первой подходящей; при конфликте пробует следующую. Несколько агентов могут делать это одновременно. Работу над полученной задачей, её артефактами и рабочей копией ведёт захвативший агент; другой агент не продолжает её только по совпадению человека или машины. Освобождение без завершения удаляет собственный claim, после чего незавершённая задача снова доступна. После аварии claim может остаться: на первом этапе автоматического обнаружения или снятия stale claims нет. Человек/агент вручную сверяет состояние работы и удаляет stale claim; `owner` и `claimed_at` помогают диагностике, но не служат доказательством актуальности сеанса.

Для описанного `mkdir`-протокола агенты должны обращаться к одному файловому хранилищу проекта. Каталоги claim не являются механизмом синхронизации разных независимых копий файловой системы.

## Завершение и архив

После успешного выполнения задачи порядок операций из концепции:

1. Создать `completed/<id>`.
2. Перенести весь `tasks/<task>/` в `archive/<task>/`.
3. Удалить `claims/<task>/`.

Маркер позволяет дешево проверять зависимости, архив сохраняет историю, а `tasks/` не содержит завершённых задач. Агент завершает и публикует работу по общим требованиям SOV к проверкам, ревью и публикации; для публикуемой задачи marker создаётся только после подтверждения публикации в удалённом `main`. Файловые шаги завершения не являются одной атомарной транзакцией. Прерывание между ними оставляет промежуточное состояние, которое следует диагностировать и завершить до повторного выполнения операции; нельзя выдавать наличие одного маркера за доказательство успешного переноса всего каталога. При этом проверка зависимостей согласно концепции опирается именно на маркер.

## Интерфейс скила и возможной CLI

`sov-tasks` скрывает низкоуровневый формат от оркестратора, создаёт и выбирает задачи, сообщает вычисленное состояние, зависимости и порядок, обеспечивает захват, освобождение и завершение в соответствии с файловым протоколом. Смысловая декомпозиция, приоритеты, архитектура, критерии приёмки, workflow и управление AI-сеансами принадлежат скилам, не CLI. CLI при добавлении не меняет файловую модель и не становится независимым task manager.

Рекомендуемый начальный интерфейс `sov-task`:

| Команда | Назначение |
| --- | --- |
| `list`, `list-ready`, `show <id>` | Просмотр задач и их вычисленного состояния. |
| `create` | Создание каталога и карточки задачи. |
| `claim <id>` | Найти задачу, проверить YAML, отсутствие completion marker и зависимости, атомарно создать claim, при необходимости записать диагностические файлы, вернуть результат. |
| `claim-next` | Просмотреть задачи по ID и последовательно пробовать claim готовых, вернуть первую захваченную или `no ready tasks`; устраняет гонку между раздельными `list-ready` и `claim`. |
| `release <id>` | Освободить claim без завершения. |
| `complete <id>` | Проверить существование задачи и claim и выполнить весь протокол завершения. Если `owner` используется как проверяемый атрибут, сверить его с текущим владельцем; выбранная простая модель не делает этот файл обязательным средством авторизации. |
| `validate [id]` | Проверка отдельной задачи или всего хранилища. |

Минимальная валидация: корректный YAML; наличие `id`, его строковый тип и формат `NNNN`, совпадение с именем каталога; непустые `title`, `description`, непустой список `acceptance_criteria`; `depends_on` — список корректных строковых ID, без зависимости на себя; отсутствие дублирующихся ID. Расширенные проверки целостности ссылок, циклов зависимостей, осиротевших claims, claims для завершённых задач, совпадений задач с архивом и маркеров без исторических задач могут появиться в будущей команде `doctor`; `archive` и `graph` также отложены. Минимальная проверка `validate` не выдаётся за `doctor`.

CLI осуществляет файловые операции, валидацию и охрану инвариантов; не решает, что разрабатывать и каким образом. При первоначальном включении нового протокола в ранее подключённом целевом проекте требуется отдельное контролируемое переключение установки и старых сеансов; этот документ не устанавливает автоматическую миграцию старых списков, назначений или локальных артефактов.
