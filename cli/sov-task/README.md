# `sov-task` — файловое ядро задач

Реализация [контракта SOV Tasks](../../docs/specs/filesystem-tasks.md) для одного общего локального каталога `.sov`. Исходники скилов описывают новый протокол; уже установленные проекты остаются на закреплённом прежнем выпуске до отдельного переключения. Порядок установки и перехода готовится отдельно (PLAN-037).

Требуются Python 3 и PyYAML (`python3 -m pip install PyYAML` в выбранном окружении). Указывайте **абсолютный путь** к основной папке состояния, одинаковый для всех worktree. До использования создайте в ней `tasks/`, `claims/`, `completed/`, `archive/`; при обновлении отсутствие одного из этих каталогов — ошибка, а не сигнал создать пустое состояние.

```sh
python3 cli/sov-task/sov_task.py --state-dir /project/.sov create --file /tmp/card.yaml --slug mailbox-sync
python3 cli/sov-task/sov_task.py --state-dir /project/.sov list-ready
python3 cli/sov-task/sov_task.py --state-dir /project/.sov claim-next --owner agent-a
python3 cli/sov-task/sov_task.py --state-dir /project/.sov show 0001
python3 cli/sov-task/sov_task.py --state-dir /project/.sov validate
```

Доступны `list`, `list-ready`, `show <id>`, `create --file <yaml> --slug <name>`, `claim <id> [--owner ...]`, `claim-next [--owner ...]`, `release <id> [--owner ...]`, `complete <id> [--owner ...]`, `validate [id]`. Карточка для `create` содержит обязательные поля спецификации; если `id` отсутствует, CLI под локальным `flock` выдаёт следующий ID после максимального ID в задачах, архиве, маркерах и claims. ID в YAML должен быть строкой в кавычках (например, `"0012"`). `--slug` — строчные латинские слова с цифрами через дефис. Номера до 9999; переполнение — ошибка. Ответы — JSON, ошибки — JSON на stderr и код 2; `validate` при нарушениях выводит JSON со списком ошибок на stdout и код 2. `claim` при занятой или неготовой задаче возвращает `not_ready`, `claim-next` — `no_ready_tasks`, оба с кодом 0.

`claim` атомарно создаёт каталог и повторно проверяет условия. `owner` — диагностический текст: если он записан в claim, `release` и `complete` требуют совпадающее значение, но это не проверка живости сеанса или безопасный автоматический перехват. Если исполнение прекращено без успеха, освободите **свой** claim через `release`. При аварии перед ручным удалением оставшегося claim сначала сверьте артефакты, работу старого агента и Git. `complete` вызывается только после успешных проверок и подтверждённой публикации результата задачи в удалённом `main`: CLI это внешнее условие не проверяет.

`complete` выполняет marker → перенос папки задачи целиком → удаление claim. Если выполнение прервалось, `validate` сообщает о неполном состоянии. Повтор `complete` с прежним claim продолжает однозначный перенос: при marker + task переносит task; при marker + archive удаляет claim. Если отсутствует claim, есть совпадающие папки, повреждена карточка или отсутствует marker при уже перенесённой папке — нужна ручная проверка, CLI не восстанавливает историю догадкой. Для зависимостей достаточно marker даже во время промежуточного переноса, как предписывает спецификация; это **не** означает, что завершение переноса подтверждено. При неполном `create` после сбоя `validate` сигнализирует об отсутствующей/неполной карточке.

Гарантии рассчитаны на одну локальную файловую систему с атомарными `mkdir` и `rename` и поддержкой `flock`; не распространяются на независимые копии `.sov`. Перенос между файлами не является единой транзакцией, `fsync` каталога при записи marker не выполняется (устойчивость к внезапной потере питания не заявляется). Для смены активного исполнителя нет lease и автоочистки stale claims. `validate` проверяет формат карточек и диагностирует известные промежуточные состояния, но не является расширенным `doctor`: граф, циклы и полнота всех зависимостей не проверяются.

Проверка: `python3 -m unittest discover -s cli/sov-task -v` из корня репозитория.
