# SOV

SOV — проект набора взаимосвязанных Agent Skills и шаблонов артефактов для разработки с агентами в средах типа OpenCode. Цель, границы и предполагаемый порядок работы описаны в [спецификации принципов работы](docs/sov-spec.md). Контракты и шаблоны артефактов подготовлены; исходные инструкции всех скилов, включая `sov-orchestrator`, находятся в [`skills/`](skills/README.md). Доступна инструкция ручного подключения к проекту; основные маршруты и ограничения проверены на отдельном пробном проекте.

## Установка и обновление в существующем проекте (для агента)

Эта процедура подключает SOV к **целевому** проекту с Git и OpenCode без установщика. Сначала прочитай его `AGENTS.md`, `rules/index.md`, `docs/index.md` (если они есть), проверь текущие изменения и согласуй с владельцем проекта недостающие решения. Не копируй `AGENTS.md`, `rules/` или `docs/` **этого** репозитория как правила целевого проекта. Инструкции шагов находятся в [`skills/`](skills/README.md), артефакты — в [`templates/`](templates/README.md), команды — в [`.opencode/commands/`](.opencode/README.md).

### Первое подключение

1. Запиши абсолютные пути к основной папке целевого проекта (`<project>`) и **внешнему, неизменяемому на время работы выпуску** SOV (`<sov>`), а также его версию (commit или release). Рекомендуется хранить `skills/`, `templates/`, `.opencode/commands/`, исходники `cli/sov-state/` и собранный из них бинарник вне целевого проекта по закреплённым путям, доступным основной копии и каждой worktree. Не ссылайся на относительный путь из основной копии и не используй меняющийся `main`. В целевом проекте остаются его `AGENTS.md`, `rules/`, `docs/` и исключённая из Git `.sov/`; проектные настройки OpenCode включают проектных субагентов уровней моделей. Проверь наличие `skills/*/SKILL.md`, `templates/ROADMAP.md`, `templates/ARCHIVE.md`, `templates/task.md`, [`templates/opencode/agents/`](templates/opencode/agents/), трёх файлов команд и исходников CLI в `<sov>`. Проверь Linux, Go по [`go.mod`](cli/sov-state/go.mod) (сейчас Go 1.25.4 или совместимая более новая версия), `git`, OpenCode, а для публикации через GitHub — `gh`, доступ к remote, права чтения ресурсов, записи в основную папку и создания worktree. Если необходимый инструмент или доступ отсутствует, сообщи о препятствии, не объявляй установку законченной.
2. Подключи все папки скилов SOV к OpenCode. Например, добавь **к существующему** `opencode.json` проекта (или `.opencode/opencode.json`) путь к `<sov>/skills` в `skills.paths`, сохранив другие настройки и пути; для глобального подключения добавь тот же путь в пользовательскую конфигурацию OpenCode:

   ```json
   {
     "$schema": "https://opencode.ai/config.json",
     "skills": { "paths": ["/абсолютный/путь/к/sov/skills"] }
   }
   ```

   Это пример для нового файла, а не команда заменить существующий JSON. Рекомендуется установить [`sov.md`](.opencode/commands/sov.md), [`sov-feature.md`](.opencode/commands/sov-feature.md) и [`sov-bug.md`](.opencode/commands/sov-bug.md) в `~/.config/opencode/commands/` из той же версии `<sov>`, сверив одноимённые файлы до замены. Глобальные команды доступны и в неподключённом проекте: запуск допустим только после проверки проектных правил, версии, путей и источника задач; сама видимость `/sov` ничего не подтверждает. Если глобальный способ недоступен, установи эти файлы в `<project>/.opencode/commands/` и обеспечь их доступность также в worktree (обычно через Git). Если в глобальном или проектном каталоге уже есть одноимённые команды или скилы SOV другой версии, выясни, какие файлы фактически выбирает OpenCode, и согласуй конфликт до работы; не полагайся на случайный приоритет. После изменения конфигурации перезапусти OpenCode: работающая сессия не обязана подхватить новые файлы. Проверь отдельно разрешение OpenCode на чтение каталога `<sov>` **из основной копии и worktree**: обнаружение скила через `skills.paths` ещё не означает доступ к соседним шаблонам или исходникам. При отказе в чтении добавь к существующей конфигурации узкое разрешение `permission.external_directory` для согласованного абсолютного пути `<sov>/**` (например, `"/путь/к/sov/**": "allow"`), перезапусти OpenCode и повтори проверку; не открывай без необходимости все внешние каталоги.
3. Подключи **в проекте** двух субагентов OpenCode: установи [`sov-standard.md`](templates/opencode/agents/sov-standard.md) и [`sov-advanced.md`](templates/opencode/agents/sov-advanced.md) из того же закреплённого `<sov>` в `<project>/.opencode/agents/`, не перезаписывая существующие одноимённые файлы без сравнения и решения владельца. Поле `model` внутри проектных файлов — точка настройки уровней: по умолчанию `standard = openai/gpt-6-luna`, `advanced = openai/gpt-6-sol`. Для другого провайдера измени **эти два поля** на доступные `provider/model-id` по решению проекта, сохранив `mode: subagent`, назначение и инструкцию агента. Не добавляй несуществующие поля `standard`/`advanced` в `opencode.json`, не меняй `model`, `default_agent`, встроенные `build` и `plan` либо модели команд `/sov*`. При существующем глобальном или проектном агенте того же имени выясни фактически выбранную конфигурацию и согласуй конфликт; проверяй модель после объединения настроек, а не только текст файла. Эти проектные файлы должны входить в проверяемую worktree (обычно через Git); если ещё не опубликованы, проверяй worktree с их точными копиями и повтори проверку после публикации. Из текущего проекта проверь обе реально выбранные модели через `opencode models <provider>` и наличие/модель агентов через `opencode debug agent sov-standard` и `opencode debug agent sov-advanced`; команда `opencode run --agent sov-standard` **не** проверяет субагента (OpenCode переключится на основной), для пробы запускай его через инструмент `task` основного агента. Невозможность получить доступ к любой модели — препятствие, не повод молча использовать модель основного агента. После изменения файлов перезапусти OpenCode: прежняя сессия не обязана загрузить новые модели.
4. Выбери источник задач явно. Файловый источник `<project>/.sov/ROADMAP.md` и `<project>/.sov/ARCHIVE.md` работает через установленный и проверенный `sov-state`; иной CLI/API допустим **только** при реализованном подключении в `sov-tasks` и подтверждённой доступности. Установленный бинарник сам по себе не переключает старый проект; при неподдерживаемом источнике сообщи о препятствии вместо молчаливого переключения. Добавь `.sov/` в корневой `.gitignore` и проверь исключение с помощью `git check-ignore .sov/ROADMAP.md`; при наличии уже отслеживаемых файлов `.sov/` согласуй их удаление из индекса отдельно. Для файлового источника **только при первом подключении и до начала работы писателей** создай отсутствующие очередь из [`templates/ROADMAP.md`](templates/ROADMAP.md) с постоянным префиксом ID и архив из [`templates/ARCHIVE.md`](templates/ARCHIVE.md); существующие файлы не заменяй. После инициализации все штатные изменения — только через `sov-tasks` и CLI, без прямой записи из установки. При обновлении отсутствие прежде существовавшей очереди или архива означает возможную утрату состояния: не создавай файлы автоматически. Подготовь `<project>/.sov/tasks/` и `<project>/.sov/worktree/` как локальные папки основной копии. Не создавай второй список задач внутри worktree.
5. В существующих `AGENTS.md` и применимых `rules/` целевого проекта запиши **принятые проектом** правила: абсолютный путь к основной папке и ресурсу SOV (либо воспроизводимый способ их определения), версию ресурсов, файловый источник задач, префикс ID, **устойчивые ID исполнителей** (при параллельной работе одного разработчика — отдельные постоянные рабочие слоты и способ явного выбора слота перед каждым поручением и возобновлением), целевую ветку и правила публикации, ссылки на `rules/index.md` и `docs/index.md`. Не дублируй универсальный алгоритм выбора и назначения задач в правилах проекта: он находится в `sov-orchestrator` и `sov-tasks`. Укажи пути к проектным `sov-standard`/`sov-advanced` и действующие модели либо способ их проверки; при изменении модели уровня новые шаги получают новую модель, уже выполненные не переписываются. Для файлового протокола обязательно запиши абсолютный путь к одному бинарнику и один `state-dir=<project>/.sov` основной копии, одинаковый в каждой worktree; не вычисляй их относительно текущей worktree или из случайного `PATH`. Сеансы с одним ID не могут безопасно одновременно выбирать, создавать или продолжать задачи. Не используй ID сессии как единственное назначение задачи; при смене устойчивого исполнителя существующие назначения переносит `sov-tasks` только по явному решению с фиксацией причины. Укажи, что перед работой агент читает применимые правила и опубликованные требования в `docs/`; технический план их не заменяет. Явно выбери с владельцем и зафиксируй профиль Open Knowledge Format: расположение спецификаций, ADR и правил, метаданные и индексы для каждого типа документов; существующие файлы не устанавливают профиль автоматически. Если `AGENTS.md`, `rules/`, `docs/` или индексов ещё нет, создай только согласованные с проектом документы и ссылки, не подставляя текст SOV вместо его правил. При конфликте с действующими правилами остановись и получи решение владельца.
6. Проверь доступ из **основной копии и пробной worktree с устанавливаемой конфигурацией**. При глобальном подключении создай пробную worktree от обычной базовой ветки: её проверка действительна, только если она уже содержит принятые проектные `AGENTS.md`/`rules/` с версией, путями, моделями и источником задач; иначе сначала предоставь ей те же проверяемые файлы и явно зафиксируй, что это предварительная проверка до их публикации. При проектных командах, агентах или `opencode.json` базовая удалённая ветка без этих файлов **не проверяет установку**: создай пробную worktree от локального коммита с устанавливаемыми файлами либо проверь временную копию worktree, в которую внесены в точности те же ещё не опубликованные файлы; после публикации повтори проверку из чистой worktree целевой ветки. В обоих случаях после перезапуска OpenCode проверь, что из каждой копии доступны все скилы и `/sov`, `/sov-feature`, `/sov-bug`, **оба субагента с выбранными проектом моделями**, что команды и агенты не конфликтуют с одноимёнными, а агент может прочитать шаблон из `<sov>/templates/`, общий список через зафиксированный `sov-state read --state-dir <project>/.sov` и папку артефактов основной копии, создать/прочитать пробный артефакт в `<project>/.sov/tasks/`. Пробный вызов каждого субагента через `task` должен сообщить фактическую модель и прочитать нужный скил; ревью назначай новому независимому вызову. Убедись, что `/sov*` сохраняют текущий `build`/`plan` и его модель; в `plan` пишущая операция не передаётся субагенту для обхода ограничений. Проверь именно разрешения OpenCode на внешние каталоги, не только результат терминальной команды. До включения писателей проверь совместимый бинарник, mutex и no-op commit по процедуре ниже. Проверь исключение `.sov/` и отсутствие её в составе коммита. Удали пробную worktree штатно после проверки сохранности данных; не заменяй ею рабочую копию уже выполняемой задачи.

### Подготовка общего бинарника `sov-state` (Linux)

Это обязательный шаг поставки перед включением файлового протокола в `sov-tasks` целевого проекта. Требуется локальная ФС с `flock`, атомарным `rename` и `fsync`, существующие обычные `<project>/.sov/ROADMAP.md` и `ARCHIVE.md` (не symlink и не hardlink), право чтения обоих файлов и записи в `.sov/`. Отсутствующий при обновлении ROADMAP не восстанавливай из шаблона. Выбери `<sov>/bin/sov-state` как общий абсолютный путь; если `<sov>` недоступен для записи, заранее согласуй **один** другой абсолютный каталог для бинарника. Несколько проектов одной совместимой версии могут использовать **один бинарник** по этому пути, но каждый указывает свой абсолютный `state-dir=<project>/.sov` и сохраняет свой `.roadmap.lock` внутри него; не создавай общий каталог состояния для разных проектов. Для разных закреплённых версий выбирай соответствующие им бинарники и пути, не заменяй бинарник, пока его используют сессии другой версии. Не клади копии в worktree. Для сборки и проверки кандидата из того же закреплённого `<sov>`:

```sh
mkdir -p "<sov>/bin"                    # либо заранее выбранный каталог
sh "<sov>/cli/sov-state/build-candidate.sh" "<sov>/bin/.sov-state-next"
"<sov>/bin/.sov-state-next" --version
```

Скрипт требует Go, собирает временный файл в каталоге назначения, сверяет `--version` с `sov-state 0.2.0 (protocol v:1)` и публикует только целого кандидата; при ошибке не трогает установленный бинарник. При иной закреплённой версии SOV сверяй ожидаемые версии скрипта, исходников, скилов и команд **до** обновления; несовпадение — повод остановиться, а не игнорировать проверку. На время замены останови старых писателей. До публикации кандидата проверь его исполняемость и JSON `v:1`, `status:ok`, `resource:ROADMAP.md` командой `read --state-dir "<project>/.sov"` и `resource:ARCHIVE.md` командой `read-archive --state-dir "<project>/.sov"` из основной копии и двух пробных worktree: абсолютные пути CLI и `state-dir` должны быть **теми же**, `revision` и `content_base64` — совпадать. Проверь разрешение OpenCode из обеих копий на запуск бинарника и доступ к внешнему каталогу состояния (и на запись в него для будущего переноса); для внешнего каталога при необходимости согласуй узкое `permission.external_directory` на `<project>/.sov/**` так же, как для `<sov>/**`. Не считай запуск из терминала доказательством разрешения OpenCode.

Для первого включения протокола, **до** проверки `commit`, создай постоянный `<project>/.sov/.roadmap.lock` с mode `0600` только если его ещё нет: при отсутствии файла и symlink выполни `(umask 077; set -C; : > "<project>/.sov/.roadmap.lock")`; если исключающее создание не удалось, остановись и проверь причину. При существующем файле проверь, что он обычный, не symlink/hardlink, и сохрани его inode. При обновлении не удаляй и не заменяй mutex. С остановленными писателями проверь read/commit-права кандидата без изменения списка: скопируй ROADMAP в отдельный входной файл, возьми `revision` из нового `read`, выполни `commit --state-dir "<project>/.sov" --expected <revision> --input <абсолютный-путь-к-копии>`; ожидается `status:ok`, `changed:false` и прежний revision. Повтори из другой worktree, предварительно перечитав список; проверь один и тот же inode mutex и одинаковый список после проверок. Не запускай такой `commit` на проекте со старым активным писателем. После успешных проверок опубликуй кандидата атомарным `mv` **в том же каталоге** на выбранный абсолютный путь `sov-state`; ещё раз проверь `--version` и `read` из основной копии и worktree. Если после замены проверка не прошла, восстанови сохранённый прежний бинарник до возобновления писателей и разбери препятствие. Включение нового `sov-tasks` требует отдельного обновления инструкций и сессий при остановленных писателях; само наличие бинарника не разрешает параллельных координаторов.

После остановки или обновления всех старых писателей и проверки нового CLI включи файлы `sov-tasks` и команд из одной версии SOV, перезапусти OpenCode. При создании задачи `sov-tasks` читает и условно обновляет список из **основной** папки через CLI, а оркестратор после подтверждённой записи создаёт `.sov/tasks/<ID>/` и передаёт её абсолютный путь исполнителям. При прерывании между этими действиями он сверяет строку и папку и завершает недостающее, не создавая дубликат. Терминальные задачи без зависимых строк `sov-tasks` переносит через CLI в ARCHIVE; `task.md` при этом остаётся. В новой сессии `/sov` без аргументов сначала ищет в общем списке задачи `in_progress` и `blocked`, назначенные этому устойчивому исполнителю: одну продолжает после сверки артефактов и Git/PR (для `blocked` сообщает препятствие), при нескольких просит ID; лишь при отсутствии таких задач выбирает новую `planned`. Файлы `task.md`, `plan.md`, `checks.md` и другие копируются из `templates/` только по необходимости выбранного маршрута и заполняются фактическим содержанием. Код и постоянные `docs/`/`rules/` читаются из worktree задачи; общие артефакты не дублируются. Согласованные требования сохраняются в `docs/specs/`, решения — в `docs/adrs/` и правилах целевого проекта по принятому профилю. До выполнения [процедуры включения](docs/parallel-activation.md) в целевом проекте действует один координатор.

### Повторная установка и обновление

При переходе существующего проекта с версии без архива сначала останови всех писателей и сохрани проверяемую резервную копию `.sov/` по принятому проектом способу. Убедись, что ROADMAP существует и читается старым бинарником, все его ID и зависимости корректны, а ARCHIVE ещё никогда не существовал: отсутствие прежде существовавшего архива означает возможную потерю данных, а не повод создать пустой. Только при **первом переходе** и после проверки отсутствия ARCHIVE создай его из [`templates/ARCHIVE.md`](templates/ARCHIVE.md) с ограниченными правами (`0600`) без замены ROADMAP, mutex или артефактов. Не переносите старые завершённые строки до проверки нового CLI и обновления всех писателей. Затем установи версию 0.2.0 и переключи инструкции при остановленных писателях по процедуре ниже; `sov-tasks` может перенести допустимые терминальные строки при первой штатной операции или отдельном запросе на уборку. При сбое установки до первого переноса возвращай прежние бинарник и инструкции; после первого переноса откат на версию без архива запрещён без отдельной сверки и восстановления объединённого списка при остановленных писателях.

Сначала сравни установленную закреплённую версию, бинарник, конфигурацию, скилы, команды, **проектных субагентов и их модели**, пути, `AGENTS.md`, `rules/`, `docs/`, `.gitignore`, список и локальные артефакты с предлагаемыми изменениями; сравни пользовательские правки каждого обновляемого файла. Запиши используемый источник и версию ресурсов SOV (commit или release) в правилах проекта. Перед использованием поиска по устойчивому исполнителю проверь действующие назначения: если они основаны на ID прежних сессий, выясни владельца каждой незавершённой задачи и перенеси назначение через `sov-tasks` только по явному решению с причиной в `task.md`; до разрешения таких назначений не считай отсутствие собственных задач основанием начать следующую `planned`.

Подготовь новый **отдельный закреплённый** checkout SOV и сверь версию бинарника/контракт `v:1` со скилами, агентами и командами этой версии до переключения конфигурации; не обновляй checkout на месте, пока его используют старые сессии. Останови старых писателей на согласованное окно во **всех проектах**, использующих заменяемый путь к бинарнику; для независимого обновления проекта установи новую версию по новому пути и переключи только этот проект. Сборку и проверки кандидата из раздела выше выполни **до** замены действующего бинарника и инструкций. При ошибке сборки или несовместимости кандидат удаляется, прежний бинарник, источник и инструкции остаются рабочими. Сохрани прежний бинарник отдельной копией перед атомарной заменой, не подменяя файл mutex и ROADMAP. Обновляй только выбранные файлы и пути к ресурсам вместе с версиями в правилах проекта, сохраняя пользовательские правки; новые агенты `sov-standard`/`sov-advanced` устанавливай только после проверки конфликта имён и согласования пользовательских моделей. При конфликте согласуй решение. До допуска новых писателей проверь исполняемость, контракт `v:1`, read и no-op commit через **тот же** `state-dir` и mutex из основной копии и двух worktree, разрешения OpenCode на доступ и запуск, скилы, агентов с выбранными моделями и команды после перезапуска. Если проверка после переключения не прошла, верни прежние бинарник, конфигурацию и инструкции при остановленных писателях; зафиксируй препятствие. Никогда не возвращайся к прямой записи списка как запасному способу, если уже включён CLI-протокол. Не пересоздавай папки, ROADMAP или mutex при обновлении. Если инструкции SOV изменились, оцени влияние на незавершённые задачи, маршруты, имеющиеся артефакты и критерии завершения; зафиксируй необходимые действия в материалах каждой затронутой задачи до продолжения. Повтори проверки из пункта 6, включая worktree и исключение `.sov/`. Одной установки бинарника недостаточно для переключения протокола задач или разрешения параллельных координаторов.

## Планируемая структура

`skills/` предназначен для исходников скилов SOV, `.opencode/commands/` — для команд среды OpenCode, `templates/` содержит заготовки локальных артефактов. Продуктовые требования и решения будут размещаться в `docs/specs/` и `docs/adrs/`, правила разработки — в `rules/`.
