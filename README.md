# SOV

SOV — проект набора взаимосвязанных Agent Skills и шаблонов артефактов для разработки с агентами в средах типа OpenCode. Цель, границы и предполагаемый порядок работы описаны в [спецификации принципов работы](docs/sov-spec.md). Контракты и шаблоны артефактов подготовлены; исходные инструкции всех скилов, включая `sov-orchestrator`, находятся в [`skills/`](skills/README.md). Доступна инструкция ручного подключения к проекту; сквозная проверка маршрутов SOV пока не проведена.

## Установка и обновление в существующем проекте (для агента)

Эта процедура подключает SOV к **целевому** проекту с Git и OpenCode без установщика. Сначала прочитай его `AGENTS.md`, `rules/index.md`, `docs/index.md` (если они есть), проверь текущие изменения и согласуй с владельцем проекта недостающие решения. Не копируй `AGENTS.md`, `rules/` или `docs/` **этого** репозитория как правила целевого проекта. Инструкции шагов находятся в [`skills/`](skills/README.md), артефакты — в [`templates/`](templates/README.md), команды — в [`.opencode/commands/`](.opencode/README.md).

### Первое подключение

1. Запиши абсолютные пути к основной папке целевого проекта (`<project>`) и к установленной, доступной агенту папке исходников SOV (`<sov>`), а также версию SOV (commit или release). Выбери и явно зафиксируй способ подключения ресурсов: например, общую постоянную папку `<sov>` для всех worktree; не ссылайся на относительный путь из основной копии, недоступный из worktree. Проверь наличие `skills/*/SKILL.md`, `templates/ROADMAP.md`, `templates/task.md` и трёх файлов команд в `<sov>`. Проверь `git`, OpenCode, а для публикации через GitHub — `gh`, доступ к remote, права чтения ресурсов, записи в основную папку и создания worktree. Если необходимый инструмент или доступ отсутствует, сообщи о препятствии, не объявляй установку законченной.
2. Подключи все папки скилов SOV к OpenCode. Например, добавь **к существующему** `opencode.json` проекта (или `.opencode/opencode.json`) путь к `<sov>/skills` в `skills.paths`, сохранив другие настройки и пути:

   ```json
   {
     "$schema": "https://opencode.ai/config.json",
     "skills": { "paths": ["/абсолютный/путь/к/sov/skills"] }
   }
   ```

   Это пример для нового файла, а не команда заменить существующий JSON. Скопируй [`sov.md`](.opencode/commands/sov.md), [`sov-feature.md`](.opencode/commands/sov-feature.md) и [`sov-bug.md`](.opencode/commands/sov-bug.md) в `<project>/.opencode/commands/`, сравнивая одноимённые файлы до замены. Команды проектные и должны быть доступны также в worktree (обычно они отслеживаются Git). Если в проекте уже есть команды с такими именами или скилы SOV из другой установки, остановись и согласуй, какие использовать. После изменения конфигурации перезапусти OpenCode: работающая сессия не обязана подхватить новые файлы.
3. Выбери источник задач явно. В первой версии `sov-tasks` поддерживает файловый `<project>/.sov/ROADMAP.md`; CLI допустим **только** при реализованном подключении в `sov-tasks` и подтверждённой доступности. Установленный CLI сам по себе недостаточен: если запрошен неподдерживаемый CLI, сообщи об ограничении и предложи явно выбрать файловый источник вместо молчаливого переключения. Добавь `.sov/` в корневой `.gitignore` и проверь исключение с помощью `git check-ignore .sov/ROADMAP.md`; при наличии уже отслеживаемых файлов `.sov/` согласуй их удаление из индекса отдельно. Для выбранного файлового источника при отсутствии списка создай его из [`templates/ROADMAP.md`](templates/ROADMAP.md), предварительно выбрав постоянный префикс ID; существующий список не заменяй. Подготовь `<project>/.sov/tasks/` и `<project>/.sov/worktree/` как локальные папки основной копии. Не создавай второй список задач внутри worktree.
4. В существующих `AGENTS.md` и применимых `rules/` целевого проекта запиши **принятые проектом** правила: абсолютный путь к основной папке и ресурсу SOV (либо воспроизводимый способ их определения), версию ресурсов, файловый источник задач, префикс ID, целевую ветку и правила публикации, ссылки на `rules/index.md` и `docs/index.md`. Укажи, что перед работой агент читает применимые правила и опубликованные требования в `docs/`; технический план их не заменяет. Явно выбери с владельцем и зафиксируй профиль Open Knowledge Format: расположение спецификаций, ADR и правил, метаданные и индексы для каждого типа документов; существующие файлы не устанавливают профиль автоматически. Если `AGENTS.md`, `rules/`, `docs/` или индексов ещё нет, создай только согласованные с проектом документы и ссылки, не подставляя текст SOV вместо его правил. При конфликте с действующими правилами остановись и получи решение владельца.
5. Проверь доступ из **основной копии и пробной worktree**: OpenCode после перезапуска видит все скилы и `/sov`, `/sov-feature`, `/sov-bug`; агент может прочитать шаблон из `<sov>/templates/`, общий `<project>/.sov/ROADMAP.md` и папку артефактов основной копии, а также создать/прочитать пробный артефакт в `<project>/.sov/tasks/`. Проверь, что путь к ресурсам и разрешение OpenCode на внешние каталоги действуют и из worktree; при отказе доступа настрой разрешение в проекте/среде по согласованию, не отключая проверки ради успеха. Проверь исключение `.sov/` и отсутствие её в составе коммита. Удали пробную worktree штатно после проверки сохранности данных; не заменяй ею рабочую копию уже выполняемой задачи.

При создании задачи `sov-tasks` берёт список из **основной** папки, а оркестратор создаёт `.sov/tasks/<ID>/` и передаёт её абсолютный путь исполнителям. Файлы `task.md`, `plan.md`, `checks.md` и другие копируются из `templates/` только по необходимости выбранного маршрута и заполняются фактическим содержанием. Код и постоянные `docs/`/`rules/` читаются из worktree задачи; общие артефакты не дублируются. Согласованные требования сохраняются в `docs/specs/`, решения — в `docs/adrs/` и правилах целевого проекта по принятому профилю.

### Повторная установка и обновление

Сначала сравни установленную версию, конфигурацию, команды, пути, `AGENTS.md`, `rules/`, `docs/`, `.gitignore`, список и локальные артефакты с предлагаемыми изменениями. Запиши используемый источник и версию ресурсов SOV (например, commit или release) в правилах проекта. Обновляй подключённый источник и только выбранные файлы, сохраняя пользовательские правки; ничего не перезаписывай молча и не создавай повторно папки/список. При конфликте названий, содержания или способов подключения согласуй решение до изменения. Если инструкции SOV изменились, оцени влияние на незавершённые задачи, маршруты, имеющиеся артефакты и критерии завершения; зафиксируй необходимые действия в материалах каждой затронутой задачи до продолжения. Повтори проверки из пункта 5, включая worktree, исключение `.sov/` и перезапуск OpenCode после изменения его файлов. Если проверка не прошла, сохрани прежнюю работоспособную установку и зафиксируй препятствие.

## Планируемая структура

`skills/` предназначен для исходников скилов SOV, `.opencode/commands/` — для команд среды OpenCode, `templates/` содержит заготовки локальных артефактов. Продуктовые требования и решения будут размещаться в `docs/specs/` и `docs/adrs/`, правила разработки — в `rules/`.
