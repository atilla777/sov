# SOV

SOV — проект набора взаимосвязанных Agent Skills и шаблонов артефактов для разработки с агентами в средах типа OpenCode. Цель, границы и предполагаемый порядок работы описаны в [спецификации принципов работы](docs/sov-spec.md). Контракты и шаблоны артефактов подготовлены; исходные инструкции всех скилов, включая `sov-orchestrator`, находятся в [`skills/`](skills/README.md). Доступна инструкция ручного подключения к проекту; основные маршруты и ограничения проверены на отдельном пробном проекте.

## Установка и обновление в существующем проекте (для агента)

Эта процедура подключает SOV к **целевому** проекту с Git и OpenCode без установщика. Сначала прочитай его `AGENTS.md`, `rules/index.md`, `docs/index.md` (если они есть), проверь текущие изменения и согласуй с владельцем проекта недостающие решения. Не копируй `AGENTS.md`, `rules/` или `docs/` **этого** репозитория как правила целевого проекта. Инструкции шагов находятся в [`skills/`](skills/README.md), артефакты — в [`templates/`](templates/README.md), команды — в [`.opencode/commands/`](.opencode/README.md).

### Первое подключение

1. Запиши абсолютные пути к основной папке целевого проекта (`<project>`) и к установленной, доступной агенту папке исходников SOV (`<sov>`), а также версию SOV (commit или release). Выбери и явно зафиксируй способ подключения ресурсов: например, общую постоянную папку `<sov>` для всех worktree; не ссылайся на относительный путь из основной копии, недоступный из worktree. Закрепи один checkout/release SOV для `skills/`, `templates/`, `.opencode/commands/` и `cli/sov-state/` вместе; не собирай CLI из другого checkout или меняющегося `main`. Проверь наличие `skills/*/SKILL.md`, `templates/ROADMAP.md`, `templates/task.md`, трёх файлов команд и исходников CLI в `<sov>`. Проверь Linux, Go по [`go.mod`](cli/sov-state/go.mod) (сейчас Go 1.25.4 или совместимая более новая версия), `git`, OpenCode, а для публикации через GitHub — `gh`, доступ к remote, права чтения ресурсов, записи в основную папку и создания worktree. Если необходимый инструмент или доступ отсутствует, сообщи о препятствии, не объявляй установку законченной.
2. Подключи все папки скилов SOV к OpenCode. Например, добавь **к существующему** `opencode.json` проекта (или `.opencode/opencode.json`) путь к `<sov>/skills` в `skills.paths`, сохранив другие настройки и пути:

   ```json
   {
     "$schema": "https://opencode.ai/config.json",
     "skills": { "paths": ["/абсолютный/путь/к/sov/skills"] }
   }
   ```

   Это пример для нового файла, а не команда заменить существующий JSON. Скопируй [`sov.md`](.opencode/commands/sov.md), [`sov-feature.md`](.opencode/commands/sov-feature.md) и [`sov-bug.md`](.opencode/commands/sov-bug.md) в `<project>/.opencode/commands/`, сравнивая одноимённые файлы до замены. Команды проектные и должны быть доступны также в worktree (обычно они отслеживаются Git). Если в проекте уже есть команды с такими именами или скилы SOV из другой установки, остановись и согласуй, какие использовать. После изменения конфигурации перезапусти OpenCode: работающая сессия не обязана подхватить новые файлы. Проверь отдельно разрешение OpenCode на чтение каталога `<sov>` **из основной копии и worktree**: обнаружение скила через `skills.paths` ещё не означает доступ к соседним шаблонам или исходникам. При отказе в чтении добавь к существующей конфигурации узкое разрешение `permission.external_directory` для согласованного абсолютного пути `<sov>/**` (например, `"/путь/к/sov/**": "allow"`), перезапусти OpenCode и повтори проверку; не открывай без необходимости все внешние каталоги.
3. Выбери источник задач явно. Файловый источник `<project>/.sov/ROADMAP.md` работает через установленный и проверенный `sov-state`; иной CLI/API допустим **только** при реализованном подключении в `sov-tasks` и подтверждённой доступности. Установленный бинарник сам по себе не переключает старый проект; при неподдерживаемом источнике сообщи о препятствии вместо молчаливого переключения. Добавь `.sov/` в корневой `.gitignore` и проверь исключение с помощью `git check-ignore .sov/ROADMAP.md`; при наличии уже отслеживаемых файлов `.sov/` согласуй их удаление из индекса отдельно. Для файлового источника **только при первом подключении и до начала работы писателей** создай отсутствующий список из [`templates/ROADMAP.md`](templates/ROADMAP.md), предварительно выбрав постоянный префикс ID; существующий список не заменяй. После инициализации все штатные изменения списка — только через `sov-tasks` и CLI, без прямой записи из установки. При обновлении отсутствие прежде существовавшего списка означает возможную утрату состояния, а не пустую очередь: не создавай новый список автоматически. Подготовь `<project>/.sov/tasks/` и `<project>/.sov/worktree/` как локальные папки основной копии. Не создавай второй список задач внутри worktree.
4. В существующих `AGENTS.md` и применимых `rules/` целевого проекта запиши **принятые проектом** правила: абсолютный путь к основной папке и ресурсу SOV (либо воспроизводимый способ их определения), версию ресурсов, файловый источник задач, префикс ID, **устойчивый идентификатор исполнителя, одинаковый для его новых сессий** (для независимых исполнителей — разные постоянные ID и способ определения текущего), целевую ветку и правила публикации, ссылки на `rules/index.md` и `docs/index.md`. Для файлового протокола обязательно запиши абсолютный путь к одному бинарнику и один `state-dir=<project>/.sov` основной копии, одинаковый в каждой worktree; не вычисляй их относительно текущей worktree или из случайного `PATH`. Сеансы с одним ID не могут безопасно одновременно выбирать или продолжать одну задачу. Не используй ID сессии как единственное назначение задачи; при смене устойчивого исполнителя существующие назначения переносит `sov-tasks` только по явному решению с фиксацией причины. Укажи, что перед работой агент читает применимые правила и опубликованные требования в `docs/`; технический план их не заменяет. Явно выбери с владельцем и зафиксируй профиль Open Knowledge Format: расположение спецификаций, ADR и правил, метаданные и индексы для каждого типа документов; существующие файлы не устанавливают профиль автоматически. Если `AGENTS.md`, `rules/`, `docs/` или индексов ещё нет, создай только согласованные с проектом документы и ссылки, не подставляя текст SOV вместо его правил. При конфликте с действующими правилами остановись и получи решение владельца.
5. Проверь доступ из **основной копии и пробной worktree**: OpenCode после перезапуска видит все скилы и `/sov`, `/sov-feature`, `/sov-bug`; агент может прочитать шаблон из `<sov>/templates/`, общий список через `sov-state read --state-dir <project>/.sov` и папку артефактов основной копии, а также создать/прочитать пробный артефакт в `<project>/.sov/tasks/`. Проверь, что путь к ресурсам и разрешение OpenCode на внешние каталоги действуют и из worktree; при отказе доступа настрой разрешение в проекте/среде по согласованию, не отключая проверки ради успеха. До включения писателей проверь совместимый бинарник, mutex и no-op commit по процедуре ниже. Проверь исключение `.sov/` и отсутствие её в составе коммита. Удали пробную worktree штатно после проверки сохранности данных; не заменяй ею рабочую копию уже выполняемой задачи.

### Подготовка общего бинарника `sov-state` (Linux)

Это обязательный шаг поставки перед включением файлового протокола в `sov-tasks` целевого проекта. Требуется локальная ФС с `flock`, атомарным `rename` и `fsync`, существующий обычный `<project>/.sov/ROADMAP.md` (не symlink и не hardlink), право чтения списка и записи в `.sov/`. Отсутствующий при обновлении ROADMAP не восстанавливай из шаблона. Выбери `<sov>/bin/sov-state` как общий абсолютный путь; если `<sov>` недоступен для записи, заранее согласуй **один** другой абсолютный каталог для бинарника. Не клади копии в worktree. Для сборки и проверки кандидата из того же закреплённого `<sov>`:

```sh
mkdir -p "<sov>/bin"                    # либо заранее выбранный каталог
sh "<sov>/cli/sov-state/build-candidate.sh" "<sov>/bin/.sov-state-next"
"<sov>/bin/.sov-state-next" --version
```

Скрипт требует Go, собирает временный файл в каталоге назначения, сверяет `--version` с `sov-state 0.1.0 (protocol v:1)` и публикует только целого кандидата; при ошибке не трогает установленный бинарник. При иной закреплённой версии SOV сверяй ожидаемые версии скрипта, исходников, скилов и команд **до** обновления; несовпадение — повод остановиться, а не игнорировать проверку. На время замены останови старых писателей. До публикации кандидата проверь его исполняемость и JSON `v:1`, `status:ok`, `resource:ROADMAP.md` командой `read --state-dir "<project>/.sov"` из основной копии и двух пробных worktree: абсолютные пути CLI и `state-dir` должны быть **теми же**, `revision` и `content_base64` — совпадать. Проверь разрешение OpenCode из обеих копий на запуск бинарника и доступ к внешнему каталогу состояния (и на запись в него для будущего `commit`); для внешнего каталога при необходимости согласуй узкое `permission.external_directory` на `<project>/.sov/**` так же, как для `<sov>/**`. Не считай запуск из терминала доказательством разрешения OpenCode.

Для первого включения протокола, **до** проверки `commit`, создай постоянный `<project>/.sov/.roadmap.lock` с mode `0600` только если его ещё нет: при отсутствии файла и symlink выполни `(umask 077; set -C; : > "<project>/.sov/.roadmap.lock")`; если исключающее создание не удалось, остановись и проверь причину. При существующем файле проверь, что он обычный, не symlink/hardlink, и сохрани его inode. При обновлении не удаляй и не заменяй mutex. С остановленными писателями проверь read/commit-права кандидата без изменения списка: скопируй ROADMAP в отдельный входной файл, возьми `revision` из нового `read`, выполни `commit --state-dir "<project>/.sov" --expected <revision> --input <абсолютный-путь-к-копии>`; ожидается `status:ok`, `changed:false` и прежний revision. Повтори из другой worktree, предварительно перечитав список; проверь один и тот же inode mutex и одинаковый список после проверок. Не запускай такой `commit` на проекте со старым активным писателем. После успешных проверок опубликуй кандидата атомарным `mv` **в том же каталоге** на выбранный абсолютный путь `sov-state`; ещё раз проверь `--version` и `read` из основной копии и worktree. Если после замены проверка не прошла, восстанови сохранённый прежний бинарник до возобновления писателей и разбери препятствие. Включение нового `sov-tasks` требует отдельного обновления инструкций и сессий при остановленных писателях; само наличие бинарника не разрешает параллельных координаторов.

После остановки или обновления всех старых писателей и проверки нового CLI включи файлы `sov-tasks` и команд из одной версии SOV, перезапусти OpenCode. При создании задачи `sov-tasks` читает и условно обновляет список из **основной** папки через CLI, а оркестратор после подтверждённой записи создаёт `.sov/tasks/<ID>/` и передаёт её абсолютный путь исполнителям. При прерывании между этими действиями он сверяет строку и папку и завершает недостающее, не создавая дубликат. В новой сессии `/sov` без аргументов сначала ищет в общем списке задачи `in_progress` и `blocked`, назначенные этому устойчивому исполнителю: одну продолжает после сверки артефактов и Git/PR (для `blocked` сообщает препятствие), при нескольких просит ID; лишь при отсутствии таких задач выбирает новую `planned`. Файлы `task.md`, `plan.md`, `checks.md` и другие копируются из `templates/` только по необходимости выбранного маршрута и заполняются фактическим содержанием. Код и постоянные `docs/`/`rules/` читаются из worktree задачи; общие артефакты не дублируются. Согласованные требования сохраняются в `docs/specs/`, решения — в `docs/adrs/` и правилах целевого проекта по принятому профилю. До сквозной проверки параллельного режима действует один координатор.

### Повторная установка и обновление

Сначала сравни установленную закреплённую версию, бинарник, конфигурацию, скилы, команды, пути, `AGENTS.md`, `rules/`, `docs/`, `.gitignore`, список и локальные артефакты с предлагаемыми изменениями; сравни пользовательские правки каждого обновляемого файла. Запиши используемый источник и версию ресурсов SOV (commit или release) в правилах проекта. Перед использованием поиска по устойчивому исполнителю проверь действующие назначения: если они основаны на ID прежних сессий, выясни владельца каждой незавершённой задачи и перенеси назначение через `sov-tasks` только по явному решению с причиной в `task.md`; до разрешения таких назначений не считай отсутствие собственных задач основанием начать следующую `planned`.

Подготовь новый **отдельный закреплённый** checkout SOV и сверь версию бинарника/контракт `v:1` со скилами и командами этой версии до переключения конфигурации; не обновляй checkout на месте, пока его используют старые сессии. Останови старых писателей на согласованное окно; сборку и проверки кандидата из раздела выше выполни **до** замены действующего бинарника и инструкций. При ошибке сборки или несовместимости кандидат удаляется, прежний бинарник, источник и инструкции остаются рабочими. Сохрани прежний бинарник отдельной копией перед атомарной заменой, не подменяя файл mutex и ROADMAP. Обновляй только выбранные файлы и пути к ресурсам вместе с версиями в правилах проекта, сохраняя пользовательские правки; при конфликте согласуй решение. До допуска новых писателей проверь исполняемость, контракт `v:1`, read и no-op commit через **тот же** `state-dir` и mutex из основной копии и двух worktree, разрешения OpenCode на доступ и запуск, скилы и команды после перезапуска. Если проверка после переключения не прошла, верни прежние бинарник, конфигурацию и инструкции при остановленных писателях; зафиксируй препятствие. Никогда не возвращайся к прямой записи списка как запасному способу, если уже включён CLI-протокол. Не пересоздавай папки, ROADMAP или mutex при обновлении. Если инструкции SOV изменились, оцени влияние на незавершённые задачи, маршруты, имеющиеся артефакты и критерии завершения; зафиксируй необходимые действия в материалах каждой затронутой задачи до продолжения. Повтори проверки из пункта 5, включая worktree и исключение `.sov/`. Одной установки бинарника недостаточно для переключения протокола задач или разрешения параллельных координаторов.

## Планируемая структура

`skills/` предназначен для исходников скилов SOV, `.opencode/commands/` — для команд среды OpenCode, `templates/` содержит заготовки локальных артефактов. Продуктовые требования и решения будут размещаться в `docs/specs/` и `docs/adrs/`, правила разработки — в `rules/`.
