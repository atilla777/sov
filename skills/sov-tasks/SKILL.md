# Учёт задач SOV

Этот скил — единственный интерфейс к общему списку задач. Оркестратор и скилы шагов запрашивают у него задачу и состояние, но не читают и не редактируют источник списка напрямую. Здесь ведутся только идентификатор, название, статус, назначение, зависимости, порядок и признак необходимости публикации. Запрос, маршрут, причины блокировки, проверки и подтверждение публикации сохраняются оркестратором в `.sov/tasks/<task-id>/task.md`, а не копируются как второй общий статус. Артефактами и worktree этот скил не управляет.

## Источник и адресация

1. Получи абсолютный путь к **основной** папке проекта, явно выбранный источник, закреплённую версию SOV, абсолютные пути к `sov-state` и `state-dir=<основная папка>/.sov`, а также выбранный для этого поручения устойчивый ID исполнителя из `AGENTS.md` / применимых правил. При нескольких слотах проекта не выбирай ID по ID сессии, текущей worktree или найденной задаче: вызывающий оркестратор должен определить слот до поиска, создания, назначения и продолжения. При неясном ID сообщи о препятствии и запроси выбор, не угадывай владельца по строкам списка. Не выводи общую папку из текущего каталога worktree. Для файлового источника используй только CLI этой же версии SOV после проверки `--version` (в этой версии `sov-state 0.2.0`, протокол `v:1`), исполняемости, `read` и `read-archive` из текущей рабочей копии. Если настройка или инструмент недоступны, остановись: не переходи на прямую запись и не создавай другой список. В уже подключённом проекте работа старых сессий по прежним инструкциям должна быть остановлена до переключения писателей; процедура — в [`README.md`](../../README.md#подготовка-общего-бинарника-sov-state-linux).
2. CLI `sov-state` — байтовый транспорт **существующих** файлов списка и архива, а не другой источник задач и не исполнитель семантических проверок. При отсутствии любого файла выясни, первое ли это подключение или утрата состояния: при первом подключении установка создаёт список из [`templates/ROADMAP.md`](../../templates/ROADMAP.md), архив из [`templates/ARCHIVE.md`](../../templates/ARCHIVE.md) и постоянный mutex при остановленных писателях. Обновление прежнего файлового источника без архива — отдельный этап установки при остановленных писателях; не создавай архив молча при обычной работе. Если проект выбрал иной неподключённый CLI/API, сообщи о препятствии, не подменяя выбранный источник файловым.
3. Передай вызывающему агенту запись задачи и абсолютный путь `<основная папка>/.sov/tasks/<task-id>/`. Папку при начале сохраняемой работы создаёт оркестратор. Стабильный ID — ключ к папке и внешним ссылкам; после создания его нельзя переименовывать или выдавать повторно.

## Формат файлового списка

Формат и пустые образцы — в [`templates/ROADMAP.md`](../../templates/ROADMAP.md) и [`templates/ARCHIVE.md`](../../templates/ARCHIVE.md). В поле `Следующий ID` записан очередной свободный номер с постоянным префиксом проекта; новые задачи добавляются **в конец** ROADMAP, после чего номер увеличивается. Удаление, отмена или завершение задачи не освобождают ID. Физический порядок строк ROADMAP определяет очередь; не сортируй таблицу при редактировании. ID уникален между файлами (временно одинаковая **полностью совпадающая** строка допустима только при прерванной архивации). ID и название непустые. В ARCHIVE только `done` и `cancelled`, без счётчика ID; его строки не выбираются в очередь. Статус ROADMAP — ровно один из `planned`, `in_progress`, `blocked`, `done`, `cancelled`; исполнитель — устойчивый идентификатор из правил проекта или `—`, не ID текущей сессии; зависимости — уникальные ID через запятую либо `—`; публикация — `yes` или `no` (определяется поручением и правилами проекта при создании). Не подменяй признак публикации статусом PR.

Перед любой выдачей, выбором и изменением получи `content_base64` и `revision` через `sov-state read` и `sov-state read-archive --state-dir <абсолютный state-dir>`, декодируй bytes и проверь оба файла: уникальность ID, номер `Следующий ID` больше всех уже выданных номеров с тем же префиксом, допустимость полей, ссылки зависимостей строк ROADMAP **только на строки ROADMAP**, отсутствие зависимости от себя и циклов. В архиве допускаются ссылки на архивные и оставшиеся ID для сохранения истории; архивные строки не участвуют в проверке доступности. Если ID присутствует в обоих файлах, разрешено только полное совпадение терминальных строк без входящих ссылок из остающегося ROADMAP: это прерванный перенос, сначала доведи его до конца по процедуре ниже. Любое иное расхождение — препятствие; не выбирай и не меняй задачи, сообщи конкретные строки. Отсутствие ответа `read` не означает пустой список. Результаты чтения — снимки, а не общая транзакция; перед назначением и любым изменением заново читай оба файла и проверяй состояние. Разные независимые одновременные координаторы, даже одного разработчика, обязаны иметь **разные устойчивые ID** из правил проекта; две сессии с одним ID не должны параллельно выбирать, создавать, продолжать или менять задачи от его имени. Для каждого целевого проекта параллельных координаторов допускай только после [контролируемого включения](../../docs/parallel-activation.md) с остановкой старых писателей и проверкой общей установки.

## Условная запись файлового источника

Для **каждого** изменения (создание и выдача ID, назначение, освобождение/смена исполнителя, блокировка и возобновление, статус и публикация, название, зависимости, перестановка строк/приоритет) выполни полный цикл:

1. Выполни `sov-state read --state-dir <абсолютный state-dir>` через зафиксированный **абсолютный путь к бинарнику**. Убедись в `status:ok`, `v:1`, `resource:ROADMAP.md`; декодируй `content_base64` без изменения bytes и проверь весь список и внешние предусловия конкретной операции. Для `done` с `Публикация = yes` повторно проверь фактическое слияние PR, а не только запись в артефакте.
2. Собери полную новую версию из **этого** снимка в отдельном обычном локальном файле папки задачи или отдельном временном каталоге сессии (для создания до выдачи ID — каталог сессии). Не редактируй существующий `ROADMAP.md` напрямую и не используй его, `.roadmap.lock` или hardlink на них в качестве `--input`. Сохрани не затронутые строки и их порядок; проверь результирующий список и внешние условия. Удаляй только собственные временные файлы после выяснения исхода операции.
3. Вызови `sov-state commit --state-dir <абсолютный state-dir> --expected <revision из read> --input <абсолютный путь к новой версии> --lock-timeout 5s`. Только `status:ok` при exit 0 подтверждает изменение. При `changed:false` проверь на свежем чтении требуемый смысловой результат: no-op сам по себе не выдаёт ID и не доказывает назначение. Верни вызывающему агенту подтверждённые поля, а не предполагаемый исход.
4. При `revision_conflict` (exit 10) перечитай список, заново проверь все предусловия и **пересобери** файл, в том числе ID, порядок и зависимости; замена одного `--expected` недопустима. Не более трёх попыток `commit` на операцию, включая первую, с коротким ограниченным случайным ожиданием между конфликтами. Если предпосылки изменились (например, задача назначена другому), пересмотри выбор или остановись. После трёх конфликтов сохрани контекст и сообщи препятствие; бесконечных повторов нет. При `lock_timeout` (exit 11) остановись либо один раз повтори полный цикл после нового чтения/проверки в пределах общего лимита трёх попыток. `invalid_input` (12) и обычный `io_error` (13) требуют устранения причины, а не обхода CLI.

Таймаут процесса, потеря stdout, неполный/непонятный ответ или `may_have_committed:true` означают **неопределённый исход**. Прочитай свежий список через CLI и проверь именно нужный эффект: ID, название/контекст, исполнитель, статус, зависимости и другие затронутые поля. Если результат подтверждён, сверь необходимые артефакты и продолжи без второго commit; если он не подтверждён, заново проверь предпосылки и начинай полный цикл; при чужой правке или неразличимых результатах остановись. Для создания заранее сохрани контекст намерения в локальных материалах поручения: одинаковые строки разных создателей не позволяют надёжно опознать свой ID; не создавай вторую задачу при такой неопределённости. Хеш bytes сам по себе не доказывает семантический результат. Исправление повреждённого списка — отдельная контролируемая процедура обслуживания при остановленных писателях, а не ручная запись в обход CLI.

### Архивация терминальных строк

После подтверждённого перевода в `done` или `cancelled`, после изменения зависимостей, а также при первой штатной операции после обновления установки найди в ROADMAP строки с терминальным статусом, на которые **не ссылается ни одна остающаяся строка** (включая другие терминальные). Выбери такие строки, удали их из новой версии ROADMAP и добавь в конец ARCHIVE без изменения полей и порядка остальных строк; повтори выбор для освободившихся терминальных строк, пока кандидатов нет. Оставь `Следующий ID` неизменным. Статус и доказательство публикации подтверждаются **до** архивации, не в её ходе. Архивные строки не становятся доступными зависимостями для новых задач; при попытке сослаться на архивный ID остановись и предложи пересмотреть замысел зависимости. Папку `.sov/tasks/<ID>/` не удаляй.

Для переноса используй только `sov-state archive --state-dir <state-dir> --expected <revision ROADMAP> --input <новый ROADMAP> --archive-expected <revision ARCHIVE> --archive-input <новый ARCHIVE> --lock-timeout 5s`. Оба входа — отдельные локальные файлы, собранные из свежих снимков; заранее проверь, что каждая перенесённая строка есть ровно в одном месте новой пары файлов, ни один ID не потерян и оставшиеся зависимости указывают на ROADMAP. CLI под одним mutex проверяет оба revision, **сначала публикует ARCHIVE**, затем ROADMAP; семантику Markdown он не проверяет. При конфликте любого файла повтори чтение, проверки и сборку обоих файлов с лимитом трёх попыток. При ошибке или потерянном ответе перечитай оба файла: если строка есть и там и там в точности одинаковая, а ссылок из оставшейся очереди на неё нет, повтори перенос с уже существующей архивной строкой, не добавляя её повторно; если только в архиве — перенос завершён; если только в ROADMAP — повтори с нового снимка после проверки условий. При расхождении строк или новой зависимости не угадывай исход: остановись. До разрешения дублирующей строки не выполняй другие изменения списка. Операция не является атомарной для читателей двух файлов: они обязаны распознавать и завершать допустимый промежуточный дубликат; строка никогда не исчезает из обоих файлов. Не удаляй ARCHIVE и не создавай его заново ради восстановления.

## Операции

- **Получить**: по ID верни все поля строки ROADMAP, её место в очереди, а также вычисленную доступность и причину недоступности; для архивного ID верни его поля и указание, что он вне очереди. При отсутствии в обоих файлах явно сообщи об этом; не выдавай новый ID вместо отсутствующего.
- **Найти для продолжения**: верни все строки `in_progress` и `blocked`, у которых исполнитель совпадает с **выбранным ID слота** из правил проекта, вместе с их ID, статусом и путями артефактов. Не расширяй поиск на другие слоты того же человека и не ограничивай его текущей сессией; `done` и `cancelled` не являются незавершёнными задачами. При одном совпадении верни его; при нескольких верни все ID для выбора человеком без автоматического назначения; при нуле явно сообщи об этом для последующего выбора следующей `planned`. При обновлении установки сначала проверь, не остались ли назначения по прежним ID сессий: пока их владельцы не выяснены, не считай ноль совпадений доказательством отсутствия собственной работы. Задача с другим исполнителем, включая другой слот того же разработчика или прежний ID сессии, не становится своей автоматически: смена назначения требует явного решения с причиной в `task.md`.
- **Создать**: уточни название, необходимость публикации и зависимости; убедись, что ID зависимостей существуют и нет цикла. На свежем снимке возьми `Следующий ID`, добавь строку с `planned`, исполнителем `—`, выбранными зависимостями и публикацией; увеличь номер. Верни ID и путь к папке артефактов только после подтверждения записи, не создавая саму папку. При конфликте пересчитай ID на новом снимке; после неоднозначного исхода не создавай дубликат. Новые задачи реализации, зависящие от подготовки требований, остаются `planned` до подтверждённой публикации требований.
- **Выбрать следующую**: просматривай строки по порядку и верни первую задачу со статусом `planned`, исполнителем `—`, зависимостями только в `done` и выполненными условиями начала работы. Для новой функциональности проверь опубликованные требования; для исправления бага — определённость ожидаемого поведения или предусмотренное начальное согласование через `sov-spec`. Отдельная опубликованная спецификация не требуется для однозначного бага без противоречия опубликованным источникам. Не требуй готового исследования или плана до начала задачи, которая их создаёт; до реализации пригодность этих результатов проверяет оркестратор. Зависимость `cancelled` **не** выполнена; `blocked`, `planned` и `in_progress` также не выполнены. Если нет доступной, сообщи, пуст ли список либо какие зависимости, назначения или условия мешают; не снимай блокировки для продолжения работы.
- **Назначить / начать**: назначай доступную `planned` задачу выбранному устойчивому ID слота из правил проекта и одновременно переводи в `in_progress`. До подтверждённого commit **не** начинай работу, не создавай worktree и не меняй артефакты задачи. Для явно указанного `planned` ID применяй те же условия начала, что для выбора следующей; при конфликте повторно проверь доступность и чужое назначение, выбери другую доступную задачу либо остановись. Для уже назначенной выбранному слоту `in_progress` возвращай текущее состояние для продолжения без повторного назначения, а при `blocked` возвращай препятствие без автоматического перехода в `in_progress`. Не забирай задачу с другим исполнителем, даже если это другой слот того же человека или сессия оборвалась; смена исполнителя или освобождение назначения требует явного решения с фиксацией причины в `task.md`.
- **Обновить**: меняй только явно запрошенные поля строки ROADMAP после проверки текущего статуса и последствий для зависимых задач; архивные строки не обновляй как действующие задачи. Добавление зависимости не должно создавать цикл или делать текущую работу недопустимой без решения оркестратора. При `blocked` сохраняй исполнителя и требуй от оркестратора указать причину и условие снятия блокировки в `task.md`; возвращай в `in_progress` только после устранения препятствия. `cancelled` не переводится в `done` автоматически, а отменённые зависимости требуют отдельного решения. `done` требует достигнутого результата, обязательных проверок и отсутствия блокирующих замечаний; для строки с `Публикация = yes` дополнительно проверь подтверждённое слияние PR в целевую ветку по сведениям оркестратора (`task.md` и фактическое состояние GitHub). Созданный PR, push ветки и готовность к слиянию недостаточны. Если проект согласовал иной маршрут публикации, противоречащий требованию PR в спецификации SOV, не отмечай задачу `done` без разрешения этого противоречия.

После каждого подтверждённого изменения верни вызывающему агенту прежнее и новое состояние, ID, путь артефактов и результат проверки списка. Список и `task.md` не являются одной транзакцией: при создании сначала подтверди строку списка, затем оркестратор создаёт папку и `task.md`; при `done` сначала сохрани в `task.md` доказательство публикации и сверь GitHub, затем запиши статус. При возобновлении выясни фактическое состояние обоих источников и закончи недостающее действие, не выдавая локальный текст за второй общий статус.

## Самопроверка сценариев

На копиях обоих образцов проверь: два создания дают разные ID; два исполнителя пытаются назначить одну задачу — только победитель начинает; изменение разных строк, перестановка и зависимости после конфликта пересобираются без потери чужих правок; цикл, `cancelled`-зависимость и `done` до слияния PR отклоняются; три конфликта дают остановку, а потерянный ответ проверяется чтением без слепого повтора. Проверь также продолжение `in_progress`/`blocked` новым сеансом своего устойчивого ID, неоднозначность нескольких задач, отсутствие доступных задач и восстановление папки/`task.md` после подтверждённого создания. Для двух слотов одного разработчика проверь: поиск по одному не возвращает задачу другого; явный ID задачи с чужим назначением не даёт её продолжить; без выбранного слота нет создания, назначения и продолжения; две одновременные сессии под одним ID не допускаются даже для разных задач. Для архивирования проверь цепочку `TASK-001 done → TASK-002 planned → TASK-003 planned`: TASK-001 остаётся в ROADMAP, пока на неё ссылается TASK-002; после удаления зависимости TASK-001 переносится в ARCHIVE, но TASK-002 и TASK-003 остаются в очереди. Проверь, что `cancelled` не разблокирует зависимость, а цепочка терминальных задач переносится после удаления последней входящей зависимости; `Следующий ID` сохраняется и выдаёт новый ID без повторения архивных. Смоделируй дубликат идентичной строки в двух файлах после прерывания между публикациями: восстановление удаляет её только из ROADMAP; различающиеся строки, ссылка из ROADMAP на архивный ID и отсутствие архива останавливают работу. Два параллельных переноса с одним revision дают один успех, затем проигравший пересобирает оба файла из новых снимков. При наличии проекта с фактическим списком не заменяй его образцами ради проверки.
