# Учёт файловых задач SOV

Этот скил — интерфейс оркестратора к [файловому протоколу задач](../../docs/specs/filesystem-tasks.md). Задачи хранятся в общей `.sov/` **основной** папки целевого проекта; относительный путь из worktree не подходит. Скил определяет смысл операции, CLI [`sov-task`](../../cli/sov-task/README.md) выполняет файловые действия и проверяет свои инварианты. Остальные скилы получают состояние через `sov-tasks`, а не ведут отдельный список. Установленный целевой проект использует этот маршрут только после отдельного переключения по [инструкции](../../docs/install-filesystem-tasks.md) и остановки старых писателей.

## Источник и формат

1. Получи из правил целевого проекта абсолютные пути к основной папке, общей `.sov/` и **закреплённому** скрипту `sov_task.py` той же версии SOV, выбранный источник задач и разрешения на запуск Python с PyYAML. Перед записью проверь, что файловый протокол действительно подключён: наличие исходников в репозитории SOV или глобальной команды `/sov` не переключает работающий проект. Если источник недоступен, не создавай новое состояние и не возвращайся к `ROADMAP.md` или `sov-state`.
2. Запускай `python3 <абсолютный путь к sov_task.py> --state-dir <абсолютный путь к основной .sov> <команда>` из основной копии или worktree с **одним** state-dir. В нём должны существовать `tasks/`, `claims/`, `completed/`, `archive/`; отсутствующий при работе каталог может означать потерю состояния. CLI возвращает JSON; ошибка в stderr и exit 2, у `validate` — JSON с `valid:false` и exit 2. `claim` возвращает `status:not_ready`, `claim-next` — `status:no_ready_tasks` с exit 0, это не успешный захват. Обрабатывай эти исходы явно. Перед выбором и после подозрения на сбой вызови `validate`, сообщай диагностику и не работай с повреждённой или незавершённой записью до её сверки.
3. Каталог задачи — `.sov/tasks/<id>-<slug>/`, карточка `task.yaml` содержит строковый четырёхзначный `id`, непустые `title`, `description`, список строковых `depends_on` и непустой `acceptance_criteria`. `slug` — строчные латинские слова/цифры с дефисами. ID и имя каталога неизменны; не переназначай завершённый ID. CLI выдаёт ID при `create` после максимального ID в задачах, архиве, маркерах и захватах, но не проверяет смысл требований и полноту графа. Поля `status`, `claimed_by`, `claimed_at`, `completed_at` не записывай в YAML. `owner` и `claimed_at` внутри claim — диагностические сведения, **не lock и не доказательство живости сеанса**.
4. Сообщай вызывающему агенту ID, имя каталога, абсолютный путь к нему, вычисленное состояние и зависимости. `task.md` и остальные артефакты шагов находятся **в этом же каталоге**, а не в отдельной папке по ID. При `complete` весь каталог с файлами перемещается в `.sov/archive/<id>-<slug>/`; сообщай новый путь оркестратору. Из worktree не читай относительную `.sov/` как общую.

## Операции и решения агента

- **Создать:** уточни результат, описание, проверяемые критерии и зависимости, проверь существующие ID (активные через `list`/`show`, завершённые через `list-completed`/`show-completed`), отсутствие самозависимости и циклов в доступном графе. Запиши подготовленную YAML-карточку во временный файл вне хранилища; вызови `create --file <абсолютный путь> --slug <slug>` без ID либо с заранее обоснованным свободным ID. После успешного ответа проверь карточку через `show <id>` и сообщи фактический ID; заполни `task.md` в созданной папке перед началом работы. При потерянном ответе сверь `list`, `list-completed`, карточки и контекст намерения: не создавай дубликат при неразличимых результатах. Для декомпозиции Spec карточки реализации создавай только после подтверждённой публикации требований в удалённом `main`; зависимость от завершённой задачи подготовки используй, если она существует, а для внешней Spec не выдумывай её ID.
- **Просмотреть / выбрать:** `list` показывает незавершённые задачи по ID с вычисленным `state`; `list-ready` — готовые без claim с завершёнными зависимостями; `show <id>` — незавершённую задачу. `list-completed` показывает завершённые карточки по ID с полной семантикой `task.yaml`, `show-completed <id>` — одну завершённую карточку; при ошибке целостности архива остановись и разбери её, не считай частичный перенос завершением. Отсутствие `show` не означает, что ID свободен. Только `completed/<id>` удовлетворяет зависимость: архив без маркера, удаление задачи или артефакт `task.md` не подходят. Из готовых выбирай по возрастанию ID с учётом поручения и внешних условий начала (опубликованные требования для новой функциональности, определённое поведение бага); при занятой/заблокированной задаче рассматривай следующую. CLI не проверяет эти условия и не выбирает смысл задачи вместо агента. При отсутствии готовых сообщи, пусто ли хранилище либо что мешает (зависимости, claims, внешние условия); не снимай препятствия ради выбора.
- **Начать по ID / следующую:** для явно указанного ID прочитай `show`, сверь `READY`, зависимости и внешние условия, затем `claim <id> [--owner <диагностический текст>]`. Для следующей подходящей по содержанию задачи применяй те же условия и `claim`; если все подходящие готовы к началу, `claim-next` атомарно перебирает ID и пропускает занятые. После `not_ready` проверь новое состояние и попробуй следующую доступную; не начинай до положительного ответа `IN PROGRESS` и существующего каталога `claims/<id>-<slug>/`. В среде двух агентов успех проверки `list-ready` без успешного claim не даёт права менять артефакты или worktree. Используй один согласованный диагностический `--owner` для release/complete, если указал его при claim; совпадение owner само по себе не даёт другому сеансу права продолжать.
- **Продолжить / освободить:** при явном продолжении по ID сверь `show`, claim, `task.md`, работу прежнего агента, worktree, Git и удалённый `main`. Если claim был штатно освобождён, заново получи его через `claim <id>`; `claim-next` здесь может выбрать другую задачу. Если claim существует, **не** считай совпадающий `owner` разрешением работать: продолжает только захвативший агент в текущей работе; после аварии сначала докажи остановку старой работы, сверяй артефакты и вручную разбери stale claim, затем заново захвати. Автоматического lease/перехвата нет. Перед паузой или отказом после записи причины и следующего шага в `task.md` вызови `release <id> [--owner ...]` для своего claim; задача снова становится `READY` либо `BLOCKED` по зависимостям. При сбое release перепроверь claim и фактическую работу, не объявляй освобождение по одному отсутствию ответа. Препятствие в исполнении записывай в `task.md`, а не в `blocked`-статус; при необходимости не выбирай задачу повторно, пока препятствие не устранено.
- **Завершить:** оркестратор подтверждает результат, обязательные проверки, отсутствие блокирующих замечаний и, для публикуемой задачи, включение итогового SHA в удалённый `main` и проверки после push. Только после этого вызывай `complete <id> [--owner ...]` с собственным claim; CLI **не** проверяет публикацию. Порядок файловых действий: создать `completed/<id>`, перенести целиком каталог задачи в `archive/`, удалить claim. Получи положительный ответ и проверь архив, marker и отсутствие исходной папки/claim; обнови путь артефактов. `task.md` с подтверждением публикации сохраняется в архиве. Непубликуемую задачу заверши после её применимых проверок.

## Прерывания и пределы проверки

`complete` не является транзакцией нескольких каталогов. При таймауте или потере ответа вызови `validate [id]`, проверь marker, задачу, архив и claim: при marker + task или marker + archive с **прежним собственным** claim повтор `complete` завершает перенос; при отсутствии claim, двух папках или архиве без marker остановись для ручной сверки. Marker разблокирует зависимость даже во время промежуточного переноса, но не доказывает завершение архивации. Не вызывай `release` после создания marker. При потере ответа `create` или `claim` также сначала установи фактический исход, не создавай ещё одну задачу и не работай под чужим claim. `validate` выявляет формат и известные промежуточные состояния, но не заменяет проверки циклов, всех ссылок, публикации и полномочий агента; о гарантиях CLI см. [описание](../../cli/sov-task/README.md).

## Самопроверка сценариев

На отдельном временном хранилище проверь создание двух разных ID, зависимую задачу до и после marker, выбор следующей с пропуском занятой/зависимой, двух агентов на один ID (только один `mkdir` успешен), явное продолжение после release и остановку при оставшемся чужом claim, отсутствие готовых задач, сохранность `task.md` после complete и восстановление прерванного переноса. Отдельно проверь, что инструкция требует подтверждения публикации **до** complete, не принимает `owner` за lock и не выдаёт промежуточный marker за окончательный успех. Не проводи эти пробы на подключённом проекте и не заменяй его данные образцами.
