# Учёт задач SOV

Этот скил — единственный интерфейс к общему списку задач. Оркестратор и скилы шагов запрашивают у него задачу и состояние, но не читают и не редактируют источник списка напрямую. Здесь ведутся только идентификатор, название, статус, назначение, зависимости, порядок и признак необходимости публикации. Запрос, маршрут, причины блокировки, проверки и подтверждение публикации сохраняются оркестратором в `.sov/tasks/<task-id>/task.md`, а не копируются как второй общий статус. Артефактами и worktree этот скил не управляет.

## Источник и адресация

1. Получи абсолютный путь к **основной** папке проекта, явно выбранный источник, закреплённую версию SOV, абсолютные пути к `sov-state` и `state-dir=<основная папка>/.sov`, а также устойчивый идентификатор исполнителя из `AGENTS.md` / применимых правил. Не выводи общую папку из текущего каталога worktree и не используй ID сессии как единственный ключ продолжения. Для файлового источника используй только CLI этой же версии SOV после проверки `--version` (в этой версии `sov-state 0.1.0`, протокол `v:1`), исполняемости и `read` из текущей рабочей копии. Если настройка или инструмент недоступны, остановись: не переходи на прямую запись и не создавай другой список. В уже подключённом проекте работа старых сессий по прежним инструкциям должна быть остановлена до переключения писателей; процедура — в [`README.md`](../../README.md#подготовка-общего-бинарника-sov-state-linux).
2. CLI `sov-state` — байтовый транспорт **существующего** файлового списка, а не другой источник задач и не исполнитель семантических проверок. При отсутствии списка выясни, первое ли это подключение или утрата состояния: только при первом подключении установка создаёт список из [`templates/ROADMAP.md`](../../templates/ROADMAP.md) с согласованным префиксом ID и постоянный mutex при остановленных писателях. `sov-tasks` не создаёт их при обычной работе. Если проект выбрал иной неподключённый CLI/API, сообщи о препятствии, не подменяя выбранный источник файловым.
3. Передай вызывающему агенту запись задачи и абсолютный путь `<основная папка>/.sov/tasks/<task-id>/`. Папку при начале сохраняемой работы создаёт оркестратор. Стабильный ID — ключ к папке и внешним ссылкам; после создания его нельзя переименовывать или выдавать повторно.

## Формат файлового списка

Формат и пустой образец — в [`templates/ROADMAP.md`](../../templates/ROADMAP.md). В поле `Следующий ID` записан очередной свободный номер с постоянным префиксом проекта; новые задачи добавляются **в конец** таблицы, после чего номер увеличивается. Удаление, отмена или завершение задачи не освобождают ID. Физический порядок строк определяет очередь; не сортируй таблицу при редактировании. ID уникален, ID и название непустые. Статус — ровно один из `planned`, `in_progress`, `blocked`, `done`, `cancelled`; исполнитель — устойчивый идентификатор из правил проекта или `—`, не ID текущей сессии; зависимости — уникальные ID через запятую либо `—`; публикация — `yes` или `no` (определяется поручением и правилами проекта при создании). Не подменяй признак публикации статусом PR.

Перед любой выдачей, выбором и изменением получи `content_base64` и `revision` через `sov-state read --state-dir <абсолютный state-dir>`, декодируй bytes и проверь список: единственность ID, отсутствие повторяющихся строк, номер `Следующий ID` больше всех уже выданных номеров с тем же префиксом, допустимость полей, ссылки зависимостей на существующие задачи, отсутствие зависимости от себя и циклов. При нарушении не выбирай и не меняй задачи: сообщи конкретные строки и попроси исправить состояние. Отсутствие ответа `read` не означает пустой список. Результат чтения — снимок; перед назначением и любым изменением заново читай и проверяй состояние. Разные независимые одновременные исполнители обязаны иметь **разные устойчивые ID** из правил проекта; две сессии с одним ID не должны параллельно выбирать или продолжать задачи. До проверки сквозного параллельного режима по правилам проекта нескольких независимых координаторов не запускай.

## Условная запись файлового источника

Для **каждого** изменения (создание и выдача ID, назначение, освобождение/смена исполнителя, блокировка и возобновление, статус и публикация, название, зависимости, перестановка строк/приоритет) выполни полный цикл:

1. Выполни `sov-state read --state-dir <абсолютный state-dir>` через зафиксированный **абсолютный путь к бинарнику**. Убедись в `status:ok`, `v:1`, `resource:ROADMAP.md`; декодируй `content_base64` без изменения bytes и проверь весь список и внешние предусловия конкретной операции. Для `done` с `Публикация = yes` повторно проверь фактическое слияние PR, а не только запись в артефакте.
2. Собери полную новую версию из **этого** снимка в отдельном обычном локальном файле папки задачи или отдельном временном каталоге сессии (для создания до выдачи ID — каталог сессии). Не редактируй существующий `ROADMAP.md` напрямую и не используй его, `.roadmap.lock` или hardlink на них в качестве `--input`. Сохрани не затронутые строки и их порядок; проверь результирующий список и внешние условия. Удаляй только собственные временные файлы после выяснения исхода операции.
3. Вызови `sov-state commit --state-dir <абсолютный state-dir> --expected <revision из read> --input <абсолютный путь к новой версии> --lock-timeout 5s`. Только `status:ok` при exit 0 подтверждает изменение. При `changed:false` проверь на свежем чтении требуемый смысловой результат: no-op сам по себе не выдаёт ID и не доказывает назначение. Верни вызывающему агенту подтверждённые поля, а не предполагаемый исход.
4. При `revision_conflict` (exit 10) перечитай список, заново проверь все предусловия и **пересобери** файл, в том числе ID, порядок и зависимости; замена одного `--expected` недопустима. Не более трёх попыток `commit` на операцию, включая первую, с коротким ограниченным случайным ожиданием между конфликтами. Если предпосылки изменились (например, задача назначена другому), пересмотри выбор или остановись. После трёх конфликтов сохрани контекст и сообщи препятствие; бесконечных повторов нет. При `lock_timeout` (exit 11) остановись либо один раз повтори полный цикл после нового чтения/проверки в пределах общего лимита трёх попыток. `invalid_input` (12) и обычный `io_error` (13) требуют устранения причины, а не обхода CLI.

Таймаут процесса, потеря stdout, неполный/непонятный ответ или `may_have_committed:true` означают **неопределённый исход**. Прочитай свежий список через CLI и проверь именно нужный эффект: ID, название/контекст, исполнитель, статус, зависимости и другие затронутые поля. Если результат подтверждён, сверь необходимые артефакты и продолжи без второго commit; если он не подтверждён, заново проверь предпосылки и начинай полный цикл; при чужой правке или неразличимых результатах остановись. Для создания заранее сохрани контекст намерения в локальных материалах поручения: одинаковые строки разных создателей не позволяют надёжно опознать свой ID; не создавай вторую задачу при такой неопределённости. Хеш bytes сам по себе не доказывает семантический результат. Исправление повреждённого списка — отдельная контролируемая процедура обслуживания при остановленных писателях, а не ручная запись в обход CLI.

## Операции

- **Получить**: по ID верни все поля строки, её место в очереди, а также вычисленную доступность и причину недоступности. При отсутствии ID явно сообщи об этом; не выдавай новый ID вместо отсутствующего.
- **Найти для продолжения**: верни все строки `in_progress` и `blocked`, у которых исполнитель совпадает с устойчивым идентификатором вызывающего агента из правил проекта, вместе с их ID, статусом и путями артефактов. Не ограничивай поиск текущей сессией; `done` и `cancelled` не являются незавершёнными задачами. При одном совпадении верни его; при нескольких верни все ID для выбора человеком без автоматического назначения; при нуле явно сообщи об этом для последующего выбора следующей `planned`. При обновлении установки сначала проверь, не остались ли назначения по прежним ID сессий: пока их владельцы не выяснены, не считай ноль совпадений доказательством отсутствия собственной работы. Задача с другим исполнителем, включая прежний ID сессии, не становится своей автоматически: смена назначения требует явного решения с причиной в `task.md`.
- **Создать**: уточни название, необходимость публикации и зависимости; убедись, что ID зависимостей существуют и нет цикла. На свежем снимке возьми `Следующий ID`, добавь строку с `planned`, исполнителем `—`, выбранными зависимостями и публикацией; увеличь номер. Верни ID и путь к папке артефактов только после подтверждения записи, не создавая саму папку. При конфликте пересчитай ID на новом снимке; после неоднозначного исхода не создавай дубликат. Новые задачи реализации, зависящие от подготовки требований, остаются `planned` до подтверждённой публикации требований.
- **Выбрать следующую**: просматривай строки по порядку и верни первую задачу со статусом `planned`, исполнителем `—`, зависимостями только в `done` и выполненными условиями начала работы (включая опубликованные требования для разработки). Зависимость `cancelled` **не** выполнена; `blocked`, `planned` и `in_progress` также не выполнены. Если нет доступной, сообщи, пуст ли список либо какие зависимости, назначения или условия мешают; не снимай блокировки для продолжения работы.
- **Назначить / начать**: назначай доступную `planned` задачу устойчивому исполнителю из правил проекта и одновременно переводи в `in_progress`. До подтверждённого commit **не** начинай работу, не создавай worktree и не меняй артефакты задачи. Для явно указанного `planned` ID применяй те же условия начала, что для выбора следующей; при конфликте повторно проверь доступность и чужое назначение, выбери другую доступную задачу либо остановись. Для уже назначенной тому же исполнителю `in_progress` возвращай текущее состояние для продолжения без повторного назначения, а при `blocked` возвращай препятствие без автоматического перехода в `in_progress`. Не забирай задачу с другим исполнителем, даже если сессия оборвалась; смена исполнителя или освобождение назначения требует явного решения с фиксацией причины в `task.md`.
- **Обновить**: меняй только явно запрошенные поля после проверки текущего статуса и последствий для зависимых задач. Добавление зависимости не должно создавать цикл или делать текущую работу недопустимой без решения оркестратора. При `blocked` сохраняй исполнителя и требуй от оркестратора указать причину и условие снятия блокировки в `task.md`; возвращай в `in_progress` только после устранения препятствия. `cancelled` не переводится в `done` автоматически, а отменённые зависимости требуют отдельного решения. `done` требует достигнутого результата, обязательных проверок и отсутствия блокирующих замечаний; для строки с `Публикация = yes` дополнительно проверь подтверждённое слияние PR в целевую ветку по сведениям оркестратора (`task.md` и фактическое состояние GitHub). Созданный PR, push ветки и готовность к слиянию недостаточны. Если проект согласовал иной маршрут публикации, противоречащий требованию PR в спецификации SOV, не отмечай задачу `done` без разрешения этого противоречия.

После каждого подтверждённого изменения верни вызывающему агенту прежнее и новое состояние, ID, путь артефактов и результат проверки списка. Список и `task.md` не являются одной транзакцией: при создании сначала подтверди строку списка, затем оркестратор создаёт папку и `task.md`; при `done` сначала сохрани в `task.md` доказательство публикации и сверь GitHub, затем запиши статус. При возобновлении выясни фактическое состояние обоих источников и закончи недостающее действие, не выдавая локальный текст за второй общий статус.

## Самопроверка сценариев

На копии образца списка проверь: два создания дают разные ID; два исполнителя пытаются назначить одну задачу — только победитель начинает; изменение разных строк, перестановка и зависимости после конфликта пересобираются без потери чужих правок; цикл, `cancelled`-зависимость и `done` до слияния PR отклоняются; три конфликта дают остановку, а потерянный ответ проверяется чтением без слепого повтора. Проверь также продолжение `in_progress`/`blocked` новым сеансом своего устойчивого ID, неоднозначность нескольких задач, отсутствие доступных задач и восстановление папки/`task.md` после подтверждённого создания. При наличии проекта с фактическим списком не заменяй его образцом ради проверки.
