# Учёт задач SOV

Этот скил — единственный интерфейс к общему списку задач. Оркестратор и скилы шагов запрашивают у него задачу и состояние, но не читают и не редактируют источник списка напрямую. Здесь ведутся только идентификатор, название, статус, назначение, зависимости, порядок и признак необходимости публикации. Запрос, маршрут, причины блокировки, проверки и подтверждение публикации сохраняются оркестратором в `.sov/tasks/<task-id>/task.md`, а не копируются как второй общий статус. Артефактами и worktree этот скил не управляет.

## Источник и адресация

1. Получи абсолютный путь к **основной** папке проекта, явно выбранный источник, закреплённую версию SOV, абсолютные пути к `sov-state` и `state-dir=<основная папка>/.sov`, устойчивый ID владельца из `AGENTS.md` / применимых правил и выданный вызывающему оркестратору UUID сеанса. Не подменяй владельца UUID и не выводи общую папку из текущего каталога worktree. Для файлового источника используй только CLI этой же версии SOV после проверки `--version` (в этой версии `sov-state 0.3.0`, протокол `v:1`), исполняемости, `read` и `read-archive` из текущей рабочей копии. Если настройка или инструмент недоступны, остановись: не переходи на прямую запись и не создавай другой список. В уже подключённом проекте работа старых сессий по прежним инструкциям должна быть остановлена до переключения писателей; процедура — в [`README.md`](../../README.md#подготовка-общего-бинарника-sov-state-linux).
2. CLI `sov-state` — байтовый транспорт **существующих** файлов списка и архива, а не другой источник задач и не исполнитель семантических проверок. При отсутствии любого файла выясни, первое ли это подключение или утрата состояния: при первом подключении установка создаёт список из [`templates/ROADMAP.md`](../../templates/ROADMAP.md), архив из [`templates/ARCHIVE.md`](../../templates/ARCHIVE.md) и постоянный mutex при остановленных писателях. Обновление прежнего файлового источника без архива — отдельный этап установки при остановленных писателях; не создавай архив молча при обычной работе. Если проект выбрал иной неподключённый CLI/API, сообщи о препятствии, не подменяя выбранный источник файловым.
3. Передай вызывающему агенту запись задачи и абсолютный путь `<основная папка>/.sov/tasks/<task-id>/`. Папку при начале сохраняемой работы создаёт оркестратор. Стабильный ID — ключ к папке и внешним ссылкам; после создания его нельзя переименовывать или выдавать повторно.

Для **только читающих** запросов (`получить`, `найти для продолжения`, `просмотреть очередь`, диагностика) после отдельной проверки подключения можно вызывать [read-only `sov-tasks-view`](../../cli/sov-tasks-view/README.md) из той же закреплённой версии SOV с абсолютными `--cli` и `--state-dir`. `validate` проверяет оба файла; `get`, `owner`, `queue` возвращают проверенные поля без ручного `read | python -c`. При `invalid_state`, `unstable_snapshot`, `recovery_required`, ошибке транспорта или отсутствующем ID следуй диагностике и остановись/восстанови по правилам ниже, не выбирай задачу по частичному разбору. Пока помощник не подключён и проверен, действуют чтения `sov-state` и полная ручная проверка обоих файлов по следующему разделу; не считай наличие исходников подключением. Перед **любой записью** по-прежнему перечитай оба файла, проверь смысл, владельца и захват, пересобери полные входы и выполни CAS по разделам ниже; вывод просмотра не служит ожидаемым revision для пропуска этих проверок. Внешние условия начала задачи, проверок и публикации инструмент чтения не проверяет.

## Формат файлового списка

Формат и пустые образцы — в [`templates/ROADMAP.md`](../../templates/ROADMAP.md) и [`templates/ARCHIVE.md`](../../templates/ARCHIVE.md). В поле `Следующий ID` записан очередной свободный номер с постоянным префиксом проекта; новые задачи добавляются **в конец** ROADMAP, после чего номер увеличивается. Удаление, отмена или завершение задачи не освобождают ID. Физический порядок строк ROADMAP определяет очередь; не сортируй таблицу при редактировании. ID уникален между файлами (временно одинаковая **полностью совпадающая** строка допустима только при прерванной архивации). ID и название непустые. В ARCHIVE только `done` и `cancelled`, без счётчика ID; его строки не выбираются в очередь. Статус ROADMAP — ровно один из `planned`, `in_progress`, `blocked`, `done`, `cancelled`; `Исполнитель` — устойчивый ID владельца из правил проекта или `—`; `Координатор` — UUID выданный `sov-state session-id` либо `—` без захвата. Для `planned` оба поля `—`; для `blocked`, `done`, `cancelled` поле координатора `—`. `in_progress` может иметь `—` только при подтверждённой паузе либо до захвата после миграции; такой статус **не** разрешает работу без получения захвата. Зависимости — уникальные ID через запятую либо `—`; публикация — `yes` или `no` (определяется поручением и правилами проекта при создании). Не подменяй признак публикации фактом локального коммита.

Перед любой выдачей, выбором и изменением получи `content_base64` и `revision` через `sov-state read` и `sov-state read-archive --state-dir <абсолютный state-dir>`, декодируй bytes и проверь оба файла: уникальность ID, номер `Следующий ID` больше всех уже выданных номеров с тем же префиксом, допустимость полей, ссылки зависимостей строк ROADMAP **только на строки ROADMAP**, отсутствие зависимости от себя и циклов, форму владельца/захвата по статусу. В архиве допускаются ссылки на архивные и оставшиеся ID для сохранения истории; архивные строки не участвуют в проверке доступности. Если ID присутствует в обоих файлах, разрешено только полное совпадение терминальных строк без входящих ссылок из остающегося ROADMAP: это прерванный перенос, сначала доведи его до конца по процедуре ниже. Любое иное расхождение — препятствие; не выбирай и не меняй задачи, сообщи конкретные строки. Отсутствие ответа `read` не означает пустой список. Результаты чтения — снимки, а не общая транзакция; перед назначением и любым изменением заново читай оба файла и проверяй состояние. Один устойчивый владелец может вести любое число разных задач разными UUID сеансов; два сеанса не могут одновременно захватить **одну** задачу. Для каждого целевого проекта параллельных координаторов допускай только после [контролируемого включения](../../docs/parallel-activation.md) с остановкой старых писателей и проверкой общей установки.

## Условная запись файлового источника

Для **каждого** изменения (создание и выдача ID, назначение, освобождение/смена исполнителя, блокировка и возобновление, статус и публикация, название, зависимости, перестановка строк/приоритет) выполни полный цикл:

1. Выполни `sov-state read --state-dir <абсолютный state-dir>` через зафиксированный **абсолютный путь к бинарнику**. Убедись в `status:ok`, `v:1`, `resource:ROADMAP.md`; декодируй `content_base64` без изменения bytes и проверь весь список и внешние предусловия конкретной операции. Для `done` с `Публикация = yes` повторно проверь включение итогового SHA в удалённый `main` и успешность обязательных проверок, а не только запись в артефакте.
2. Собери полную новую версию из **этого** снимка в отдельном обычном локальном файле папки задачи или отдельном временном каталоге сессии (для создания до выдачи ID — каталог сессии). Не редактируй существующий `ROADMAP.md` напрямую и не используй его, `.roadmap.lock` или hardlink на них в качестве `--input`. Сохрани не затронутые строки и их порядок; проверь результирующий список и внешние условия. Удаляй только собственные временные файлы после выяснения исхода операции.
3. Вызови `sov-state commit --state-dir <абсолютный state-dir> --expected <revision из read> --input <абсолютный путь к новой версии> --lock-timeout 5s`. Только `status:ok` при exit 0 подтверждает изменение. При `changed:false` проверь на свежем чтении требуемый смысловой результат: no-op сам по себе не выдаёт ID и не доказывает назначение. Верни вызывающему агенту подтверждённые поля, а не предполагаемый исход.
4. При `revision_conflict` (exit 10) перечитай список, заново проверь все предусловия и **пересобери** файл, в том числе ID, порядок и зависимости; замена одного `--expected` недопустима. Не более трёх попыток `commit` на операцию, включая первую, с коротким ограниченным случайным ожиданием между конфликтами. Если предпосылки изменились (например, задача назначена другому), пересмотри выбор или остановись. После трёх конфликтов сохрани контекст и сообщи препятствие; бесконечных повторов нет. При `lock_timeout` (exit 11) остановись либо один раз повтори полный цикл после нового чтения/проверки в пределах общего лимита трёх попыток. `invalid_input` (12) и обычный `io_error` (13) требуют устранения причины, а не обхода CLI.

Таймаут процесса, потеря stdout, неполный/непонятный ответ или `may_have_committed:true` означают **неопределённый исход**. Прочитай свежий список через CLI и проверь именно нужный эффект: ID, название/контекст, исполнитель, статус, зависимости и другие затронутые поля. Если результат подтверждён, сверь необходимые артефакты и продолжи без второго commit; если он не подтверждён, заново проверь предпосылки и начинай полный цикл; при чужой правке или неразличимых результатах остановись. Для создания заранее сохрани контекст намерения в локальных материалах поручения: одинаковые строки разных создателей не позволяют надёжно опознать свой ID; не создавай вторую задачу при такой неопределённости. Хеш bytes сам по себе не доказывает семантический результат. Исправление повреждённого списка — отдельная контролируемая процедура обслуживания при остановленных писателях, а не ручная запись в обход CLI.

### Захват задачи

До первой операции сохраняемой работы основной оркестратор один раз выполняет `sov-state session-id` того же установленного бинарника, проверяет `v:1`, `status:ok`, `resource:SESSION` и UUID v4 и хранит ID в контексте текущего запуска. Команда не открывает очередь и не регистрирует владельца; для нового запуска генерируется **новый** UUID. Не бери UUID из произвольного предыдущего `task.md` и не присваивай свой UUID другому активному сеансу. Другой доступный источник задач потребует собственного подключённого способа захвата, а не имитации этой команды.

Любую запись **по выполняемой задаче** делай только после свежего чтения и проверки её `Исполнитель` и `Координатор`: владелец совпадает с устойчивым ID вызывающего, захват совпадает с UUID текущего запуска. Это относится к статусу, завершению, зависимостям и изменению других полей занятой строки. Отдельные операции очереди над другими незанятыми строками не освобождают и не изменяют чужие захваты. При `revision_conflict` повтори смысловую проверку захвата; потеря ответа на получение захвата разрешается новым чтением именно этой строки. После подтверждённой потери захвата прекрати менять `task.md`, worktree и публикацию данной задачи; не считай совпадение владельца правом продолжать. Скилы шагов получают ID задачи и пути от оркестратора, не создают собственные захваты.

При штатной паузе условно установи `Координатор = —`, сохранив `in_progress` и владельца, запиши в `task.md` состояние для продолжения. Это не разблокирует `blocked` и не снимает назначение с задачи. При `blocked`, `done`, `cancelled` освободи захват в той же условной записи статуса. Возобновление `blocked` требует сначала устранить препятствие, затем одним commit записать `in_progress` и собственный UUID. Если обнаружен чужой UUID, не делай автоматическую передачу по таймауту или PID: старый сеанс должен явно освободить захват либо должна быть подтверждена его остановка, сверены артефакты, Git и удалённый `main`, а основание передачи записано в `task.md`; затем условно смени UUID, только если старый всё ещё совпадает. Если подтверждения нет — препятствие. Проверка жизненного цикла через надёжный механизм среды допустима лишь когда он действительно подключён и проверен в проекте; текущая CLI не определяет, жива ли сессия.

### Архивация терминальных строк

После подтверждённого перевода в `done` или `cancelled`, после изменения зависимостей, а также при первой штатной операции после обновления установки найди в ROADMAP строки с терминальным статусом, на которые **не ссылается ни одна остающаяся строка** (включая другие терминальные). Выбери такие строки, удали их из новой версии ROADMAP и добавь в конец ARCHIVE без изменения полей и порядка остальных строк; повтори выбор для освободившихся терминальных строк, пока кандидатов нет. Оставь `Следующий ID` неизменным. Статус и доказательство публикации подтверждаются **до** архивации, не в её ходе. Архивные строки не становятся доступными зависимостями для новых задач; при попытке сослаться на архивный ID остановись и предложи пересмотреть замысел зависимости. Папку `.sov/tasks/<ID>/` не удаляй.

Для переноса используй только `sov-state archive --state-dir <state-dir> --expected <revision ROADMAP> --input <новый ROADMAP> --archive-expected <revision ARCHIVE> --archive-input <новый ARCHIVE> --lock-timeout 5s`. Оба входа — отдельные локальные файлы, собранные из свежих снимков; заранее проверь, что каждая перенесённая строка есть ровно в одном месте новой пары файлов, ни один ID не потерян и оставшиеся зависимости указывают на ROADMAP. CLI под одним mutex проверяет оба revision, **сначала публикует ARCHIVE**, затем ROADMAP; семантику Markdown он не проверяет. При конфликте любого файла повтори чтение, проверки и сборку обоих файлов с лимитом трёх попыток. При ошибке или потерянном ответе перечитай оба файла: если строка есть и там и там в точности одинаковая, а ссылок из оставшейся очереди на неё нет, повтори перенос с уже существующей архивной строкой, не добавляя её повторно; если только в архиве — перенос завершён; если только в ROADMAP — повтори с нового снимка после проверки условий. При расхождении строк или новой зависимости не угадывай исход: остановись. До разрешения дублирующей строки не выполняй другие изменения списка. Операция не является атомарной для читателей двух файлов: они обязаны распознавать и завершать допустимый промежуточный дубликат; строка никогда не исчезает из обоих файлов. Не удаляй ARCHIVE и не создавай его заново ради восстановления.

## Операции

- **Получить**: по ID верни все поля строки ROADMAP, её место в очереди, а также вычисленную доступность и причину недоступности; для архивного ID верни его поля и указание, что он вне очереди. При отсутствии в обоих файлах явно сообщи об этом; не выдавай новый ID вместо отсутствующего.
- **Найти для продолжения**: верни все строки `in_progress` и `blocked` устойчивого владельца из правил проекта, их ID, статус, захват и пути артефактов. Не ограничивай поиск текущей сессией; `done` и `cancelled` не являются незавершёнными задачами. При одном совпадении верни его; при нескольких верни все ID для выбора человеком без автоматического назначения; при нуле явно сообщи об этом для последующего выбора следующей `planned`. Найденная строка с чужим захватом **не** разрешает продолжение, пока захват не освобождён или явно не передан. При обновлении установки выясни владельцев прежних ID сеансов/слотов; не считай отсутствие собственных задач доказательством отсутствия незавершённой работы, пока назначения не сверены. Задача с другим владельцем не становится своей автоматически: смена назначения требует явного решения с причиной в `task.md`.
- **Создать**: уточни название, необходимость публикации и зависимости; убедись, что ID зависимостей существуют и нет цикла. На свежем снимке возьми `Следующий ID`, добавь строку с `planned`, владельцем и координатором `—`, выбранными зависимостями и публикацией; увеличь номер. Верни ID и путь к папке артефактов только после подтверждения записи, не создавая саму папку. При конфликте пересчитай ID на новом снимке; после неоднозначного исхода не создавай дубликат. Новые задачи реализации, зависящие от подготовки требований, остаются `planned` до подтверждённой публикации требований.
- **Выбрать следующую**: просматривай строки по порядку и верни первую задачу со статусом `planned`, исполнителем `—`, зависимостями только в `done` и выполненными условиями начала работы. Для новой функциональности проверь опубликованные требования; для исправления бага — определённость ожидаемого поведения или предусмотренное начальное согласование через `sov-spec`. Отдельная опубликованная спецификация не требуется для однозначного бага без противоречия опубликованным источникам. Не требуй готового исследования или плана до начала задачи, которая их создаёт; до реализации пригодность этих результатов проверяет оркестратор. Зависимость `cancelled` **не** выполнена; `blocked`, `planned` и `in_progress` также не выполнены. Если нет доступной, сообщи, пуст ли список либо какие зависимости, назначения или условия мешают; не снимай блокировки для продолжения работы.
- **Назначить / начать**: назначай доступную `planned` задачу устойчивому владельцу из правил проекта и **в одном commit** записывай `in_progress` и UUID текущего координатора. До подтверждённого commit **не** начинай работу, не создавай worktree и не меняй артефакты задачи. Для явно указанного `planned` ID применяй те же условия начала, что для выбора следующей; при конфликте повторно проверь доступность и чужое назначение, выбери другую доступную задачу либо остановись. Для `in_progress` того же владельца с `Координатор = —` условно захвати задачу собственным UUID до продолжения; с чужим UUID остановись и разреши передачу по разделу выше. При `blocked` возвращай препятствие без автоматического перехода в `in_progress`. Не забирай задачу с другим владельцем, даже если сессия оборвалась; смена владельца требует явного решения с фиксацией причины в `task.md`.
- **Обновить**: меняй только явно запрошенные поля строки ROADMAP после проверки текущего статуса, собственного захвата для выполняемой задачи и последствий для зависимых задач; архивные строки не обновляй как действующие задачи. Добавление зависимости не должно создавать цикл или делать текущую работу недопустимой без решения оркестратора. При `blocked` сохраняй владельца, освобождай захват и требуй от оркестратора указать причину и условие снятия блокировки в `task.md`; возвращай в `in_progress` с новым захватом только после устранения препятствия. `cancelled` не переводится в `done` автоматически, а отменённые зависимости требуют отдельного решения. `done` требует достигнутого результата, обязательных проверок и отсутствия блокирующих замечаний; при терминальном статусе освободи захват в том же commit. Для строки с `Публикация = yes` дополнительно проверь включение итогового коммита после прямого push в удалённый `main` по сведениям оркестратора (`task.md` и фактическое чтение remote) и успешность обязательных проверок после push, если они предусмотрены. Локальный коммит или push только ветки задачи недостаточны. Если проект требует PR или не допускает прямой push в `main`, не отмечай задачу `done` без разрешения противоречия.

После каждого подтверждённого изменения верни вызывающему агенту прежнее и новое состояние, ID, путь артефактов и результат проверки списка. Список и `task.md` не являются одной транзакцией: при создании сначала подтверди строку списка, затем оркестратор создаёт папку и `task.md`; при `done` сначала сохрани в `task.md` доказательство публикации и сверь удалённый `main`, затем запиши статус. При возобновлении выясни фактическое состояние обоих источников и закончи недостающее действие, не выдавая локальный текст за второй общий статус.

## Самопроверка сценариев

На копиях обоих образцов проверь: два создания дают разные ID; несколько сеансов одного владельца получают разные UUID и захватывают разные задачи; два сеанса пытаются назначить или захватить одну задачу — только победитель начинает; чужой захват не считается своим даже при совпадении владельца. Изменение разных строк, перестановка и зависимости после конфликта пересобираются без потери чужих правок; цикл, `cancelled`-зависимость и `done` до подтверждения публикации в удалённом `main` отклоняются; три конфликта дают остановку, а потерянный ответ проверяется чтением без слепого повтора. Проверь штатное освобождение, продолжение `in_progress` без захвата новым сеансом, `blocked` после разрешения препятствия, несколько собственных задач с выбором ID, остановку при чужом захвате и передачу только после подтверждённой остановки прежнего сеанса. Для архивирования проверь цепочку `TASK-001 done → TASK-002 planned → TASK-003 planned`: TASK-001 остаётся в ROADMAP, пока на неё ссылается TASK-002; после удаления зависимости TASK-001 переносится в ARCHIVE, но TASK-002 и TASK-003 остаются в очереди. Проверь, что `cancelled` не разблокирует зависимость, а цепочка терминальных задач переносится после удаления последней входящей зависимости; `Следующий ID` сохраняется и выдаёт новый ID без повторения архивных. Смоделируй дубликат идентичной строки в двух файлах после прерывания между публикациями: восстановление удаляет её только из ROADMAP; различающиеся строки, ссылка из ROADMAP на архивный ID и отсутствие архива останавливают работу. Два параллельных переноса с одним revision дают один успех, затем проигравший пересобирает оба файла из новых снимков. При наличии проекта с фактическим списком не заменяй его образцами ради проверки.
