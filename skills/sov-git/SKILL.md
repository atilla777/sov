# Git и публикация задачи SOV

Этот скил выполняет операции с Git и GitHub доступными инструментами среды; отдельного движка нет. Оркестратор определяет поручение, маршрут и состояние задачи через `sov-tasks`, принимает результат проверок и записывает публикацию в `.sov/tasks/<id>-<slug>/task.md`. Этот скил не завершает задачу и не заменяет проверки шага или независимое ревью. Перед действиями прочитай `AGENTS.md`, `rules/index.md` и применимые правила **целевого проекта**: remote, прямой push в `main`, проверки и необходимые решения человека. При требовании PR или запрете прямого push остановись и согласуй изменение правил/защиты ветки, не обходи их.

В `/sov-fast` независимое ревью результата может быть обоснованно пропущено только вне разработки основного кода игры/движка и при отсутствии требования проекта; упоминание повторного ревью ниже относится к обязательному или уже назначенному ревью. Исправления в границах поручения до первой публикации в `main` продолжай в той же задаче. Hook и CI для того же состояния учитывай как свидетельства проведённых ими проверок без повторного ручного запуска, если правила проекта не требуют отдельного запуска; после изменения ветки повторяй только затронутые проверки.

## Подготовка ветки и worktree

1. Получи от оркестратора ID, имя каталога `<id>-<slug>`, подтверждённый claim своего агента через `sov-tasks`, абсолютный путь к основной папке проекта, remote и целевую ветку `main`, путь `<основная папка>/.sov/tasks/<id>-<slug>/` и применимые правила. Перед подготовкой ветки и публикацией сверяй существование своего claim и отсутствие конкурирующей работы; диагностический `owner` не подтверждает право другого сеанса использовать worktree. Проверь `git status`, `git worktree list`, текущую ветку, remote и уже существующие ветку/worktree задачи до создания новых. Не присваивай чужую рабочую копию или ветку; при неожиданных изменениях уточни владельца. `.sov/` должен быть исключён из Git основной копии; проверь исключение до записи локальных артефактов. Если рабочая копия уже существует, сверяй её фактическое состояние и продолжай, а не создавай повторную.
2. Обнови сведения о remote (например, `git fetch <remote> main`), проверь актуальный удалённый `main` и опубликованные требования, необходимые задаче. Для новой ветки выбери уникальное имя по правилам проекта и создай её **от актуального удалённого `main`**, затем worktree по пути `<основная папка>/.sov/worktree/<id>-<slug>/` (например, `git worktree add -b <branch> <path> <remote>/main`). Не переключай основную копию и не сбрасывай её незакоммиченные изменения. Если имя или путь уже заняты, выясни происхождение, не удаляй и не переписывай их автоматически.
3. Передай оркестратору абсолютные пути к worktree и **общему** каталогу задачи в основной копии. Код, `docs/` и `rules/` читай и меняй из worktree; состояние задач доступно через `sov-tasks` из основной папки, а локальные артефакты — по переданному абсолютному пути. Проверь, что worktree видит ресурсы SOV (скилы и шаблоны) по установленному пути; не считай `.sov/` внутри worktree копией общего хранилища. Запиши ветку, базу и пути в `task.md`, чтобы можно было продолжить работу после прерывания.

## Проверка и публикация

1. Перед публикацией сверь результат задачи и проверки с правилами проекта. После `fetch` проверь `git status`, полный diff и все коммиты относительно актуального `<remote>/main`, staged diff и состав push: только согласованные файлы, без секретов, случайных локальных данных, `.sov/` и посторонних правок. Выполни `git diff --check` для рабочих изменений и `git diff --cached --check` после подготовки индекса. Убедись, что ветка задачи включает актуальный `main` (fast-forward возможен) и совместима с изменениями других задач; отсутствие текстового конфликта само по себе не доказывает совместимость. Если база изменилась, согласуй обновление ветки, сохрани чужие изменения и повтори затронутые тесты, проверки и независимое ревью; при пропуске ревью пересмотри риск.
2. Подготовь коммит только из проверенных файлов, ещё раз сверь историю и remote перед публикацией. Отправь проверенную ветку **нефорсированным** `git push <remote> HEAD:refs/heads/main` из worktree задачи, без PR и без переключения основной копии. Если параллельная задача опубликовалась между fetch и push, обычный push будет отклонён: обнови базу, заново сверь полный результат и повтори затронутые проверки и назначенное ревью; не применяй `--force` или удаление чужих коммитов. Если правила требуют обязательных проверок до публикации, проведи их до push; если проектная защита запрещает прямую публикацию, остановись и согласуй правила, не обходи защиту.
3. После push независимо прочитай удалённый `main` (`git ls-remote <remote> refs/heads/main`, затем `git fetch <remote> main`), проверь, что итоговый SHA ветки задачи включён в его историю и ожидаемый результат присутствует. Запиши remote, `main`, SHA итогового коммита, удалённый SHA и результат проверки в `task.md`; лишь затем, после успешных обязательных проверок (включая проверки после push, если применимы), оркестратор может вызвать `complete` через `sov-tasks`. При ошибке push или неизвестном результате сначала выясни фактическое состояние remote, не отправляй повторно вслепую. При провале проверок после публикации сохрани задачу открытой, исправь её и повтори затронутые проверки перед следующим push.

## Продолжение и очистка

- После прерывания сначала сравни `task.md` с `git status`, ветками, worktree и удалённым `main` через `ls-remote`/`fetch`; проверь включение итогового коммита и результат проверок. Не повторяй push только потому, что запись в артефакте отсутствует; выполни лишь незавершённые действия. Если remote недоступен, не выдавай локальную запись за подтверждение публикации. При изменении базы или коммитов проверь актуальность прежних тестов и ревью.
- Удаляй worktree только после подтверждения сохранности изменений: публикация подтверждена или непубликуемые результаты сохранены в согласованном месте; `git status` чист либо каждый оставшийся файл разобран и сохранён, артефакты доступны из основной папки. Используй обычное `git worktree remove <path>` и проверь `git worktree list`. Не применяй `--force`, `git reset --hard`, удаление папки вручную или удаление ветки с несохранённой работой ради очистки. При ошибке публикации сохрани рабочую копию и укажи препятствие. Ветку удаляй только по правилам проекта после проверки, что она больше не нужна.

## Самопроверка сценариев

На пробном репозитории либо пошагово по инструкции проверь: новая задача берёт базу из актуального удалённого `main`, сохраняет незакоммиченные изменения основной копии и использует общие артефакты; повторный запуск узнаёт имеющуюся worktree; в push не попадают посторонние или служебные файлы; продвижение базы вызывает нужные повторные проверки; push только ветки задачи не завершает задачу, а подтверждённый SHA в удалённом `main` позволяет завершить её после обязательных проверок; отклонённый из-за гонки push не форсируется; после прерывания уже опубликованный коммит не отправляется повторно; worktree с несохранёнными изменениями или при ошибке публикации не удаляется. Запиши реальные проверки и их ограничения в артефакты задачи.
