# Git и публикация задачи SOV

Этот скил выполняет операции с Git и GitHub доступными инструментами среды; отдельного движка нет. Оркестратор определяет поручение, маршрут и состояние задачи через `sov-tasks`, принимает результат проверок и записывает публикацию в `.sov/tasks/<task-id>/task.md`. Этот скил не меняет статус задачи и не заменяет проверки шага или независимое ревью. Перед действиями прочитай `AGENTS.md`, `rules/index.md` и применимые правила **целевого проекта**: целевую ветку, порядок PR, проверки, слияние и необходимые решения человека. При противоречии правил обязательным условиям SOV остановись и уточни решение.

## Подготовка ветки и worktree

1. Получи от оркестратора ID задачи, абсолютный путь к основной папке проекта, целевую ветку и remote, путь `<основная папка>/.sov/tasks/<task-id>/` и применимые правила. Проверь `git status`, `git worktree list`, текущую ветку, remote и уже существующие ветку/worktree задачи до создания новых. Не присваивай чужую рабочую копию или ветку; при неожиданных изменениях уточни владельца. `.sov/` должен быть исключён из Git основной копии; проверь исключение до записи локальных артефактов. Если рабочая копия уже существует, сверяй её фактическое состояние и продолжай, а не создавай повторную.
2. Обнови сведения о remote (например, `git fetch <remote> <target>`), проверь актуальную целевую ветку и опубликованные требования, необходимые задаче. Для новой ветки выбери уникальное имя по правилам проекта и создай её **от актуальной удалённой целевой ветки**, затем worktree по пути `<основная папка>/.sov/worktree/<task-id>/` (например, `git worktree add -b <branch> <path> <remote>/<target>`). Не переключай основную копию и не сбрасывай её незакоммиченные изменения. Если имя или путь уже заняты, выясни происхождение, не удаляй и не переписывай их автоматически.
3. Передай оркестратору абсолютные пути к worktree и **общей** папке артефактов в основной копии. Код, `docs/` и `rules/` читай и меняй из worktree; список задач доступен через `sov-tasks` из основной папки, а локальные артефакты — по переданному абсолютному пути. Проверь, что worktree видит ресурсы SOV (скилы и шаблоны) по установленному пути; не считай `.sov/` внутри worktree копией общего хранилища. Запиши ветку, базу и пути в `task.md`, чтобы можно было продолжить работу после прерывания.

## Проверка и публикация

1. Перед публикацией сверь результат задачи и проверки с правилами проекта. Проверь `git status`, полный diff относительно актуальной целевой ветки, список коммитов, staged diff и состав PR: только согласованные файлы, без секретов, случайных локальных данных, `.sov/` и посторонних правок. Выполни `git diff --check` для рабочих изменений и `git diff --cached --check` после подготовки индекса. Сверь совместимость с обновлённой целевой веткой после `fetch`: отсутствие текстового конфликта само по себе не означает согласованность изменений. При расхождении согласуй способ обновления ветки, разреши конфликты без потери чужих изменений и повтори затронутые тесты, проверки и независимое ревью; не обходи блокирующие замечания.
2. Подготовь коммит только из проверенных файлов, отправь ветку и создай PR в **целевую ветку** средствами Git/GitHub (например, `gh pr create`). До создания PR проверь его базу, состав коммитов и diff от базы; если PR уже открыт, используй существующий. Запиши ссылку на PR в `task.md`. Проверь обязательные статусы GitHub и выполни предусмотренный правилами порядок согласования и слияния. Если параллельная задача успела слить свой PR, заново сверь актуальную целевую ветку и входы этой задачи: отсутствие конфликта Git не доказывает совместимость; при необходимости обнови ветку и повтори затронутые проверки и ревью до слияния. При изменении ветки, PR или разрешении конфликтов заново проверь затронутый результат и повтори необходимое независимое ревью перед слиянием.
3. После слияния проверь фактическое состояние PR в GitHub (`gh pr view`), целевую ветку и включение ожидаемого результата (учти разрешённый проектом способ слияния, включая squash/rebase). Запиши ссылку на PR, подтверждение слияния и целевую ветку в `task.md`; лишь затем оркестратор может отметить публикуемую задачу `done` через `sov-tasks`. Push, открытый или одобренный PR и успешные checks без слияния недостаточны. Если PR не слит, оставь задачу незавершённой с причиной ожидания или препятствием.

## Продолжение и очистка

- После прерывания сначала сравни `task.md` с `git status`, ветками, worktree, remote и фактическим состоянием PR (`gh pr view`, включая закрытый/слитый). Не повторяй push/создание PR или слияние только потому, что запись в артефакте отсутствует; выполни лишь незавершённые действия. Если remote недоступен, не выдавай локальную запись за подтверждение публикации. При изменении базы или коммитов проверь актуальность прежних тестов и ревью.
- Удаляй worktree только после подтверждения сохранности изменений: публикация подтверждена или непубликуемые результаты сохранены в согласованном месте; `git status` чист либо каждый оставшийся файл разобран и сохранён, артефакты доступны из основной папки. Используй обычное `git worktree remove <path>` и проверь `git worktree list`. Не применяй `--force`, `git reset --hard`, удаление папки вручную или удаление ветки с несохранённой работой ради очистки. При ошибке публикации сохрани рабочую копию и укажи препятствие. Ветку и PR удаляй только по правилам проекта после проверки, что они больше не нужны.

## Самопроверка сценариев

На пробном репозитории либо пошагово по инструкции проверь: новая задача берёт базу из актуальной целевой ветки, сохраняет незакоммиченные изменения основной копии и использует общие артефакты; повторный запуск узнаёт имеющуюся worktree; PR не создаётся из посторонних или служебных файлов; обновление базы вызывает нужные повторные проверки; открытый PR и слитый PR дают разные исходы; после прерывания слитый PR не публикуется повторно; worktree с несохранёнными изменениями или при ошибке публикации не удаляется. Запиши реальные проверки и их ограничения в артефакты задачи.
