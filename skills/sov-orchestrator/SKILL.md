# Оркестрация поручения SOV

Основной агент ведёт **одно поручение или одну выбранную задачу** от определения результата до отчёта либо обоснованной остановки. Используй скилы шагов для их предмета, [`sov-tasks`](../sov-tasks/SKILL.md) для общего учёта и [`sov-git`](../sov-git/SKILL.md) для рабочей копии и публикации; не подменяй их инструкции собственными правилами реализации. SOV не является программным движком: действия выполняются доступными инструментами среды. Не переходи к следующей задаче автоматически.

## Определи поручение и состояние

1. Уточни результат, границы допустимых действий и критерии по запросу, ранее принятым решениям, состоянию задачи и правилам **целевого проекта**. Кратко сообщи человеку, что собираешься сделать. Читай `AGENTS.md`, `rules/index.md`, применимые правила и документы из рабочей копии проекта; при конфликте правил с обязательными условиями SOV остановись и запроси решение. Вопросы, меняющие результат или полномочия, задавай по одному, по возможности с вариантами и свободным ответом; не переспрашивай уже решённое.
2. Обсуждение вариантов может завершиться ответом без задачи, файлов или worktree. Если ожидается сохраняемая работа, получи или создай запись **через `sov-tasks`** с учётом выбранного источника, зависимостей и условия публикации. Определи устойчивый идентификатор исполнителя по правилам проекта, не подменяй его ID сессии. Явно указанный ID проверь на статус и назначение: продолжи собственную `in_progress` после сверки состояния, при `blocked` сообщи препятствие, чужую не перехватывай; новую `planned` назначай лишь при выполнении условий начала. **При пустом запросе или просьбе продолжить без ID** сначала запроси у `sov-tasks` все `in_progress` и `blocked` задачи этого исполнителя, в том числе после перезагрузки и открытия новой сессии: единственную `in_progress` продолжи после сверки, при единственной `blocked` сообщи причину и условие возобновления без переключения; если их несколько, запроси ID и не выбирай следующую задачу молча. Лишь при нуле таких задач выбери первую доступную `planned`, назначь и начни через `sov-tasks`. Новый запрос без ID обрабатывай по его собственным границам, не подменяя его прежней задачей. Если источник недоступен или исполнитель неизвестен, не угадывай прежнюю задачу и не создавай новый список поверх возможной утраты. Отсутствие доступных задач и отсутствие созданного списка — разные состояния. Не читай и не меняй `.sov/ROADMAP.md` напрямую.
3. До изменения репозитория проверь фактическое состояние Git и существующую рабочую копию через `sov-git`. Для сохраняемой задачи создай, если требуется, **общую** папку `<основная папка>/.sov/tasks/<task-id>/`; путь к артефактам внутри worktree не считается общей папкой. Сохраняй в `task.md` по [`templates/task.md`](../../templates/task.md) запрос, решения человека, критерии, требования, правила, выбранный маршрут, основание выбора/пропуска шагов, пути, проверку входов и сведения для продолжения. Общий статус, назначение и зависимости получай у `sov-tasks`, не дублируй их вторым статусом в артефактах. Для задачи с изменениями кода или документов передай `sov-git` подготовку отдельной ветки и worktree от актуальной целевой ветки; при возобновлении сначала сверяй существующие объекты.

## Выбери маршрут и проверь переходы

Оцени запрос по **желаемому результату**, а не по имени команды: обсуждение фичи и подготовка требований — [`sov-spec`](../sov-spec/SKILL.md) → независимый [`sov-review-spec`](../sov-review-spec/SKILL.md) при публикации требований → отчёт человеку → публикация; подготовленная задача разработки — [`sov-plan`](../sov-plan/SKILL.md) → [`sov-implement`](../sov-implement/SKILL.md) → независимый [`sov-review-implementation`](../sov-review-implementation/SKILL.md); поиск причины бага — [`sov-research`](../sov-research/SKILL.md); поручение исправить баг — `sov-research → sov-plan → sov-implement → sov-review-implementation`. Простое обсуждение не требует формальных шагов. Исследование причины не даёт разрешения на исправление; подготовка требований и задач не запускает реализацию. Публикация нужна согласно поручению и правилам проекта, а не автоматически для каждого ответа или исследования.

Перед каждым шагом проверь, что обязательные входы относятся к этой задаче, актуальны, содержательны и согласованы. Для разработки нужны опубликованные применимые требования из `docs/specs/` целевой ветки либо другого опубликованного источника и пригодный `plan.md`; для исправления — достаточные свидетельства и вывод `research.md`. Локальный проект `spec.md` или пустой шаблон не заменяет опубликованные требования. Готовый результат шага можно использовать без повторения, только если он проверен и остаётся пригодным. В `task.md` отмечай результат проверки, состояние шагов и причину изменения маршрута. При изменении требований, результатов исследования, плана или базы ветки переоцени зависимые результаты и повтори затронутые шаги, проверки и ревью; не обходи открытое замечание изменением маршрута.

Если исправление требует **нового ожидаемого поведения**, вернись к `sov-spec` и `sov-review-spec` **до реализации**. Небольшое уточнение в пределах поручения может публиковаться в одном PR с реализацией после согласования и ревью требований; другие задачи не опираются на него до слияния PR. Существенное изменение оформляй отдельной связанной задачей с публикацией требований перед зависимой разработкой. Отдельный технический план не изменяет продуктовое требование.

## Передай шаг и прими результат

Для каждого исполнителя явно передай ID и название шага, ожидаемый результат и границы, критерии, **абсолютные** пути к рабочей копии и общей папке артефактов, конкретные требования и правила или точные пути к ним, допустимые изменения, нужный скил и ожидаемые выходы. Исполнитель читает собственные входы, записывает свои артефакты и сообщает изменённые файлы, реально выполненные проверки, вопросы и препятствия; не рассчитывай на неявную передачу контекста диалога. Основной агент общается с человеком и ведёт `task.md`.

Принимай шаг только после собственной проверки артефактов, актуальности входов и условий завершения, а не по сообщению «готово». Для реализации проверь успешность обязательных проверок в `checks.md` для текущего состояния изменений; ошибочная, недоступная или не запущенная обязательная проверка блокирует переход. Если план или исследование создаёт значительный риск переделки, правила либо человек требуют проверки, назначь независимую **адресную** перепроверку до реализации по соответствующему скилу: для причины — конкурирующие объяснения или неполное воспроизведение, для плана — миграция данных, публичные интерфейсы, труднообратимые действия или сложные межкомпонентные зависимости. Для исследования **без исправления** покажи человеку вывод, свидетельства и ограничения, предложи перепроверку; если её запрашивают, рассмотри результат до завершения. Причину без достаточных свидетельств называй гипотезой. Запиши основание назначения или пропуска промежуточной проверки в `task.md`.

`sov-review-spec` и `sov-review-implementation` всегда выполняют **независимые субагенты**, не готовившие проверяемый результат. Если независимый исполнитель недоступен, зафиксируй препятствие; самопроверка не заменяет обязательное ревью. Передай проверяющему точное состояние файлов, включая незакоммиченные изменения, и свидетельства; проверь заполненный `review.md` и самостоятельно сопоставь вывод с результатом шага. Критичные и средние замечания блокируют переход и публикацию; низкие устраняются либо явно откладываются. Возвращай ошибки требований в `sov-spec`, исследования — в `sov-research`, технического решения — в `sov-plan`, реализации и затронутых документов — в `sov-implement`. После исправления запрашивай у независимого проверяющего повторную проверку затронутого состояния и закрытие либо обоснованное снятие блокирующих замечаний в `review.md`.

## Опубликуй и заверши

Перед публикацией **новых или изменённых продуктовых требований**, после необходимых проверок покажи человеку итоговый текст либо точную ссылку на полный текст и отражённые решения; дай возможность указать расхождения. При расхождении верни требования на `sov-spec`, повтори затронутые проверки и `sov-review-spec` до публикации. Формального подтверждения сверх этого не требуй, если его не требуют правила проекта.

Для публикуемой задачи через `sov-git` проверь полный состав изменений и коммитов относительно актуальной целевой ветки, отсутствие секретов и локальных данных, совместимость, обязательные проверки GitHub и необходимые решения человека. После обновления ветки или PR повтори затронутые проверки и независимое ревью. Создай или продолжи существующий PR и доведи его до **подтверждённого слияния**; push, открытый PR или успешные проверки не равны публикации. Запиши ссылку на PR, целевую ветку и подтверждение слияния в `task.md`, только затем переводи запись в `done` через `sov-tasks`. Для непубликуемой задачи заверши её после достижения результата и выполнения применимых условий. Удаляй worktree через `sov-git` только после проверки сохранности результатов.

Если работа прервана, в новой сессии сначала найди запись через `sov-tasks`, сверь `task.md` и артефакты с фактическими файлами, Git и состоянием PR, а общий статус и назначение — с `sov-tasks`. Уже слитый PR не создавай заново из-за пропущенной записи: подтверди слияние и заверши оставшиеся действия. Продолжай с первого незавершённого или утратившего пригодность шага. При отсутствии или противоречии записи, артефактов или рабочей копии остановись для выяснения фактов, не выдавая начало другой задачи за продолжение прежней. При внешней блокировке, отсутствии инструмента, неустранённой обязательной проверке или повторных неудачах сохрани причину, сделанное, следующий шаг и условие возобновления в `task.md`, отрази блокировку через `sov-tasks` при необходимости; не объявляй частичный результат завершением.

Отчитайся простым языком: какое поручение выполнено, результат для пользователя, проверенные факты, состояние публикации и ограничения. При подготовке требований прямо скажи, что поведение программы ещё не изменено. При остановке сообщи препятствие и точку продолжения; если нужно действие, назови **один** конкретный следующий шаг, используя только реально установленный интерфейс SOV.

## Контрольные сценарии

- **Спецификация с задачами:** запрос ограничен требованиями → `sov-spec` согласует сценарии и создаёт задачи через `sov-tasks`; отдельный субагент проверяет требования и покрытие; человек видит итоговый текст перед PR; задачи разработки не начинаются до подтверждённого слияния PR требований.
- **Подготовленная разработка:** опубликованные требования и пригодный план → реализация с успешными обязательными проверками → независимое ревью результата → PR; запись `done` допустима лишь после подтверждённого слияния. Среднее замечание возвращает работу на ответственный шаг с повтором проверки.
- **Баг без исправления / с исправлением:** только поиск причины заканчивается отчётом со свидетельствами и предложением перепроверки, без `sov-plan` и кода; запрос исправить ошибку использует `research.md` как вход плана, а при нехватке свидетельств останавливается или возвращается к исследованию.
- **Возобновление в новой сессии:** `/sov` без ID сначала получает через `sov-tasks` задачи устойчивого исполнителя; одна `in_progress` продолжается после сверки worktree, артефактов, статуса и GitHub (слитый PR не публикуется повторно); единственная `blocked` возвращает препятствие без выбора другой; несколько незавершённых задач требуют ID; только при нуле таких задач выбирается новая `planned`.
