# Оркестрация поручения SOV

Основной агент ведёт **одно поручение или одну выбранную задачу** от определения результата до отчёта либо обоснованной остановки. Используй скилы шагов для их предмета, [`sov-tasks`](../sov-tasks/SKILL.md) для общего учёта и [`sov-git`](../sov-git/SKILL.md) для рабочей копии и публикации; не подменяй их инструкции собственными правилами реализации. SOV не является программным движком: действия выполняются доступными инструментами среды. Не переходи к следующей задаче автоматически.

## Определи поручение и состояние

1. Уточни результат, границы допустимых действий и критерии по запросу, ранее принятым решениям, состоянию задачи и правилам **целевого проекта**. Кратко сообщи человеку, что собираешься сделать. Прежде чем создавать или назначать задачу, проверь разрешения текущего основного режима: в `plan` можно обсуждать и читать, но сохраняемое поручение, требующее записи списка, артефактов, кода или публикации, не начинай и не передавай пишущему субагенту в обход режима; сообщи о необходимости продолжить в `build`. Читай `AGENTS.md`, `rules/index.md`, применимые правила и документы из рабочей копии проекта; при конфликте правил с обязательными условиями SOV остановись и запроси решение. Вопросы, меняющие результат или полномочия, задавай по одному, по возможности с вариантами и свободным ответом; не переспрашивай уже решённое.
2. Обсуждение вариантов может завершиться ответом без задачи, файлов или worktree. Если ожидается сохраняемая работа, **до обращения к списку задач** установи выбранный устойчивый ID исполнителя по правилам проекта. Если настроено несколько рабочих слотов одного разработчика, человек явно выбирает слот для данного поручения или возобновления; допустим однозначный выбор по установленному проектом правилу. Не выводи его из ID сессии, текущей worktree либо того, у какого ID уже есть `in_progress`: при неясном выборе запроси слот и не создавай, не назначай и не продолжай задачу до ответа. Каждый одновременно работающий независимый координатор, в том числе одного человека, использует отдельный постоянный слот; два координатора одного слота не работают параллельно. Получи или создай запись **через `sov-tasks`** с учётом выбранного источника, зависимостей и условия публикации. Для файлового источника до работы проверь зафиксированные версию SOV, общий CLI, `state-dir` и доступность протокола; при ошибке не редактируй список напрямую. Явно указанный ID задачи проверь на статус и назначение: продолжи `in_progress` выбранного слота после сверки состояния, при `blocked` сообщи препятствие, назначение другого слота не перехватывай; новую `planned` назначай лишь при выполнении условий начала. **При пустом запросе или просьбе продолжить без ID задачи** сначала запроси у `sov-tasks` все `in_progress` и `blocked` задачи выбранного слота, в том числе после перезагрузки и открытия новой сессии: единственную `in_progress` продолжи после сверки, при единственной `blocked` сообщи причину и условие возобновления без переключения; если их несколько, запроси ID задачи и не выбирай следующую задачу молча. Лишь при нуле таких задач выбери первую доступную `planned`, назначь и начни через `sov-tasks` **после подтверждённой записи назначения**; при конфликте пересмотри выбор. Новый запрос без ID задачи обрабатывай по его собственным границам, не подменяя его прежней задачей. Если источник недоступен или слот неизвестен, не угадывай прежнюю задачу и не создавай новый список поверх возможной утраты. Отсутствие доступных задач и отсутствие созданного списка — разные состояния. Не читай и не меняй `.sov/ROADMAP.md` напрямую.
3. До изменения репозитория проверь фактическое состояние Git и существующую рабочую копию через `sov-git`. После подтверждения создания строки, если требуется, создай **общую** папку `<основная папка>/.sov/tasks/<task-id>/`; работу над `planned` начинай только после подтверждённого назначения. Путь к артефактам внутри worktree не считается общей папкой. При создании задачи до появления её ID сохраняй контекст намерения в материале поручения/сессии: при потере ответа `sov-tasks` должен сопоставить результат по свежему списку и остановиться, если совпадающие строки неразличимы. Сохраняй в `task.md` по [`templates/task.md`](../../templates/task.md) запрос, выбранный слот как контекст продолжения (не второй статус или назначение), решения человека, критерии, требования, правила, выбранный маршрут, основание выбора/пропуска шагов, пути, проверку входов, фактические уровни и модели выполненных шагов и сведения для продолжения. Общий статус, назначение и зависимости получай у `sov-tasks`, не дублируй их вторым статусом в артефактах. Для задачи с изменениями кода или документов передай `sov-git` подготовку отдельной ветки и worktree от актуальной целевой ветки **после подтверждённого назначения**; при возобновлении сначала сверяй существующие объекты.

## Выбери маршрут и проверь переходы

Оцени запрос по **желаемому результату**, а не по имени команды: обсуждение фичи и подготовка требований — [`sov-spec`](../sov-spec/SKILL.md) → независимый [`sov-review-spec`](../sov-review-spec/SKILL.md) при публикации требований → отчёт человеку → публикация; подготовленная задача разработки — [`sov-plan`](../sov-plan/SKILL.md) → [`sov-implement`](../sov-implement/SKILL.md) → независимый [`sov-review-implementation`](../sov-review-implementation/SKILL.md); поиск причины бага — [`sov-research`](../sov-research/SKILL.md); поручение исправить баг — `sov-research → sov-plan → sov-implement → sov-review-implementation`. Простое обсуждение не требует формальных шагов. Исследование причины не даёт разрешения на исправление; подготовка требований и задач не запускает реализацию. Публикация нужна согласно поручению и правилам проекта, а не автоматически для каждого ответа или исследования.

Перед каждым шагом проверь, что обязательные входы относятся к этой задаче, актуальны, содержательны и согласованы. Для `sov-research` установи ожидаемое поведение из поручения и применимых опубликованных требований; для `sov-plan` нужны определённое ожидаемое поведение и, при исправлении, пригодный обоснованный вывод `research.md` с достаточными свидетельствами. Для новой функциональности ожидаемое поведение должно быть опубликовано в `docs/specs/` целевой ветки либо ином применимом источнике. Для однозначного бага без отдельной спецификации зафиксируй ожидаемое поведение в `task.md`, сверь его с исследованием и проверь отсутствие противоречия с опубликованными источниками. Перед `sov-implement` обязателен актуальный пригодный `plan.md`; до подготовки плана не требуй его. Перед итоговым ревью необходимы успешные обязательные проверки текущего состояния. Локальный проект `spec.md` или пустой шаблон не заменяет опубликованные требования новой функциональности. Готовый результат шага можно использовать без повторения, только если он проверен и остаётся пригодным. В `task.md` отмечай результат проверки, состояние шагов и причину изменения маршрута. При изменении требований, результатов исследования, плана или базы ветки переоцени зависимые результаты и повтори затронутые шаги, проверки и ревью; не обходи открытое замечание изменением маршрута.

Если ожидаемое поведение при исправлении **неясно, противоречит опубликованному или должно измениться**, вернись к `sov-spec` и `sov-review-spec` **до реализации**. Небольшое уточнение в пределах поручения может публиковаться в одном PR с реализацией после согласования и ревью требований; другие задачи не опираются на него до слияния PR. Существенное изменение оформляй отдельной связанной задачей с публикацией требований перед зависимой разработкой. Отдельный технический план не изменяет продуктовое требование.

## Передай шаг и прими результат

Работай в текущем основном агенте OpenCode и наследуй его модель; `/sov*` не меняют `build`/`plan`, `default_agent` или модель основного агента. Для **каждого формального шага** выбери и вызови отдельный проектный субагент `sov-advanced` для `sov-spec`, `sov-research`, `sov-implement`, `sov-review-spec` и `sov-review-implementation`; `sov-standard` — для обычного `sov-plan`. План с миграцией данных, публичным интерфейсом, труднообратимыми действиями или сложными межкомпонентными зависимостями поручай `sov-advanced` и запиши обоснование повышения. Если риск выявился уже в ходе `sov-plan` на `standard`, передай подготовленный материал и оставшееся решение `advanced` до принятия плана. Адресную независимую перепроверку исследования поручай `sov-advanced`, перепроверку плана — отдельному проверяющему уровня проверяемого плана. `sov-tasks`, `sov-git` и `sov-okf` — вспомогательные скилы ответственного агента, а не дополнительные субагенты с собственными моделями. Если результат уже существует и проверен, не запускай шаг только ради вызова субагента.

Перед вызовом сверь настроенный в **целевом проекте** уровень, модель и доступность субагента; если модель или агент недоступны, сообщи о препятствии, не замещай его общим субагентом или моделью основного агента молча. В режиме `plan` не поручай субагенту запись файлов, изменение задач, кода или публикацию в обход разрешений основного режима: выполни доступное обсуждение/чтение и сообщи о необходимости перехода в `build` для изменяющих действий. Для каждого исполнителя явно передай ID и название шага, выбранный уровень, ожидаемый результат и границы, критерии, **абсолютные** пути к рабочей копии и общей папке артефактов, конкретные требования и правила или точные пути к ним, допустимые изменения, нужный скил и ожидаемые выходы. Исполнитель читает собственные входы, записывает свои артефакты и сообщает изменённые файлы, реально выполненные проверки, вопросы и препятствия; не рассчитывай на неявную передачу контекста диалога. Основной агент общается с человеком и ведёт `task.md`. Зафиксируй фактически использованные уровень и ID модели по каждому шагу в `task.md`; при возобновлении сверяй настройки с сохранёнными сведениями и не подменяй модель старого результата новой.

Принимай шаг только после собственной проверки артефактов, актуальности входов и условий завершения, а не по сообщению «готово». Для реализации проверь успешность обязательных проверок в `checks.md` для текущего состояния изменений; ошибочная, недоступная или не запущенная обязательная проверка блокирует переход. Если план или исследование создаёт значительный риск переделки, правила либо человек требуют проверки, назначь независимую **адресную** перепроверку до реализации по соответствующему скилу: для причины — конкурирующие объяснения или неполное воспроизведение, для плана — миграция данных, публичные интерфейсы, труднообратимые действия или сложные межкомпонентные зависимости. Для исследования **без исправления** покажи человеку вывод, свидетельства и ограничения, предложи перепроверку; если её запрашивают, рассмотри результат до завершения. Причину без достаточных свидетельств называй гипотезой. Запиши основание назначения или пропуска промежуточной проверки в `task.md`.

`sov-review-spec` и `sov-review-implementation` всегда выполняют **новые независимые вызовы субагента `sov-advanced`**, не готовившие проверяемый результат (совпадение имени типа субагента не делает два вызова одним исполнителем). Если независимый исполнитель недоступен, зафиксируй препятствие; самопроверка не заменяет обязательное ревью. Передай проверяющему точное состояние файлов, включая незакоммиченные изменения, и свидетельства; проверь в общем `review.md` отдельные датированные записи по видам проверок, проверяемым шагам и исполнителям, ссылки повторных проверок на замечания и последнее состояние каждого замечания. Не принимай позднюю проверку другого шага за снятие прежнего замечания: критичные и средние замечания, остающиеся открытыми для перехода, блокируют его и публикацию; низкие устраняются либо явно откладываются. Возвращай ошибки требований в `sov-spec`, исследования — в `sov-research`, технического решения — в `sov-plan`, реализации и затронутых документов — в `sov-implement`. После исправления запрашивай у независимого проверяющего повторную проверку затронутого состояния и отдельную запись о закрытии либо обоснованном снятии блокирующих замечаний в `review.md`, сохраняя прежние выводы.

## Опубликуй и заверши

Перед публикацией **новых или изменённых продуктовых требований**, после необходимых проверок покажи человеку итоговый текст либо точную ссылку на полный текст и отражённые решения; дай возможность указать расхождения. При расхождении верни требования на `sov-spec`, повтори затронутые проверки и `sov-review-spec` до публикации. Формального подтверждения сверх этого не требуй, если его не требуют правила проекта.

Для публикуемой задачи через `sov-git` проверь полный состав изменений и коммитов относительно актуальной целевой ветки, отсутствие секретов и локальных данных, совместимость, обязательные проверки GitHub и необходимые решения человека. После обновления ветки или PR повтори затронутые проверки и независимое ревью. Создай или продолжи существующий PR и доведи его до **подтверждённого слияния**; push, открытый PR или успешные проверки не равны публикации. Запиши ссылку на PR, целевую ветку и подтверждение слияния в `task.md`, только затем переводи запись в `done` через `sov-tasks`. Для непубликуемой задачи заверши её после достижения результата и выполнения применимых условий. Удаляй worktree через `sov-git` только после проверки сохранности результатов.

Если работа прервана или потерян ответ записи, в новой сессии сначала установи слот, затем найди запись через `sov-tasks`, сверь выбранный слот и ID задачи с назначением в очереди, `task.md` и артефакты с фактическими файлами, Git и состоянием PR, а общий статус и назначение — с новым чтением через `sov-tasks`; не повторяй запись вслепую. Если у того же человека есть другой слот с активной задачей, не считай её своей и не используй её worktree. После подтверждённого создания строки без папки задачи доведи `task.md` до согласованного состояния; не создавай вторую строку. Уже слитый PR не создавай заново из-за пропущенной записи: подтверди слияние и заверши оставшиеся действия. Продолжай с первого незавершённого или утратившего пригодность шага. При отсутствии или противоречии записи, артефактов или рабочей копии остановись для выяснения фактов, не выдавая начало другой задачи за продолжение прежней. При внешней блокировке, отсутствии инструмента, неустранённой обязательной проверке или повторных неудачах сохрани причину, сделанное, следующий шаг и условие возобновления в `task.md`, отрази блокировку через `sov-tasks` при необходимости; не объявляй частичный результат завершением.

Отчитайся простым языком: какое поручение выполнено, результат для пользователя, проверенные факты, состояние публикации и ограничения. При подготовке требований прямо скажи, что поведение программы ещё не изменено. При остановке сообщи препятствие и точку продолжения; если нужно действие, назови **один** конкретный следующий шаг, используя только реально установленный интерфейс SOV.

## Контрольные сценарии

- **Спецификация с задачами:** запрос ограничен требованиями → `sov-spec` согласует сценарии и создаёт задачи через `sov-tasks`; отдельный субагент проверяет требования и покрытие; человек видит итоговый текст перед PR; задачи разработки не начинаются до подтверждённого слияния PR требований.
- **Подготовленная разработка:** опубликованные требования → `sov-plan` создаёт пригодный план → реализация с успешными обязательными проверками → независимое ревью результата → PR; запись `done` допустима лишь после подтверждённого слияния. Среднее замечание возвращает работу на ответственный шаг с повтором проверки.
- **Баг без исправления / с исправлением:** только поиск причины заканчивается отчётом со свидетельствами и предложением перепроверки, без `sov-plan` и кода; однозначный баг без отдельной опубликованной спецификации использует ожидаемое поведение из `task.md` и пригодный `research.md` как вход плана, затем план — как вход реализации. При нехватке свидетельств вернись к исследованию; при неясном или противоречащем требованиям поведении согласуй требования через `sov-spec` и `sov-review-spec` до реализации.
- **Баг с опубликованным требованием:** сверь `research.md` с применимым опубликованным поведением → `sov-plan` → `sov-implement` с пригодным планом → ревью. Если предлагаемое исправление меняет опубликованное правило, сначала согласуй изменение и проверь его через `sov-review-spec`.
- **Возобновление в новой сессии:** при нескольких слотах `/sov` без выбранного слота сначала запрашивает его; затем без ID задачи получает через `sov-tasks` задачи только выбранного устойчивого исполнителя. Одна `in_progress` продолжается после сверки worktree, артефактов, статуса и GitHub (слитый PR не публикуется повторно); единственная `blocked` возвращает препятствие без выбора другой; несколько незавершённых задач требуют ID задачи; только при нуле таких задач выбирается новая `planned`. Задача другого слота, даже того же человека, не возобновляется без явной смены назначения.
