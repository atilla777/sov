# Оркестрация поручения SOV

Основной агент ведёт **одно поручение или одну выбранную задачу** от определения результата до отчёта либо обоснованной остановки. Используй скилы шагов для их предмета, [`sov-tasks`](../sov-tasks/SKILL.md) для общего учёта и [`sov-git`](../sov-git/SKILL.md) для рабочей копии и публикации; не подменяй их инструкции собственными правилами реализации. SOV не является программным движком: действия выполняются доступными инструментами среды. Не переходи к следующей задаче автоматически.

`/sov-fast` — единственный вход, позволяющий оркестратору самостоятельно пропускать отдельные шаги при низком риске. Без него обычный маршрут обязателен; предложенный пропуск требует отдельного согласия человека **для конкретной задачи**, с записью решения в `task.md`. Для согласованных исключений используй те же требования к свидетельствам и входам, что при пропуске в `/sov-fast`, но не считай их разрешением самостоятельно пропустить другие шаги. Отсутствие ответа не означает согласия. Проектные правила могут требовать большего. Команды не меняют основную модель или режим OpenCode.

## Определи поручение и состояние

1. Уточни результат, границы допустимых действий и критерии по запросу, ранее принятым решениям, состоянию задачи и правилам **целевого проекта**. Кратко сообщи человеку, что собираешься сделать. Прежде чем создавать или назначать задачу, проверь разрешения текущего основного режима: в `plan` можно обсуждать и читать, но сохраняемое поручение, требующее записи списка, артефактов, кода или публикации, не начинай и не передавай пишущему субагенту в обход режима; сообщи о необходимости продолжить в `build`. Читай `AGENTS.md`, `rules/index.md`, применимые правила и документы из рабочей копии проекта; при конфликте правил с обязательными условиями SOV остановись и запроси решение. Вопросы, меняющие результат или полномочия, задавай по одному, по возможности с вариантами и свободным ответом; не переспрашивай уже решённое.
2. Обсуждение вариантов может завершиться ответом без задачи, файлов или worktree. Если ожидается сохраняемая работа, установи устойчивый ID владельца по правилам проекта и получи **новый UUID текущего запуска основного агента** через `sov-state session-id` после проверки закреплённой версии CLI. Один вызов на запуск, не один на задачу и не один на субагента; не копируй UUID прежней сессии. Для файлового источника до работы проверь зафиксированные версию SOV, общий CLI, `state-dir` и доступность протокола; при ошибке не редактируй список напрямую. Получи или создай запись **через `sov-tasks`** с учётом выбранного источника, зависимостей и условия публикации. Явно указанный ID задачи проверь на статус, владельца и захват: продолжай `in_progress` только после подтверждённого захвата этим UUID; при чужом захвате остановись до безопасной передачи, при `blocked` сообщи препятствие; новую `planned` назначай лишь при выполнении условий начала. **При пустом запросе или просьбе продолжить без ID задачи** сначала запроси у `sov-tasks` все `in_progress` и `blocked` задачи устойчивого владельца, в том числе после перезагрузки и открытия новой сессии: при единственной `in_progress` сверь её состояние и получи захват перед работой, при единственной `blocked` сообщи препятствие и условие возобновления; если их несколько, запроси ID задачи и не выбирай следующую молча. Лишь при нуле таких задач выбери первую доступную `planned`, назначь и начни через `sov-tasks` **после подтверждённого назначения с захватом**; при конфликте пересмотри выбор. Новый запрос без ID задачи обрабатывай по его собственным границам, не подменяя его прежней задачей: независимая новая задача может начаться, даже если другая задача того же владельца выполняется в иной сессии. Если источник недоступен или владелец неизвестен, не угадывай прежнюю задачу и не создавай новый список поверх возможной утраты. Отсутствие доступных задач и отсутствие созданного списка — разные состояния. Не читай и не меняй `.sov/ROADMAP.md` напрямую.
3. До изменения репозитория проверь фактическое состояние Git и существующую рабочую копию через `sov-git`. После подтверждения создания строки, если требуется, создай **общую** папку `<основная папка>/.sov/tasks/<task-id>/`; работу над `planned` начинай только после подтверждённых назначения и захвата. Путь к артефактам внутри worktree не считается общей папкой. При создании задачи до появления её ID сохраняй контекст намерения в материале поручения/сессии: при потере ответа `sov-tasks` должен сопоставить результат по свежему списку и остановиться, если совпадающие строки неразличимы. Сохраняй в `task.md` по [`templates/task.md`](../../templates/task.md) запрос, контекст получения или передачи захвата (не второй общий статус), решения человека, критерии, требования, правила, выбранный маршрут, основание выбора/пропуска шагов, пути, проверку входов, фактические уровни и модели выполненных шагов и сведения для продолжения. Общий статус, владелец, UUID захвата и зависимости получай у `sov-tasks`, не дублируй их вторым статусом в артефактах. Перед каждым шагом, записью артефактов и операцией Git задачи перепроверяй текущий захват через `sov-tasks`: если он сменился, остановись; передавай UUID своего захвата субагенту вместе с ID задачи. Для задачи с изменениями кода или документов передай `sov-git` подготовку отдельной ветки и worktree от актуальной целевой ветки **после подтверждённого захвата**; при возобновлении сначала сверяй существующие объекты.

Отделяй обсуждение и временный эксперимент вне файлов репозитория от сохраняемой работы. Изменение файлов проекта, в том числе документации и конфигурации, веди как задачу с учётом правил ветки и PR; не оставляй отклонённые временные изменения в итоговом diff и не удаляй чужую работу. При продолжении сверяй сохранённый режим задачи: быстрый режим не наследуется новой задачей, а при отсутствии подтверждения первоначального `/sov-fast` используй обычный маршрут либо спроси человека.

## Выбери маршрут и проверь переходы

Оцени запрос по **желаемому результату**, а не по имени команды: обсуждение фичи и подготовка требований — [`sov-spec`](../sov-spec/SKILL.md) → независимый [`sov-review-spec`](../sov-review-spec/SKILL.md) при публикации требований → отчёт человеку → публикация; подготовленная задача разработки — [`sov-plan`](../sov-plan/SKILL.md) → [`sov-implement`](../sov-implement/SKILL.md) → независимый [`sov-review-implementation`](../sov-review-implementation/SKILL.md); поиск причины бага — [`sov-research`](../sov-research/SKILL.md); поручение исправить баг — `sov-research → sov-plan → sov-implement → sov-review-implementation`. Простое обсуждение не требует формальных шагов. Исследование причины не даёт разрешения на исправление; подготовка требований и задач не запускает реализацию. Публикация нужна согласно поручению и правилам проекта, а не автоматически для каждого ответа или исследования.

Перед каждым выполняемым шагом проверь, что обязательные входы относятся к этой задаче, актуальны, содержательны и согласованы. Для `sov-research` установи ожидаемое поведение из поручения и применимых опубликованных требований; для `sov-plan` нужны определённое ожидаемое поведение и, в обычном маршруте исправления, пригодный обоснованный вывод `research.md` с достаточными свидетельствами. Для новой функциональности ожидаемое поведение должно быть опубликовано в `docs/specs/` целевой ветки либо ином применимом источнике. Для однозначного бага без отдельной спецификации зафиксируй ожидаемое поведение в `task.md`, сверь его со свидетельствами и проверь отсутствие противоречия с опубликованными источниками. Перед `sov-implement` в обычном маршруте обязателен актуальный пригодный `plan.md`; в быстром режиме при его пропуске — пригодное решение и проверки в `task.md`. До подготовки плана не требуй его. Перед назначенным итоговым ревью необходимы успешные обязательные проверки текущего состояния. Локальный проект `spec.md` или пустой шаблон не заменяет опубликованные требования новой функциональности. Готовый результат шага можно использовать без повторения, только если он проверен и остаётся пригодным. В `task.md` отмечай результат проверки, состояние шагов и причину изменения маршрута. При изменении требований, результатов исследования, плана или базы ветки переоцени зависимые результаты и повтори затронутые шаги, проверки и ревью; не обходи открытое замечание изменением маршрута.

Если ожидаемое поведение при исправлении **неясно, противоречит опубликованному или должно измениться**, вернись к `sov-spec` и `sov-review-spec` **до реализации**. Небольшое уточнение в пределах поручения может публиковаться в одном PR с реализацией после согласования и ревью требований; другие задачи не опираются на него до слияния PR. Существенное изменение оформляй отдельной связанной задачей с публикацией требований перед зависимой разработкой. Отдельный технический план не изменяет продуктовое требование.

### Быстрый маршрут по явному `/sov-fast`

Для небольшой, ясной и обратимой задачи сначала установи ожидаемый результат и факты, позволяющие выбрать решение. Запиши в коротком `task.md` границы, риск, применимые проверки и причину выбора или пропуска `sov-research`, `sov-plan`, итогового ревью. Если причина/решение очевидны и проверены доступными свидетельствами, отдельные `research.md` и `plan.md` не создавай ради формы. При неполном воспроизведении, конкурирующих причинах/решениях, миграции данных, труднообратимом действии, сложных зависимостях или новом продуктовом поведении переходи к необходимым формальным шагам до продолжения; уже пригодные факты переиспользуй. Не выдавай гипотезу за установленную причину.

Если формальный `sov-implement` не назначен, выполни небольшое изменение и применимые проверки в основном агенте, запиши их результаты в `checks.md` с привязкой к состоянию файлов. Это непосредственное исполнение задачи, а не выполненный субагентом шаг. Если назначаешь формальный шаг после обоснованного пропуска исследования или плана, передай исполнителю запись решения и свидетельств из `task.md` вместо отсутствующего файла. Для документационной правки проверяй содержание, ссылки и оформление, а не игровые тесты; для изменения hook проверяй действительный непустой push и отказ при ошибке, если меняется блокировка push. Засчитывай успешные hook и CI для **того же** состояния и проверенных ими команд без повторного ручного прогона, указывая commit/диапазон, условия и результат. После изменения кода/конфигурации или базы повторяй затронутые проверки; если правила проекта прямо требуют отдельного ручного запуска, согласуй конфликт, а не пропускай его молча.

Итоговое независимое ревью обязательно для разработки **основного кода игры или движка** даже в быстром режиме. В остальных задачах назначь его, когда ошибка может затронуть чужие hooks/проверки, данные, публичные интерфейсы, труднообратимые действия либо последствия неясны; пример — установщик pre-push, меняющий действующие hooks. При пропуске ревью самостоятельно сверь полный diff с результатом и правилами, проверки с текущим состоянием и отсутствие посторонних файлов; зафиксируй решение, не называя самопроверку независимой. Проектные требования к обязательному ревью и согласованию требований остаются в силе; открытые блокирующие замечания не исчезают при смене маршрута.

## Передай шаг и прими результат

Работай в текущем основном агенте OpenCode и наследуй его модель; `/sov*` не меняют `build`/`plan`, `default_agent` или модель основного агента. Для **каждого формального шага** выбери и вызови отдельный проектный субагент `sov-advanced` для `sov-spec`, `sov-research`, `sov-implement`, `sov-review-spec` и `sov-review-implementation`; `sov-standard` — для обычного `sov-plan`. План с миграцией данных, публичным интерфейсом, труднообратимыми действиями или сложными межкомпонентными зависимостями поручай `sov-advanced` и запиши обоснование повышения. Если риск выявился уже в ходе `sov-plan` на `standard`, передай подготовленный материал и оставшееся решение `advanced` до принятия плана. Адресную независимую перепроверку исследования поручай `sov-advanced`, перепроверку плана — отдельному проверяющему уровня проверяемого плана. `sov-tasks`, `sov-git` и `sov-okf` — вспомогательные скилы ответственного агента, а не дополнительные субагенты с собственными моделями. Если результат уже существует и проверен, не запускай шаг только ради вызова субагента.

Перед вызовом сверь настроенный в **целевом проекте** уровень, модель и доступность субагента; если модель или агент недоступны, сообщи о препятствии, не замещай его общим субагентом или моделью основного агента молча. В режиме `plan` не поручай субагенту запись файлов, изменение задач, кода или публикацию в обход разрешений основного режима: выполни доступное обсуждение/чтение и сообщи о необходимости перехода в `build` для изменяющих действий. Для каждого исполнителя явно передай ID и название шага, выбранный уровень, ожидаемый результат и границы, критерии, **абсолютные** пути к рабочей копии и общей папке артефактов, конкретные требования и правила или точные пути к ним, допустимые изменения, нужный скил и ожидаемые выходы. Исполнитель читает собственные входы, записывает свои артефакты и сообщает изменённые файлы, реально выполненные проверки, вопросы и препятствия; не рассчитывай на неявную передачу контекста диалога. Основной агент общается с человеком и ведёт `task.md`. Зафиксируй фактически использованные уровень и ID модели по каждому шагу в `task.md`; при возобновлении сверяй настройки с сохранёнными сведениями и не подменяй модель старого результата новой.

Принимай шаг только после собственной проверки артефактов, актуальности входов и условий завершения, а не по сообщению «готово». Для реализации проверь успешность обязательных проверок в `checks.md` для текущего состояния изменений; ошибочная, недоступная или не запущенная обязательная проверка блокирует переход. Если план или исследование создаёт значительный риск переделки, правила либо человек требуют проверки, назначь независимую **адресную** перепроверку до реализации по соответствующему скилу: для причины — конкурирующие объяснения или неполное воспроизведение, для плана — миграция данных, публичные интерфейсы, труднообратимые действия или сложные межкомпонентные зависимости. Для исследования **без исправления** покажи человеку вывод, свидетельства и ограничения, предложи перепроверку; если её запрашивают, рассмотри результат до завершения. Причину без достаточных свидетельств называй гипотезой. Запиши основание назначения или пропуска промежуточной проверки в `task.md`.

Если `sov-review-spec` или `sov-review-implementation` обязателен либо назначен, проводи **новый независимый вызов субагента `sov-advanced`**, не готовившего проверяемый результат (совпадение имени типа субагента не делает два вызова одним исполнителем). Если независимый исполнитель недоступен, зафиксируй препятствие; самопроверка не заменяет обязательное ревью. Передай проверяющему точное состояние файлов, включая незакоммиченные изменения, и свидетельства; проверь в общем `review.md` отдельные датированные записи по видам проверок, проверяемым шагам и исполнителям, ссылки повторных проверок на замечания и последнее состояние каждого замечания. Не принимай позднюю проверку другого шага за снятие прежнего замечания: критичные и средние замечания, остающиеся открытыми для перехода, блокируют его и публикацию; низкие устраняются либо явно откладываются. Возвращай ошибки требований в `sov-spec`, исследования — в `sov-research`, технического решения — в `sov-plan`, реализации и затронутых документов — в `sov-implement` или в непосредственное быстрое исполнение. После исправления запрашивай у независимого проверяющего повторную проверку затронутого состояния и запись о закрытии либо обоснованном снятии блокирующих замечаний в `review.md`, сохраняя прежние выводы.

## Опубликуй и заверши

До первого слияния исправления в границах задачи остаются в той же задаче и существующем PR: не заводи вторую задачу только из-за коммита, замечания или повторного push. После изменения повтори затронутые проверки и назначенное ревью; если его не было и риск вырос, назначь его. При проверке условий публикации ниже упоминание повторного независимого ревью относится к обязательному либо назначенному ревью, а не превращает обоснованно пропущенное в обязательное. Новые/изменённые требования всё равно проходят `sov-spec` и `sov-review-spec`.

Перед публикацией **новых или изменённых продуктовых требований**, после необходимых проверок покажи человеку итоговый текст либо точную ссылку на полный текст и отражённые решения; дай возможность указать расхождения. При расхождении верни требования на `sov-spec`, повтори затронутые проверки и `sov-review-spec` до публикации. Формального подтверждения сверх этого не требуй, если его не требуют правила проекта.

Для публикуемой задачи через `sov-git` проверь полный состав изменений и коммитов относительно актуальной целевой ветки, отсутствие секретов и локальных данных, совместимость, обязательные проверки GitHub и необходимые решения человека. После обновления ветки или PR повтори затронутые проверки и независимое ревью. Создай или продолжи существующий PR и доведи его до **подтверждённого слияния**; push, открытый PR или успешные проверки не равны публикации. Запиши ссылку на PR, целевую ветку и подтверждение слияния в `task.md`, только затем переводи запись в `done` через `sov-tasks` с освобождением захвата в том же commit. Для непубликуемой задачи заверши её после достижения результата и выполнения применимых условий. Удаляй worktree через `sov-git` только после проверки сохранности результатов. При штатном завершении сеанса до завершения задачи сначала сохрани контекст, затем условно освободи захват; если освобождение не подтверждено, сообщи о занятой задаче для безопасного продолжения.

Если работа прервана или потерян ответ записи, в новой сессии найди запись по владельцу через `sov-tasks`, сверь ID задачи и захват, `task.md` и артефакты с фактическими файлами, Git и состоянием PR; не повторяй запись вслепую. Сначала получи собственный захват по правилам `sov-tasks`, только затем меняй артефакты или worktree. Чужой активный UUID не перехватывай по времени, владельцу или одному PID: если старый координатор мог продолжить запись, сообщи препятствие. После подтверждённого создания строки без папки задачи доведи `task.md` до согласованного состояния; не создавай вторую строку. Уже слитый PR не создавай заново из-за пропущенной записи: подтверди слияние и заверши оставшиеся действия. Продолжай с первого незавершённого или утратившего пригодность шага. При отсутствии или противоречии записи, артефактов или рабочей копии остановись для выяснения фактов, не выдавая начало другой задачи за продолжение прежней. При внешней блокировке, отсутствии инструмента, неустранённой обязательной проверке или повторных неудачах сохрани причину, сделанное, следующий шаг и условие возобновления в `task.md`, отрази блокировку через `sov-tasks` при необходимости; не объявляй частичный результат завершением.

Отчитайся простым языком: какое поручение выполнено, результат для пользователя, проверенные факты, состояние публикации и ограничения. При подготовке требований прямо скажи, что поведение программы ещё не изменено. При остановке сообщи препятствие и точку продолжения; если нужно действие, назови **один** конкретный следующий шаг, используя только реально установленный интерфейс SOV.

## Контрольные сценарии

- **Спецификация с задачами:** запрос ограничен требованиями → `sov-spec` согласует сценарии и создаёт задачи через `sov-tasks`; отдельный субагент проверяет требования и покрытие; человек видит итоговый текст перед PR; задачи разработки не начинаются до подтверждённого слияния PR требований.
- **Подготовленная разработка:** опубликованные требования → `sov-plan` создаёт пригодный план → реализация с успешными обязательными проверками → независимое ревью результата → PR; запись `done` допустима лишь после подтверждённого слияния. Среднее замечание возвращает работу на ответственный шаг с повтором проверки.
- **Баг без исправления / с исправлением:** только поиск причины заканчивается отчётом со свидетельствами и предложением перепроверки, без `sov-plan` и кода; однозначный баг без отдельной опубликованной спецификации использует ожидаемое поведение из `task.md` и пригодный `research.md` как вход плана, затем план — как вход реализации. При нехватке свидетельств вернись к исследованию; при неясном или противоречащем требованиям поведении согласуй требования через `sov-spec` и `sov-review-spec` до реализации.
- **Баг с опубликованным требованием:** сверь `research.md` с применимым опубликованным поведением → `sov-plan` → `sov-implement` с пригодным планом → ревью. Если предлагаемое исправление меняет опубликованное правило, сначала согласуй изменение и проверь его через `sov-review-spec`.
- **Возобновление в новой сессии:** `/sov` без ID задачи ищет задачи постоянного владельца; при одной `in_progress` захватывает её лишь при пустом захвате либо после подтверждённой передачи от остановленного прежнего сеанса, затем сверяет worktree, артефакты и GitHub (слитый PR не публикуется повторно). Единственная `blocked` возвращает препятствие без выбора другой; несколько незавершённых задач требуют ID задачи; только при нуле таких задач выбирается новая `planned`. Другой сеанс того же владельца может одновременно вести **другую** задачу без изменения проектных правил.
- **Быстрая правка документа:** `/sov-fast` с очевидной обратимой правкой → краткая задача, без `research.md`/`plan.md` и итогового ревью при отсутствии проектного требования; проверены содержание, ссылки и diff, но не игровые тесты; при публикации файлов — PR по правилам проекта. Тот же запрос через `/sov` не разрешает пропуск шага без отдельного согласия человека.
- **Hook и основной код:** `/sov-fast` для установщика pre-push → реальный push и отказный сценарий, ревью назначается из-за риска отключить другие hooks; `/sov-fast` для основного игрового кода → независимое ревью обязательно даже при малом diff. Замечание до первого слияния исправляется в той же задаче и PR с повтором затронутых проверок. Hook/CI уже проверенного итогового commit учитываются без повторного ручного прогона при совместимых правилах проекта.
