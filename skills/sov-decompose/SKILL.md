# Декомпозиция опубликованных требований

`sov-decompose` превращает опубликованную Spec в проверяемые задачи реализации **только по явной просьбе** человека. Просьба подготовить Spec и задачи в одном поручении сохраняется до публикации требований и не требует повторного разрешения на декомпозицию. Простая публикация Spec не запускает этот шаг: оркестратор может лишь предложить его. Шаг не согласует продуктовое поведение вместо `sov-spec`, не проверяет требования вместо `sov-review-spec`, не составляет технический план вместо `sov-plan` и не начинает реализацию.

## Входы и условия начала

1. Получи от оркестратора явный запрос и его границы, путь к рабочей копии целевого проекта и общей `.sov/`, применимые правила, точные пути к опубликованным требованиям и свидетельство включения их версии в удалённый `main`. Если поручение сохраняется, получи ID и путь к каталогу задачи для записи результата в `task.md`; нового обязательного файла для декомпозиции нет. Не начинай до подтверждения публикации, в том числе когда черновик `spec.md` уже готов или CLI считает задачу готовой.
2. Прочитай `AGENTS.md`, `rules/index.md`, применимые правила, `docs/index.md`, опубликованную Spec и связанные требования/ADR. Сверь границы запроса, актуальность версии и существенные вопросы; через `sov-tasks` прочитай `list` и `list-completed`, при необходимости `show`/`show-completed` по ID, сопоставь содержание и критерии существующих активных и завершённых задач с требованиями. Не считай отсутствие карточек дефектом опубликованной Spec; при диагностике неполного архива остановись, не объявляй покрытие подтверждённым. Если требования противоречат друг другу, недостаточны для проверяемых результатов или публикация не подтверждена, передай препятствие оркестратору; не придумывай новое продуктовое поведение.

## Подготовь срезы и проверь граф

1. Перечисли результаты и сценарии из Spec в пределах запроса и свяжи каждый с существующей или предлагаемой задачей. Предпочитай вертикальные срезы, каждый из которых даёт наблюдаемый проверяемый результат; не разбивай работу лишь по слоям кода, если возможен сквозной результат. Если вертикальный срез невозможен (например, предварительная миграция или общий блокирующий фундамент), объясни причину и конкретную зависимость.
2. Для каждого нового среза сформулируй результат, границы, проверяемые критерии приёмки, ориентир объёма одной рабочей сессии и зависимости. Большой срез дели по наблюдаемым сценариям, маленькие связанные изменения объединяй, не жертвуя самостоятельной проверяемостью. Оценку объёма отмечай как оценку, а не обещание времени. Не превращай карточку в технический `plan.md`; способ выполнения конкретной выбранной задачи определит `sov-plan`.
3. Сопоставь все применимые требования с карточками, отметь уже покрытые и сознательно оставленные вне границ запроса с причиной. Сверь существующий граф, включая завершённые ID, исключи дубли, самозависимости, отсутствующие ссылки и циклы; предложенные зависимости должны вести к реальным задачам. Если существует завершённая задача подготовки Spec, её ID может быть зависимостью, но публикация требований проверяется отдельно. Для внешней опубликованной Spec либо отсутствующей задачи подготовки не выдумывай ID: зависимость на подготовку не требуется. Не создавай epics/groups или иной источник состояния.

## Создай задачи и передай результат

1. Если запрос включает создание карточек, передай подготовленные описания, критерии и зависимости `sov-tasks`; только он создаёт `task.yaml` через закреплённую CLI `sov-task` и сообщает выданные ID. Не присваивай ID сам и не редактируй хранилище напрямую. Создавай связанные карточки в порядке зависимостей; используй подтверждённые ID для следующих. Если ответ `create` потерян, прежде повтора сверь фактические карточки и намерение через `sov-tasks`, чтобы не создать дубль. При появлении параллельной карточки пересмотри покрытие и граф до следующего создания.
2. Повторно проверь покрытие, граф и критерии на фактически созданных ID, отсутствие дубликатов и соответствие опубликованной Spec. Запиши связь требований с ID, основания нестандартных срезов, проверки и остающиеся вопросы в `task.md` поручения, если он ведётся; не создавай обязательный отдельный артефакт. Верни оркестратору задачи, критерии, зависимости и ограничения. Создание задач не захватывает их и не начинает реализацию; перед будущим стартом заново проверяются актуальность требований и условия начала.

## Самопроверка сценариев

- **Полная декомпозиция:** опубликованная в удалённом `main` Spec с двумя сценариями → две проверяемые задачи или один обоснованный общий срез, оба сценария покрыты, граф без циклов; существующая карточка не дублируется.
- **Неполная декомпозиция:** критерий Spec не покрыт ни существующей, ни новой задачей → до передачи результата исправь покрытие либо явно сообщи препятствие, не объявляй работу полной.
- **Внешняя Spec:** опубликованные требования без задачи подготовки → карточки без фиктивного ID зависимости; публикация подтверждена отдельно.
- **Нет запроса или публикации:** после ревью черновика без push либо после публикации без просьбы о задачах → `sov-decompose` не запускается. Если Spec и задачи запрошены вместе, дождись публикации и затем выполни декомпозицию без нового вопроса.
