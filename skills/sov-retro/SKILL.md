# Ретроспектива сессий SOV

`sov-retro` — аналитический скил по **явной просьбе** через `/sov`, `/sov-retro` или прямое обращение. Не запускай его автоматически после `done`, неудачи, нескольких циклов ревью или замечания. Ретро не является обязательным шагом разработки и не возобновляет завершённую задачу. Предложения не дают разрешения менять проект или SOV.

## Определи границы и собери свидетельства

1. Установи целевой проект, конкретную задачу, перечисленные сессии либо набор задач и желаемый вопрос анализа. Если их нельзя установить однозначно, уточни границы до чтения чужих сессий. Прочитай `AGENTS.md`, `rules/index.md` и применимые правила целевого проекта. При обычном отчёте в диалоге не создавай новую задачу, claim, worktree или файл. Если человек отдельно запросил постоянный документ, применяй обычные правила проекта для сохраняемой работы, включая учёт задачи, проверки и публикацию; не превращай рекомендации в согласованные изменения.
2. Для известных ID получи состояние через [`sov-tasks`](../sov-tasks/SKILL.md): `list`, `show`, `list-completed`, `show-completed` по применимости. Читай `task.md`, `checks.md`, `review.md`, при необходимости `plan.md`/`research.md` и относящиеся к результату документы/историю Git в границах запроса. Учитывай дату, состояние файла или commit для каждого свидетельства. Не считай описание намерения доказательством выполнения; не считай отсутствие записи доказательством отсутствия действия. Историю сессий используй лишь при доступности и в заданных границах, отличая её от резюме задачи. Для ретро набора задач сравни условия и исходы каждой, не объявляй одну задачу повторяющимся паттерном.
3. Langfuse необязателен. При доступном **отдельном официальном скиле `langfuse`** используй его инструкции и CLI для чтения; не выводи команды, поля API или настройки доступа из этого аналитического скила. Запрашивай лишь ограниченный объём по известному ID задачи SOV или конкретным ID/ссылкам сессий, указанным человеком; перед использованием результата **проверь** ID задачи в данных трассы либо точное совпадение ID сессии. Совпадение даты, имени проекта или текста недостаточно: такой результат исключается даже при сходстве содержания. Если скил, CLI, доступ или подтверждённая связь отсутствуют, продолжай по локальным свидетельствам и назови ограничение. Недоступные или пустые трассы не доказывают, что агент ничего не сделал. Не сохраняй ключи и сырые трассы в отчёт или репозиторий.

## Восстанови ход и предложи улучшения

1. Собери краткую последовательность: вход и ожидания → решения и передачи между шагами → проверки и замечания → итог и публикация, когда применимо. Для каждого значимого вывода укажи **наблюдение**, точный источник (путь и запись/commit или ID сессии/трассы), **гипотезу причины** отдельно от факта и степень уверенности. Если источники противоречат или недоступны, покажи расхождение и границу вывода. Затраты времени, токенов и инструментов называй измеренными только при достоверных данных; иначе не оценивай их числом.
2. Различай проявление (навигация, проверки, стандарты, инструкции, затраты инструментов, доступ к информации) и уровень возможной причины (скил, маршрут, правило проекта, инструмент, проверка, документация, вход задачи, ограничение модели). Не переноси обязательные входы реализации на позднее ревью и не объявляй одиночный случай системным дефектом без дополнительных независимых свидетельств.
3. Для каждого предложения укажи адресат (**целевой проект** или **SOV**), связь со свидетельством и гипотезой, ожидаемую пользу, стоимость/ограничение и способ проверить эффект. Для механически обнаружимой проблемы сначала рассмотри детерминированную проверку. При слабой уверенности предложи способ собрать свидетельства или проверить гипотезу вместо обязательного изменения системы. Разделяй установленный результат, возможные улучшения и остающиеся вопросы.

## Передай отчёт

Дай отчёт в диалоге по умолчанию: объём и доступные источники, краткий ход, подтверждённые наблюдения и ограниченные гипотезы, предложения с проверкой эффекта и пробелы данных. Укажи, использовались ли трассы и как подтверждена связь; отсутствие Langfuse не блокирует отчёт. Не создавай документ и не редактируй инструкции по собственным рекомендациям. Если человек просит внедрить предложение, сначала определи и согласуй отдельный объём работы по правилам проекта.

## Контрольные сценарии

- `/sov` с просьбой о ретро одной завершённой задачи и `/sov-retro` с тем же ID дают один контракт и читают её архив без повторного claim.
- Пустой `/sov-retro` без однозначного контекста уточняет задачу или сессии; обычный `/sov` после `done` ретро не запускает.
- Трасса с явным ID задачи или точным ID сессии допускается после проверки связи; найденная лишь по времени/проекту/тексту исключается.
- Без ключей, CLI или трасс отчёт строится по артефактам с указанием ограничений; пустая трасса не опровергает выполненную проверку из `checks.md`.
- Просьба о ретро и предложение улучшить правило не меняют правило; отдельная просьба сохранить отчёт проходит правила сохраняемой работы.
