# Контракты и шаблоны артефактов SOV

Шаблоны артефактов задачи относятся к локальной папке `.sov/tasks/<task-id>/` целевого проекта. Они описывают содержание результатов, а не выполняют шаги; инструкции скилов добавляются отдельно. Основные требования и границы ответственности заданы [спецификацией SOV](../docs/sov-spec.md) (§§ 5–9); способы работы целевого проекта задаются его `AGENTS.md`, `rules/` и `docs/`. Копируйте только нужные для выбранного маршрута файлы, заменяйте подсказки в угловых скобках фактическими сведениями. Пустой шаблон не является пригодным результатом шага.

Для выбранного файлового источника [образцы `ROADMAP.md`](ROADMAP.md) и [`ARCHIVE.md`](ARCHIVE.md) предназначены для первой инициализации `.sov/` **основной** папки проекта при остановленных писателях, а не для локальной папки отдельной задачи или замены существующего состояния. Дальнейшие записи выполняет [`sov-tasks`](../skills/sov-tasks/SKILL.md) через `sov-state`.

Шаблоны [субагентов OpenCode](opencode/agents/) устанавливаются **в проект** для уровней моделей `standard`/`advanced`, а не в папку локальных артефактов задачи. В проектных копиях можно менять поле `model`; инструкция установки — в [README](../README.md#первое-подключение).

## Передача работы между шагами

Оркестратор получает идентификатор задачи, общий статус, владельца, захват и зависимости через `sov-tasks` и не дублирует их в артефактах. Для продолжения из новой сессии он определяет устойчивого владельца по правилам проекта, получает новый UUID через установленную CLI, находит его незавершённую задачу и захватывает её перед работой; `task.md` содержит контекст для сверки состояния, но не заменяет запись списка. При начале сохраняемой работы он создаёт папку `.sov/tasks/<task-id>/`, если её нет, и ведёт `task.md`. Передавая формальный шаг субагенту выбранного уровня, он явно указывает **идентификатор задачи и UUID подтверждённого захвата**, **путь к рабочей копии кода** (основная копия или worktree), **абсолютный путь к общей локальной папке артефактов** (при наличии задачи), цель и допустимые изменения, применимое ожидаемое поведение (опубликованные требования новой функциональности либо однозначное исправление из `task.md` без противоречия опубликованным источникам) и правила, а также нужные входы и ожидаемый результат. Относительный `.sov/` внутри worktree не служит путём к общей папке задачи. Скилы шагов читают код и постоянные документы из переданной рабочей копии, а локальные артефакты — из переданной папки; список задач получают только через `sov-tasks`.

Каждый исполнитель возвращает оркестратору созданные и изменённые файлы, фактические проверки и их результаты, вопросы и оставшиеся препятствия. Оркестратор проверяет входы и результат перед переходом: файлы относятся к нужной задаче, актуальны для текущих требований и изменений, достаточны для следующего шага и не содержат открытых блокирующих вопросов. После изменения входов перепроверяются зависимые результаты; повторяются только затронутые шаги. Маршрут, решения о пропуске или повторе шагов и сведения для продолжения записываются в `task.md`. Нельзя считать заполнение шаблона, утверждение «проверено» без результатов или наличие файла само по себе подтверждением выполнения шага.

## Где живут данные

| Сведения | Владелец и источник |
| --- | --- |
| Идентификатор, название, общий статус (`planned`, `in_progress`, `blocked`, `done`, `cancelled`), зависимости, владелец, захват и очередь | `sov-tasks`; при файловом учёте — существующий `.sov/ROADMAP.md` и архив терминальных задач `.sov/ARCHIVE.md`, читаемые и изменяемые только через `sov-state`. Остальные скилы к ним напрямую не обращаются. |
| Запрос, границы, критерии, маршрут, прогресс шагов, препятствия и подтверждение публикации | Оркестратор, локальный `task.md`; это не второе хранилище общего статуса задачи. |
| Проекты требований, технический план, свидетельства, проверки и ревью | Ответственные за шаги, локальные файлы задачи из таблицы ниже. |
| Согласованное ожидаемое поведение и долговременные решения/ограничения | Опубликованные `docs/specs/`, `docs/adrs/` и `rules/` целевого проекта; для однозначного бага без отдельной спецификации — также ожидаемое поведение в `task.md`, не противоречащее опубликованным источникам и подтверждённое исследованием. Локальный `spec.md` не заменяет опубликованные требования новой функциональности. |

## Шаблоны и условия применения

| Шаблон | Ответственный | Когда нужен; постоянный источник |
| --- | --- | --- |
| [`task.md`](task.md) | Оркестратор | При сохраняемой работе: запрос, маршрут, контекст и продолжение; ссылается на применимые `docs/` и `rules/`. |
| [`spec.md`](spec.md) | `sov-spec` | При подготовке новых или изменяемых продуктовых требований; согласованное содержание публикуется в `docs/specs/`. Не нужен при пригодных опубликованных требованиях либо однозначном исправлении без изменения поведения. |
| [`adr.md`](adr.md) | `sov-spec` | При существенном техническом выборе во время обсуждения фичи; долговременное решение публикуется в `docs/adrs/`. |
| [`research.md`](research.md) | `sov-research` | При исследовании бага; фиксирует свидетельства и степень уверенности, не заменяет опубликованные требования и не создаёт новую спецификацию. |
| [`plan.md`](plan.md) | `sov-plan` | Для обычного маршрута разработки и исправления: пригодный технический план обязателен **перед реализацией**, не перед самим `sov-plan`; в явном `/sov-fast` при обоснованном пропуске решение и проверки фиксируются в `task.md`. При исследовании без исправления не требуется. |
| [`checks.md`](checks.md) | Агент, выполнивший проверки | Когда проверки выполнялись, обязательно для разработки: команды/действия, фактические результаты и состояние изменений. Команды определяются `rules/` проекта. |
| [`review.md`](review.md) | Независимый проверяющий | Один файл для обязательных ревью и назначенных промежуточных проверок: отдельные датированные записи сохраняют прежние выводы, ID замечаний и результаты повторных проверок. |

`task.md` содержит ссылки на входы и итоги шагов, но не копирует полный текст соседних файлов. `spec.md` — проект, а не параллельная опубликованная спецификация. Шаблоны не задают структуру продуктовых документов и правила оформления целевого проекта.

## Примеры состава для маршрутов

| Поручение | Локальные файлы при типовом ходе | Результат за пределами папки задачи |
| --- | --- | --- |
| Подготовить требования фичи и задачи реализации | `task.md`, `spec.md`, `review.md`; `adr.md` при значимом выборе; `checks.md` только если выполнялись проверки | После независимого ревью и публикации — `docs/specs/`, при необходимости `docs/adrs/`; записи задач через `sov-tasks`. Задачи реализации не начинаются до публикации требований. |
| Разработать подготовленную задачу | `task.md`, `plan.md`, `checks.md`, `review.md`; `spec.md` только при согласованном уточнении поведения, с ревью требований | Код и тесты в рабочей копии, затронутые `docs/` и `rules/`; публикация по правилам проекта. |
| Исследовать баг без исправления | `task.md`, `research.md`; `review.md` при запрошенной/необходимой независимой перепроверке; `checks.md` если выполнялись проверки кода | Отчёт человеку со свидетельствами и ограничениями. `plan.md` и публикация не обязательны; `spec.md` не создаётся автоматически. |
| Исправить однозначный баг без отдельной спецификации | `task.md` с ожидаемым поведением, `research.md`, затем `plan.md`, `checks.md`, `review.md` | Код и тесты по непротиворечивому опубликованным требованиям поведению; разовое описание бага не публикуется автоматически как новое требование. При неоднозначности или изменении поведения — `sov-spec` и `sov-review-spec` до реализации. |
| Небольшое исправление через `/sov-fast` | `task.md` с фактами, риском и выбранным маршрутом, `checks.md`; `research.md`, `plan.md`, `review.md` при необходимости | Применимые проверки, самопроверка diff при пропуске ревью и публикация по правилам проекта; основной код игры или движка требует независимого ревью. |

Простое обсуждение может завершиться ответом без локальных файлов. Набор файлов всегда определяется поручением, пригодностью уже существующих результатов и применимыми правилами проекта.
